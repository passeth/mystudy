# S20. 일상 워크플로: Explore → Plan → Code → Commit, 리뷰, 컨텍스트 명령

## 오늘의 목표
- Explore → Plan → Code → Commit 네 단계가 각각 무엇을 위한 것인지 설명하고, 작은 작업에 적용할 수 있다.
- 커밋 전에 `/diff`와 `/code-review`로 변경을 두 번 확인하는 이유와 방법을 말할 수 있다.
- `/context`, `/compact`, `/clear` 중 지금 상황에 맞는 명령을 고를 수 있다.

## 핵심 정리

### 네 단계의 리듬
집을 고칠 때 벽부터 부수지 않죠. 둘러보고, 도면을 그리고, 공사하고, 검수해요. Claude Code 101 코스가 중심에 두는 작업 흐름도 같아요. **탐색**(Explore) → **계획**(Plan) → **구현**(Code) → **커밋**(Commit)이에요. 이 리듬 없이 바로 "코드 써 줘"로 가면 나중에 고쳐 달라고 하는 횟수가 늘어요.

- **Explore와 Plan**: S19의 Plan 모드가 이 두 단계를 한 번에 맡아요. Claude가 관련 파일을 읽고 계획을 내면, 마음에 들 때까지 고쳐 달라고 해요.
- **Code**: 계획을 승인하면 구현이 시작돼요. 여기서 차이를 만드는 건 Claude가 스스로 돌려 볼 수 있는 **확인 수단**이에요. 테스트, 빌드, 린터처럼 통과와 실패가 나오는 것이면 돼요. "끝났어요"라는 말 대신 실행한 명령과 출력을 증거로 달라고 하세요.
- **Commit**: 변경을 검토한 뒤 "변경 내용을 설명하는 메시지로 커밋해 줘"라고 하면 Claude가 스테이징과 커밋을 해요. PR도 만들어 달라고 할 수 있어요.

### 커밋 전 리뷰: 두 번 본다
Claude의 요약은 사실이어도 빠진 것이 있을 수 있어요. 그리고 코드를 쓴 세션은 그 코드의 가장 좋은 심사자가 아니에요. 그래서 두 번 봐요.

1. **내 눈으로**: `/diff`는 작업 폴더의 변경을 파일별로 보여 줘요. 시키지 않은 변경, 약해진 테스트(건너뛰거나 지운 것), 새로 추가된 패키지와 하드코딩된 값을 찾아보세요.
2. **새 눈으로**: `/code-review`는 지금 대화의 기록을 모르는 별도 컨텍스트에서 변경을 검토하고 결과를 보고해요. 터미널에서는 백그라운드 서브에이전트로 돌고, `--fix`를 붙이지 않으면 보고만 해요. 사용량에 포함되니 중요한 변경에 쓰세요.

둘 다 git을 읽기 때문에 프로젝트가 git 저장소여야 해요. 변경이 통째로 틀렸다면 `/rewind`(또는 빈 프롬프트에서 `Esc` 두 번)로 되감아요. 단, 셸 명령만으로 바뀐 파일은 되감기 대상이 아니에요. GitHub PR에 자동으로 달리는 Code Review는 Team·Enterprise용 별도 서비스예요(S26).

### 컨텍스트 명령 세 가지
S03과 S18에서 본 것처럼 읽은 파일과 명령 출력은 전부 컨텍스트에 쌓여요. 가득 차면 자동으로 압축되지만, 무엇을 남기고 언제 비울지 직접 정할 수도 있어요.

| 명령 | 하는 일 | 쓸 때 |
|---|---|---|
| `/context` | 컨텍스트 사용량을 항목별로 보여 줌 | 무엇이 자리를 차지하는지 궁금할 때 |
| `/compact [지시]` | 지금까지의 대화를 요약해 자리를 비움 | 같은 작업을 계속하는데 컨텍스트가 찼을 때 |
| `/clear` | 빈 컨텍스트로 새 대화 시작 | 관계없는 새 작업으로 넘어갈 때 |

`/compact 인증 버그 수정 위주로`처럼 무엇을 남길지 지시할 수 있어요. `/clear` 한 대화는 `/resume`으로 다시 열 수 있어요. 압축 뒤에도 프로젝트 루트의 CLAUDE.md는 디스크에서 다시 읽히지만, 대화로만 말한 규칙은 흐려질 수 있어요. 계속 지켜야 할 것은 CLAUDE.md에 적어요(S21). 같은 걸 두 번 고쳐 줬는데도 틀리면, 세 번째 지적보다 `/clear` 후 더 나은 프롬프트 하나가 낫다는 것이 문서의 조언이에요. 압축과 되감기를 긴 세션에서 쓰는 법은 S23에서 봐요.

## 직접 해 보기 (5분)
`~/cc-playground`에서 해 보세요.

1. 한 바퀴 돌기: "이 폴더를 git 저장소로 만들고 첫 커밋을 해 줘"로 준비한 뒤, Plan 모드에서 "이 폴더의 파일을 표로 설명하는 README.md를 만들 계획을 세워 줘"라고 하세요. 계획을 승인하고, 끝나면 `/diff`로 변경을 읽고 `/code-review`를 돌린 다음 "변경 내용을 설명하는 메시지로 커밋해 줘"라고 하세요.
   - 관찰: 리뷰 결과는 대화에 어떻게 도착하나요? 지적이 있다면 "지금 고친다 / 이유를 묻는다 / 그냥 둔다" 중 어디에 넣을지 정해 보세요.
2. 컨텍스트 보기: `/context`로 가장 큰 항목을 찾고, `/compact README 작업 위주로`를 실행한 뒤 `/context`를 다시 보세요. 마지막으로 `/clear`를 실행하세요.
   - 관찰: 압축 전후에 무엇이 줄었고 무엇이 그대로인가요?

## 확인 문제
1. Explore와 Plan 두 단계를 한 번에 맡기기에 가장 알맞은 것은?
   - (a) Accept edits 모드
   - (b) Plan 모드
   - (c) `/clear`
2. 결제 버그 수정을 막 끝내고, 관계없는 문서 작업을 시작하려고 해요. 알맞은 명령은?
   - (a) `/compact`
   - (b) `/context`
   - (c) `/clear`
3. `/code-review`에 대한 설명으로 맞는 것은?
   - (a) 지금 대화의 기록을 그대로 이어받아 같은 맥락에서 검토한다
   - (b) 별도 컨텍스트에서 변경을 검토해 결과를 보고하고, `--fix` 없이는 고치지 않는다
   - (c) 조직 Owner가 켜야 하고 GitHub PR에만 댓글을 단다
4. (서술형) Claude가 "다 됐어요, 테스트도 통과해요"라고 요약했어요. 이 말만 믿고 커밋하면 안 되는 이유와, 커밋 전에 할 두 가지 확인을 써 보세요.
5. (상황형) 고객사 팀장이 물어요. "AI가 짠 코드를 우리가 어떻게 믿고 커밋합니까?" 오늘 배운 흐름으로 어떻게 답할까요?

## FDE 관점
파일럿에서 FDE가 보여 줘야 하는 건 "Claude가 코드를 잘 쓴다"가 아니라 "이 팀이 믿고 커밋할 수 있는 절차가 있다"예요. 네 단계 리듬이 그 절차예요. 계획은 고객 개발자가 승인하고, 구현은 고객의 기존 테스트로 확인하고, 커밋 전에는 사람의 diff 검토와 새 컨텍스트의 리뷰를 거쳐요. 마지막 승인은 사람이 한다는 점을 분명히 하세요. 파일럿 계획서의 "먼저 출시할 부분"은 이 한 바퀴로 끝낼 수 있는 크기의 작업들로 쪼개면 좋고, 한 바퀴에 걸린 시간과 리뷰에서 되돌아간 횟수는 기준선과 비교할 수 있는 측정값이 돼요.

## 영상 대본

### 장면 1 · 오늘의 질문 (약 25초)
**화면:** 프롬프트 "기능 만들어 줘"에서 바로 코드 더미로 화살표가 가고, 그 뒤로 "아니 그게 아니라…" 말풍선이 세 번 연달아 뜸. 제목 "왜 자꾸 다시 시키게 될까?"
**내레이션:** 바로 코드부터 쓰게 하면 꼭 이렇게 돼요. 그게 아니라고 세 번쯤 말하게 되죠. 오늘은 이 왕복을 줄이는 하루의 작업 흐름을 볼게요.

### 장면 2 · 네 단계 (약 30초)
**화면:** 가로로 네 칸이 차례로 켜짐: Explore(돋보기), Plan(도면), Code(망치), Commit(도장). 아래에 집 수리 그림이 같은 순서로 진행됨.
**내레이션:** 집을 고칠 때 벽부터 부수지 않죠. 둘러보고, 도면을 그리고, 공사하고, 검수해요. 클로드 코드의 작업 흐름도 같아요. 탐색, 계획, 구현, 커밋이에요.

### 장면 3 · 탐색과 계획 (약 35초)
**화면:** 상태 표시줄 "plan mode on". Claude 아이콘이 파일을 훑고 계획 문서를 냄. 사람이 한 줄에 빨간 펜을 대자 그 줄이 다시 쓰임.
**내레이션:** 앞의 두 단계는 플랜 모드가 한 번에 맡아요. 클로드가 파일을 읽고 계획을 내면, 마음에 들 때까지 고쳐요. 아직 코드가 없어서 방향을 바꾸기가 가장 쉬워요.

### 장면 4 · 구현과 확인 수단 (약 40초)
**화면:** Claude가 코드를 고치고 "테스트 실행" 버튼을 스스로 누름. 빨간 실패 → 다시 고침 → 초록 통과. 옆에 영수증 모양의 "실행한 명령 + 출력".
**내레이션:** 구현 단계의 열쇠는 확인 수단이에요. 테스트처럼 통과와 실패가 나오는 걸 주면 클로드가 스스로 고리를 닫아요. 끝났다는 말 대신 실행한 명령과 출력을 증거로 받으세요.

### 장면 5 · 내 눈으로 (약 35초)
**화면:** 화면 가득 diff: 빨간 줄과 초록 줄. 돋보기가 세 곳을 짚음: "시키지 않은 변경", "건너뛴 테스트", "새 패키지".
**내레이션:** 커밋 전에는 두 번 봐요. 첫 번째는 내 눈이에요. 슬래시 디프로 변경을 읽어요. 시키지 않은 변경, 약해진 테스트, 새로 들어온 패키지를 찾아보세요.

### 장면 6 · 새 눈으로 (약 40초)
**화면:** 왼쪽에 긴 대화 기록을 짊어진 "작성한 세션". 오른쪽에 빈손의 "리뷰어"가 diff만 보고 메모 네 줄을 건넴. 메모는 세 바구니로 나뉨: "지금 고친다", "이유를 묻는다", "그냥 둔다".
**내레이션:** 두 번째는 새 눈이에요. 슬래시 코드 리뷰는 지금 대화를 모르는 별도의 컨텍스트에서 변경을 봐요. 쓴 사람의 생각에 끌려가지 않죠. 지적은 고칠 것, 물어볼 것, 둘 것으로 나눠요.

### 장면 7 · 컨텍스트가 찬다 (약 30초)
**화면:** S18의 세로 통이 다시 등장해 블록으로 거의 참. 옆에 `/context` 화면처럼 색깔 격자와 항목별 막대.
**내레이션:** 이렇게 일하다 보면 컨텍스트가 차요. 슬래시 컨텍스트를 치면 무엇이 자리를 차지하는지 보여 줘요.

### 장면 8 · 컴팩트와 클리어 (약 40초)
**화면:** 갈림길. 왼쪽 길 "같은 작업 계속" → `/compact`: 블록이 요약 블록으로 눌림. 오른쪽 길 "새 작업" → `/clear`: 통이 비워지고 이전 통은 서랍 "/resume"에 들어감.
**내레이션:** 같은 작업을 이어 간다면 슬래시 컴팩트로 요약해요. 관계없는 새 작업이라면 슬래시 클리어로 비워요. 지운 대화는 나중에 다시 열 수 있어요.

### 장면 9 · 고객 앞에서 (약 35초)
**화면:** 팀장 말풍선 "AI 코드를 어떻게 믿죠?" 아래에 컨베이어 벨트: 계획 승인(사람) → 테스트 통과 → diff 검토(사람) → 새 눈 리뷰 → 커밋. 사람 단계에 굵은 테두리.
**내레이션:** 고객이 묻는 건 믿을 수 있느냐예요. 답은 절차예요. 계획은 사람이 승인하고, 테스트로 확인하고, 커밋 전에 두 번 봐요. 마지막 승인은 사람이에요.

### 장면 10 · 요약과 예고 (약 25초)
**화면:** 세 줄 요약: "1. 탐색 → 계획 → 구현 → 커밋 2. 커밋 전에 두 번 본다 3. 이어 가면 compact, 새 작업은 clear". 아래에 "다음: S21 CLAUDE.md와 서브에이전트".
**내레이션:** 정리할게요. 탐색하고, 계획하고, 구현하고, 커밋해요. 커밋 전에는 두 번 봐요. 이어 갈 땐 컴팩트, 새 작업은 클리어예요. 다음 시간에는 클로드가 프로젝트를 기억하게 하는 법을 볼게요.

## 정답과 해설
1. (b). Plan 모드에서 Claude는 읽고 탐색해 계획을 내고, 승인 전에는 소스를 고치지 않아요.
2. (c). 관계없는 작업으로 넘어갈 때는 빈 컨텍스트가 좋아요. 이전 대화는 `/resume`으로 다시 열 수 있어요.
3. (b). (c)는 GitHub PR용 별도 서비스인 Code Review에 대한 설명이에요.
4. 예시 답: 요약은 사실이어도 빠뜨린 변경이 있을 수 있고, 코드를 쓴 세션은 자기 판단에 끌려가기 쉽다. 그래서 (1) `/diff`로 시키지 않은 변경, 약해진 테스트, 새 패키지를 직접 확인하고, (2) `/code-review`로 대화 기록이 없는 새 컨텍스트의 검토를 받는다. 테스트 통과는 말이 아니라 실행 출력으로 확인한다.
5. 예시 답: "믿음이 아니라 절차로 커밋합니다"라고 답한다. 계획 단계에서 사람이 범위를 승인하고, 구현은 팀의 기존 테스트로 확인하고, 커밋 전에 사람이 diff를 읽고 별도 컨텍스트의 리뷰를 받는다. 틀린 변경은 되감을 수 있고, 최종 승인과 병합은 기존 코드 리뷰 절차대로 사람이 한다. 파일럿에서는 이 한 바퀴에 걸린 시간과 리뷰에서 되돌아간 횟수를 기록해 기준선과 비교하자고 제안한다.
