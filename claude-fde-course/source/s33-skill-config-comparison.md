# S33. 설정과 여러 파일 skill, 다른 기능과 비교

## 오늘의 목표
- frontmatter의 주요 필드로 "누가 부를 수 있는지"와 "어떤 도구를 미리 승인할지"를 설정할 수 있다.
- 참고 파일과 스크립트를 가진 여러 파일 skill의 구조를 짤 수 있다.
- 어떤 요구가 왔을 때 CLAUDE.md, skill, hook, 서브에이전트, MCP 중 무엇에 맞는지 고를 수 있다.

## 핵심 정리

### 설정은 frontmatter에 적는다
S32의 skill에는 `name`과 `description`만 있었죠. frontmatter는 skill의 **설정판**이에요. 자주 쓰는 필드는 이래요.

| 필드 | 하는 일 |
|---|---|
| `name` | 명령 이름. 생략하면 폴더 이름 |
| `description` | 무엇을 하고 언제 쓰는지. Claude가 고를 때 읽는다 |
| `when_to_use` | 발동 문구나 예시 요청을 설명 뒤에 덧붙인다 |
| `argument-hint` | 자동완성에 보여 줄 인자 힌트. 예: `[티켓번호]` |
| `disable-model-invocation` | `true`면 Claude가 스스로 부르지 못한다. 사용자가 `/이름`으로만 |
| `user-invocable` | `false`면 `/` 메뉴에서 숨긴다. Claude만 부른다 |
| `allowed-tools` | skill이 발동된 그 턴 동안 승인 없이 쓸 도구 |
| `context`, `agent` | `context: fork`면 서브에이전트에서 실행. `agent`로 종류 지정 |
| `paths` | 이 파일 패턴을 다룰 때만 skill을 활성화 |

알아 둘 점 세 가지예요.
- 모든 필드는 선택이고 `description`만 권장이에요. 필드 이름을 틀리게 쓰면 오류 없이 **조용히 무시**돼요. 하이픈까지 정확히 쓰세요.
- `allowed-tools`는 "이것만 쓸 수 있다"가 아니라 **"이건 묻지 않고 써도 된다"**예요. 목록에 없는 도구도 평소 권한 규칙대로 쓸 수 있고, 사전 승인은 다음 메시지를 보내면 사라져요. 도구를 막으려면 `disallowed-tools`나 S25의 권한 규칙을 써요.
- 배포처럼 부작용이 있는 절차에는 `disable-model-invocation: true`를 붙여요. Claude가 "코드가 준비된 것 같으니 배포하자"고 스스로 정하면 안 되니까요.

### 여러 파일 skill
본문이 길어지면 폴더 안에 파일을 나눠요. S32의 단계적 공개 3단계가 이거예요.

```text
release-notes/
├── SKILL.md          # 개요와 길 안내 (필수)
├── style-guide.md    # 자세한 규칙. 필요할 때만 읽는다
└── scripts/
    └── collect.sh    # 실행만 한다. 출력만 컨텍스트에 들어온다
```

```markdown
---
name: release-notes
description: 지난 릴리스 이후의 커밋을 모아 릴리스 노트 초안을 쓴다. 사용자가 릴리스 노트나 변경 내역 정리를 요청할 때 쓴다.
allowed-tools: Bash(${CLAUDE_SKILL_DIR}/scripts/collect.sh *)
---

1. `${CLAUDE_SKILL_DIR}/scripts/collect.sh`를 실행해 커밋 목록을 얻는다.
2. 분류와 문체는 [style-guide.md](style-guide.md)를 따른다.
3. 초안을 보여 주고 확인을 받는다.
```

`${CLAUDE_SKILL_DIR}`은 이 skill 폴더의 경로로 바뀌는 변수예요. 본문과 `allowed-tools`에 같은 변수를 쓰면 skill이 어디에 설치돼 있든 스크립트가 승인 창 없이 돌아요. 권장 사항: `SKILL.md`는 500줄 아래로 두고, 참고 파일은 `SKILL.md`에서 바로 한 단계로 연결하세요(파일이 또 다른 파일을 가리키는 식으로 깊어지면 Claude가 일부만 읽을 수 있어요).

### 다른 기능과 비교
| 기능 | 한 줄 정의 | 컨텍스트에 들어오는 때 | 누가 발동하나 | 맞는 용도 |
|---|---|---|---|---|
| CLAUDE.md | 항상 읽는 프로젝트 메모 | 매 세션 시작, 전부 | 자동 | "항상 이렇게" 규칙, 빌드 명령 |
| Skill | 필요할 때 꺼내는 절차와 지식 | 설명은 시작 때, 본문은 쓸 때 | Claude(설명 맞추기) 또는 사용자(`/이름`) | 반복 절차, 가끔 필요한 참고 자료 |
| Hook | 정해진 순간에 도는 스크립트 | 들어오지 않음(출력을 돌려줄 때만) | Claude Code가 이벤트마다. Claude의 판단 없이 | 매번 반드시 지켜야 하는 규칙 |
| 서브에이전트 | 따로 떨어진 컨텍스트의 작업자 | 별도 컨텍스트. 요약만 돌아옴 | Claude나 사용자가 일을 맡길 때 | 파일을 많이 읽는 조사, 병렬 작업 |
| MCP | 바깥 시스템과의 연결 | 도구 이름은 시작 때, 스키마는 쓸 때 | Claude가 도구를 부를 때 | 외부 데이터 읽기와 행동 |

고르는 요령은 이래요. 항상 알아야 하면 CLAUDE.md, 가끔 필요하면 skill, **반드시** 매번이어야 하면 hook이에요. skill이나 CLAUDE.md의 지시는 부탁이지 보장이 아니거든요. 대화를 어지럽힐 큰 작업은 서브에이전트, 바깥 시스템은 MCP예요. 섞어 쓰기도 해요. S28~S31의 MCP가 연결을 주고, skill이 "그 연결을 우리 팀 방식으로 쓰는 법"을 줘요.

## 확인 문제
1. `allowed-tools: Bash(git status *)`가 뜻하는 것은?
   - (a) 이 skill이 도는 동안 Claude는 `git status`만 쓸 수 있다
   - (b) skill이 발동된 턴 동안 `git status`는 승인 없이 쓸 수 있고, 다른 도구는 평소 권한 규칙을 따른다
   - (c) 이 세션이 끝날 때까지 모든 Bash 명령이 승인된다
2. 여러 파일 skill에서 `scripts/` 안의 스크립트는?
   - (a) skill이 발동되면 코드 전체가 컨텍스트에 들어온다
   - (b) 세션 시작 때 미리 실행된다
   - (c) Claude가 실행하고, 출력만 컨텍스트에 들어온다
3. "`.env` 파일은 절대 수정하지 않는다"를 **확실히** 지키게 하려면?
   - (a) hook으로 수정을 막는다
   - (b) skill 본문에 굵게 적는다
   - (c) CLAUDE.md 맨 위에 적는다
4. (서술형) skill과 서브에이전트의 차이를 "컨텍스트"라는 말을 넣어 두세 문장으로 설명해 보세요.
5. (상황형) 고객사 리드가 세 가지를 원해요. (1) 모든 코드에 사내 명명 규칙 적용, (2) 장애 보고서를 정해진 순서로 작성, (3) 장애 티켓을 사내 티켓 시스템에서 가져오기. 각각 어떤 기능으로 제안할까요?

## FDE 관점
현장에서 고객은 기능 이름으로 묻지 않아요. "Claude가 이걸 항상 했으면", "이건 절대 안 했으면", "우리 시스템을 봤으면"이라고 말해요. FDE의 일은 그 말을 오늘의 표로 번역하는 거예요. 잘못 고르면 파일럿에서 바로 드러나요. 반드시 지켜야 할 보안 규칙을 skill에 적어 두면 어느 날 어겨지고, 가끔 쓰는 긴 절차를 CLAUDE.md에 넣으면 컨텍스트가 무거워져 다른 지시까지 흐려져요. 파일럿 계획의 첫 출시 범위를 적을 때 "규칙은 hook 몇 개, 절차는 skill 몇 개, 연결은 MCP 서버 하나"처럼 기능별로 나눠 적으면 고객 개발팀이 누가 무엇을 관리할지 정하기 쉬워요.

## 복습 카드
- Q: Claude가 스스로 부르지 못하게 하는 필드는? / A: `disable-model-invocation: true`. 사용자가 `/이름`으로만 부른다.
- Q: `allowed-tools`는 제한인가 사전 승인인가? / A: 사전 승인. 발동된 턴 동안 묻지 않고 쓰게 할 뿐, 다른 도구를 막지 않는다.
- Q: skill 폴더 경로로 바뀌는 변수는? / A: `${CLAUDE_SKILL_DIR}`.
- Q: 매번 반드시 지켜야 하는 규칙은 어디에? / A: hook. skill과 CLAUDE.md의 지시는 부탁이지 보장이 아니다.
- Q: MCP와 skill을 함께 쓰면 각각 무엇을 주나? / A: MCP는 연결과 도구를, skill은 그 도구를 잘 쓰는 방법을 준다.

## 영상 대본

### 장면 1 · 오늘의 질문 (약 25초)
**화면:** 고객 말풍선 세 개가 차례로 뜸: "항상 이렇게 해 주세요", "이건 절대 하지 마세요", "우리 시스템을 봐 주세요". 그 아래 서랍 다섯 개가 닫힌 채 나란히 있고 물음표.
**내레이션:** 고객의 요청은 다 다르게 생겼어요. 항상 해 달라, 절대 하지 마라, 우리 시스템을 봐 달라. 이걸 전부 스킬에 넣으면 될까요? 오늘은 스킬의 설정과, 다른 기능과의 차이를 볼게요.

### 장면 2 · 설정판 (약 35초)
**화면:** 스킬 문서의 위 칸이 확대되어 스위치 여러 개가 달린 설정판으로 바뀜. 스위치 이름표: "이름", "설명", "누가 부르나", "미리 승인할 도구".
**내레이션:** 스킬 파일의 윗부분은 설정판이에요. 지난 시간에는 이름과 설명만 적었죠. 여기에 스위치를 더 달 수 있어요. 누가 부를 수 있는지, 어떤 도구를 미리 승인할지 같은 것들이에요.

### 장면 3 · 누가 부를 수 있나 (약 40초)
**화면:** 문 하나에 손잡이 두 개: "사용자"와 "모델". 첫 번째 스위치를 내리면 "모델" 손잡이가 잠김(배포 스킬 예시). 두 번째 스위치를 내리면 "사용자" 손잡이가 숨겨짐(배경 지식 예시).
**내레이션:** 기본은 사용자와 클로드 둘 다 부를 수 있어요. 스위치 하나로 클로드가 스스로 부르는 걸 막을 수 있어요. 배포처럼 사람이 때를 정해야 하는 일에 써요. 반대로 메뉴에서 숨겨서 클로드만 쓰게 할 수도 있어요.

### 장면 4 · 사전 승인은 제한이 아니다 (약 40초)
**화면:** 출입 게이트 그림. 초록 패스를 든 도구 하나는 멈추지 않고 통과. 나머지 도구들은 평소처럼 검문소에서 확인받고 통과. 위에 "막는 것이 아니라, 묻지 않는 것". 시계가 돌자 초록 패스가 사라짐.
**내레이션:** 헷갈리기 쉬운 설정이 하나 있어요. 미리 승인할 도구를 적는 칸이에요. 이건 이것만 쓰라는 제한이 아니에요. 이건 묻지 않고 써도 된다는 뜻이에요. 다른 도구는 평소 규칙대로예요. 그리고 다음 메시지를 보내면 승인은 사라져요.

### 장면 5 · 파일을 나눈다 (약 40초)
**화면:** 스킬 폴더가 펼쳐짐. 맨 위에 얇은 문서 "개요와 길 안내", 그 아래 두꺼운 문서 "자세한 규칙", 그 아래 톱니바퀴 아이콘 "스크립트". 개요 문서에서 나머지 둘로 화살표.
**내레이션:** 본문이 길어지면 파일을 나눠요. 맨 위 파일은 개요와 길 안내만 맡아요. 자세한 규칙은 다른 파일에 두고, 필요할 때만 읽게 해요. 정해진 계산이나 수집은 스크립트에 맡겨요.

### 장면 6 · 스크립트는 결과만 (약 35초)
**화면:** 톱니바퀴 스크립트가 돌아가고, 긴 코드 두루마리는 폴더 안에 그대로 남음. 작은 결과 쪽지 한 장만 "컨텍스트" 상자로 들어감.
**내레이션:** 스크립트는 읽는 게 아니라 실행해요. 코드가 아무리 길어도 대화에 들어오는 건 결과뿐이에요. 그래서 매번 같은 결과가 나와야 하는 일은 스크립트가 맞아요.

### 장면 7 · 다섯 서랍 (약 40초)
**화면:** 서랍 다섯 개가 하나씩 열리며 이름표가 붙음: "CLAUDE.md: 항상 읽는 메모", "Skill: 필요할 때 꺼내는 절차", "Hook: 정해진 순간에 도는 스크립트", "서브에이전트: 따로 일하는 작업자", "MCP: 바깥 시스템 연결".
**내레이션:** 이제 다섯 가지를 나란히 놓아 볼게요. 클로드 엠디는 항상 읽는 메모예요. 스킬은 필요할 때 꺼내는 절차예요. 훅은 정해진 순간에 자동으로 도는 스크립트예요. 서브에이전트는 따로 떨어져 일하는 작업자예요. 엠씨피는 바깥 시스템과의 연결이에요.

### 장면 8 · 부탁과 보장 (약 40초)
**화면:** 저울. 왼쪽 접시 "부탁: CLAUDE.md, Skill" 위에 손글씨 쪽지. 오른쪽 접시 "보장: Hook" 위에 자물쇠. 아래에 "절대 안 되는 일 → 자물쇠 쪽".
**내레이션:** 가장 중요한 구분은 이거예요. 메모와 스킬에 적은 지시는 부탁이에요. 클로드가 읽고 따르지만, 보장은 아니에요. 훅은 클로드의 판단과 상관없이 실행돼요. 그래서 절대 어기면 안 되는 규칙은 훅에 둬요.

### 장면 9 · 고객 앞에서 (약 35초)
**화면:** 장면 1의 고객 말풍선 세 개가 서랍으로 날아감: "항상 이렇게" → CLAUDE.md, "절대 하지 마세요" → Hook, "우리 시스템을 봐 주세요" → MCP. 네 번째 말풍선 "이 순서대로 해 주세요" → Skill.
**내레이션:** 현장에서 에프디이는 고객의 말을 이 서랍으로 번역해요. 항상 해 달라는 건 메모로, 절대 안 된다는 건 훅으로, 시스템을 봐 달라는 건 엠씨피로 가요. 순서대로 해 달라는 절차는 스킬이죠. 계획서에도 이렇게 나눠 적으세요.

### 장면 10 · 요약과 예고 (약 25초)

## 정답과 해설
1. (b). `allowed-tools`는 사전 승인이지 제한이 아니고, 발동된 턴에만 적용돼요.
2. (c). 스크립트는 실행되고 출력만 컨텍스트에 들어와요.
3. (a). skill이나 CLAUDE.md의 지시는 부탁이에요. 반드시 지켜야 하면 hook으로 막아야 해요.
4. 예시 답: skill은 지시와 지식을 지금 대화의 컨텍스트에 불러오는 것이다. 서브에이전트는 별도의 컨텍스트에서 일하고 요약만 돌려주는 작업자다. 그래서 파일을 많이 읽는 조사처럼 대화를 어지럽힐 일은 서브에이전트에 맡기고, 절차나 참고 자료는 skill로 둔다. (둘을 합쳐 skill을 `context: fork`로 서브에이전트에서 돌릴 수도 있다.)
5. 예시 답: (1) 명명 규칙은 모든 세션이 알아야 하므로 CLAUDE.md에 적고, 꼭 지켜져야 하는 부분은 편집 뒤에 검사하는 hook을 붙인다. (2) 장애 보고서는 정해진 순서의 반복 절차이므로 skill로 만들고, 양식 예시는 딸린 파일로 둔다. (3) 티켓 시스템은 바깥 시스템이므로 MCP 서버로 연결한다. 그러면 skill 본문에서 "티켓은 이 도구로 가져온다"고 안내할 수 있다.
