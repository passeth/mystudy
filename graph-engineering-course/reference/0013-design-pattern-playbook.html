그래프 설계 한 장 플레이북

10개 레슨에서 배운 것을 실제 설계 리뷰에서 쓰는 한 장짜리 체크시트로 압축했다. 인쇄해서 옆에 두고 체크하면 된다.

쓰는 법: 새 그래프를 만들기 전엔 위쪽 결정 캐스케이드로 다섯 갈래(이슈 트리·루프·실행 그래프·지식 그래프·개선 거버넌스 그래프) 중 무엇이 필요한지, 혹은 그래프가 아예 필요 없는지 먼저 고른다. 그다음 12체크로 설계를 검증한다.

1. 결정 캐스케이드 - 어떤 그래프부터 쓸 것인가

2. 12체크 - 설계 리뷰 질문

다섯 갈래 중 어느 것을 골랐어도, 실행하기 전 아래 12개를 통과해야 한다. 체크 12는 "지금이라도 안 쓰는 게 낫지 않은가"를 마지막에 다시 묻는 관문이다.

#질문관련
☐ 1 노드는 존재 자격이 있는가
다른 모델, 다른 도구, 진짜 다른 역할(예: read-only reviewer)이 아니면 노드가 아니라 인라인 코드다.		 0001 · 0004
☐ 2 엣지에 실제 데이터가 흐르는가
"그리고 나서"는 edge가 아니다. 다음 노드가 이전 노드의 출력을 실제로 읽는지 확인한다.		 0004
☐ 3 state 스키마와 writer가 정해졌는가
각 필드를 누가 읽고 쓰는지 명시했는가. 정해지지 않으면 두 노드가 같은 필드를 덮어쓴다.		 0004 · 0007
☐ 4 라우팅이 결정론적인가
판단(분류)은 모델이 하되, 그 판단에 따른 분기 실행은 코드가 항상 같은 방식으로 처리하는가.		 0004 · 0005
☐ 5 barrier가 정말 필요한가
전체 집합이 있어야만 되는 작업(전체 dedupe 등)인가, 아니면 pipeline으로 항목별 처리가 가능한가.		 0005
☐ 6 순환의 수렴 조건이 있는가
무엇을 기준으로 "새로운 것 없음"을 판단하는가. 이번 라운드만이 아니라 지금까지 본 전체와 비교하는가.		 0005
☐ 7 judge가 산출물보다 먼저 정의됐는가
무엇이 완료인지 기계가 판정할 수 있는 조건을 코드나 테스트로 먼저 적어뒀는가.		 0006
☐ 8 리뷰어가 독립된 컨텍스트인가
작성자의 추론 과정을 보지 않고, 산출물과 규칙만 보고 채점하는 리뷰어가 최소 1명 있는가.		 0006
☐ 9 부작용이 멱등적인가
같은 단계가 재실행되거나 재시도돼도 두 번 청구되거나 두 번 발송되지 않는가.		 0004 · 0006
☐ 10 checkpoint 의미를 정확히 아는가
재개가 중단 지점에서 이어서 계속인지, 영향받은 노드가 처음부터 재실행되는지 런타임별로 확인했는가.		 0004
☐ 11 현실 anchor가 있는가
그래프 안의 지표만 서로 확인하고 있지 않은가. 실제 행 수·실제 테스트·실제 입금 같은 외부 근거가 연결돼 있는가.		 0002 · 0003
☐ 12 그래프 없이도 되는가
한 번뿐이거나, 아직 단계를 모르거나, 기계적 judge가 없거나, 냅킨에 못 그린다면 지금은 그래프를 쓰지 않는다.		 0001 · 0010

3. 패턴 카드 - 여덟 가지 기본 토폴로지

Chain 체인

단계마다 정확히 하나의 입력/출력. "그리고 나서"가 실제 edge인지 먼저 확인한다. 레슨 0004

Router 라우터

분류는 모델이, 분기 실행은 코드가 결정론적으로 담당한다. 레슨 0004 · 0005

Diamond 다이아몬드

fan-out - reduce(코드) - synthesize(단일 노드). 실행 그래프의 주력 토폴로지. 레슨 0005

Pipeline vs Barrier 파이프라인

전체 집합이 꼭 필요할 때만 barrier. 아니면 항목별로 흘려보내는 pipeline이 더 빠르다. 레슨 0005

Bounded cycle 제한된 순환

무엇을 기준으로 dedupe하는지 명시하고, K회 연속 무소득이면 종료한다. 레슨 0005

Verification loop 검증 루프

judge를 산출물보다 먼저 정의하고, 서로 못 보는 독립 리뷰어 2명을 둔다. 레슨 0006

One-writer 단일 쓰기자

읽기는 병렬로 안전하지만, 쓰기는 한 곳(또는 daemon)이 소유해야 충돌이 없다. 레슨 0007

Temporal graph 시간 그래프

사실을 지우지 않고 무효화한다. 관계에 valid_from/valid_to를 붙인다. 레슨 0008

5. 파급력(blast radius)에 따른 human gate 배치

낮음 파급력

예시: 내부 초안, 읽기 전용 조사, 자기 워크스페이스 안 파일

게이트: 게이트 없음 - 사후 검토로 충분

중간 파급력

예시: 외부에 보일 결과물의 준비, 결제 초안, 발송 전 메시지

게이트: 승인 대기 큐 - 사람이 확인 후 진행

높음 파급력

예시: 실제 발송·결제·삭제·프로덕션 배포·되돌리기 어려운 변경

게이트: 명시적 사람 승인 + 결정 로그 필수, 승인 전 실행 금지

실무 번역: 사람이 병목이 되는 지점은 항상 "높음" 항목 앞이어야 한다. "낮음"에까지 사람 승인을 요구하면 게이트 자체가 무시되기 시작한다 - 그것이 pairing/audit 실패의 시작이다(레슨 0003).
