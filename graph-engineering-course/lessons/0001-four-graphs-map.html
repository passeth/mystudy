Lesson 0001 · Graph Engineering v2

한 단어, 네 개의 그래프

X 타임라인에서 "그래프 엔지니어링"이라고 부르는 것은 최소 네 가지 다른 구조다. 이름이 같다고 같은 것이라 생각하면 처방이 어긋난다.

오늘의 한 줄 답: 그래프가 헷갈릴 땐 "이 그래프의 노드가 무엇을 하는가?"만 물으면 된다. 노드가 측정하고 조정하는 루프면 개선 그래프, 한 번 실행되고 끝나는 작업이면 실행 그래프, 사실/엔티티면 지식 그래프, 질문/가설이고 실행되지 않으면 문제 트리다.

1. 왜 이렇게 헷갈리는가

2026년 7월 한 주 동안 X에는 "그래프 엔지니어링"을 표방하는 글이 최소 9건 쏟아졌다. Carlos Perez는 개선 루프를 감시하는 네트워크 이야기를 했고, Codez와 Akshay는 LangGraph류 실행 오케스트레이션을 설명했고, Sprytix와 rody는 지식/시간 그래프(GraphRAG, Graphiti)를 다뤘고, McKinsey 이슈 트리 글은 문제 분해를 그래프처럼 그렸다. 넷 다 "그래프"라고 부르지만 실제로 겹치는 부분은 "노드와 엣지로 그린다"는 시각적 습관뿐이다.

beamnxw의 표현을 빌리면 계층은 환경 → 피드백 → 흐름(harness → loop → graph)으로 쌓인다. 하지만 "루프들의 네트워크"(Perez)와 "작업 단계의 오케스트레이션"(Codez/Akshay)은 같은 흐름 계층 안에서도 전혀 다른 대상을 가리킨다 — beamnxw 자신도 두 표현을 구분해서 쓴다.

2. 판별 질문 하나로 구분하기

노드가 측정·조정 루프인가?

Goodhart, 위쪽 맹목, 충돌, 측정 부패를 걱정한다면 → B. 개선 그래프

노드가 한 번 실행되고 끝나는 작업인가?

fake edge, 상태 스키마, 라우팅, 체크포인트를 걱정한다면 → C. 실행 그래프

노드가 사실/엔티티인가?

엔티티 해상도, 시간 유효성, multi-hop 질의를 걱정한다면 → D. 지식 그래프

실행되지 않고 사람이 읽기만 하는가?

재시도·체크포인트가 없다면 → A. 문제 트리

3. 그래도 겹치는 지점

세 층은 실제로 중첩된다. 실행 그래프(C) 안에 개선 그래프(B)가 노드로 내장될 수 있다 — 예를 들어 "같은 실패가 3회 반복되면 사람에게 에스컬레이션"하는 리뷰어 루프. 실행 그래프(C)는 지식 그래프(D)를 도구로 조회할 수도 있다. 문제는 이 중첩 자체가 아니라, 각 층의 실패 모드와 처방을 섞어 쓰는 것이다. 개선 그래프에 필요한 "anchor(현실 확인)"를 실행 그래프의 "체크포인트"와 같은 것으로 착각하면 둘 다 제대로 작동하지 않는다.

실무 번역: Aside의 cron 루틴(erp-sales-hx-daily)은 실행 그래프(“fetch → parse → insert”)이면서, 그 위에 “0행이면 실패로 본다”는 개선 그래프 규칙(anchor)이 얹혀야 한다. mystudy 레슨 제작 파이프라인은 실행 그래프(연구→종합→저술→배포)이고, 그 안의 memory_search는 지식 그래프에 가깝다. Trade Intel의 "거래처명 정규화"는 지식 그래프의 엔티티 해상도 문제이지, 실행 그래프의 라우팅 문제가 아니다 — 이걸 구분해야 올바른 레슨(0004 vs 0008)으로 갈 수 있다.

4. 미니 실습 (7분)

아래 8개를 A(문제 트리)/B(개선 그래프)/C(실행 그래프)/D(지식 그래프) 중 하나로 분류해 보자. 정답은 하나 이상일 수 있다 — 그 경우 "가장 지배적인 실패 모드가 무엇인가"로 고른다.

  2. Microsoft GraphRAG의 community report 생성
  3. LangGraph의 research → write → review 그래프
  4. "활성화율이 왜 낮은가"를 원인별로 쪼갠 Why-tree
  5. Trade Intel의 거래처·담당자·계약 상태 시간 이력

  7. ERP 일배치가 "성공"이라고 보고했지만 실제로는 0행이 들어간 사건
  8. 서로를 볼 수 없는 두 리뷰어가 같은 산출물을 채점하는 구조
