Lesson 0006 · Graph Engineering v2

심판을 먼저 만들어라

에이전트는 종료 조건이 없으면 절대 끝나지 않는다. "다 된 것 같다"는 느낌이지 조건이 아니다. 그래프를 짜기 전에, 무엇이 통과인지 기계가 답할 수 있는 심판부터 만든다.

오늘의 한 줄 답: 실행 그래프에서 진짜 어려운 일은 워커를 늘리는 게 아니라 Judge(심판)를 코드보다 먼저 만들고, 일부러 부숴서 검증하고, 룰북에 규칙을 누적시키고, 서로 못 보는 독립 리뷰어 두 명을 두는 것이다. 같은 모델이 자기 숙제를 자기가 채점하게 하지 않는 것이 전체 그래프의 신뢰도를 결정한다.

그림 1. Judge → Worker → 실패 시 Rulebook 갱신 → 독립 Reviewer 두 명 → 비용별 체크 배치 → 단일 daemon 소유. Yarchi(@undefinedKi)의 8단계 레시피를 시각화.

1. 왜 심판을 코드보다 먼저 만드는가

Yarchi(@undefinedKi)의 글은 이 순서를 강조한다: 작업 내용에 대한 지시를 쓰기 전에, 무엇이 통과인지 기계가 답할 수 있는 스크립트(judge.sh)부터 만든다. 파일 하나를 받아 exit code 0(통과)/1(실패)과 이유를 출력하는 스크립트다. 코드라면 테스트 실행기를 감싸고, 문서라면 필수 섹션과 금지 패턴을 확인하고, 데이터라면 스키마와 행 수를 검증한다. 너무 애매해서 스크립트로 판단할 수 없는 경우에만 모델에게 원문과 함께 예/아니오 질문을 던지고 답을 파싱한다.

판별 질문: "이게 통과했다는 걸 어떤 명령 하나로 확인할 수 있는가?" 이 질문에 답할 수 없다면 아직 심판이 없는 것이다.

2. 심판을 일부러 부숴라

절대 실패하지 않는 심판은 장식품이다. Yarchi의 2단계: 정상 산출물을 복사해 일부러 훼손한 뒤(예: 필수 섹션 제거), 심판이 그 훼손본을 반드시 FAIL로 판정하는지 확인한다. 훼손본이 통과한다면 심판이 눈멀어 있는 것이고, 그 이후의 모든 PASS 결과는 의미가 없다.

3. 룰북은 절대 우회하지 않는다

rules/rulebook.md는 애매한 부분을 모델과 대화로 풀며 문장으로 축적한 규칙집이다. 두 가지 속성이 핵심이다: (1) 계속 자란다 — 리뷰어가 잡아낸, 룰북에 없던 모든 문제는 새 문장이 된다. (2) 아무것도 우회하지 않는다 — 산출물을 손으로 고치는 순간 진실의 원천이 둘이 되고, 하나는 사람 머릿속에만 있게 된다.

3개 항목으로 스트레스 테스트한 뒤(룰북 있는 버전 vs 없는 버전을 diff해 차이를 룰북에 반영) 그 3개 산출물은 반드시 삭제한다 — 목표는 3개 파일이 아니라 규칙이었기 때문이다. 이 단계를 건너뛰면 처음 3개만 다른 관습을 따르는 사고가 반복된다.

4. 서로 못 보는 리뷰어 두 명

워커와 같은 컨텍스트에 있는 리뷰어 하나는 워커의 추론을 이미 봤기 때문에 동의하게 된다. Yarchi와 Akshay(@akshay_pachaar) 모두 같은 결론에 도달한다 — 리뷰어는 다른 모델로, 신선한 컨텍스트에서(전체 대화가 아니라 룰북과 산출물만), 그래프가 조작할 수 없는 근거(실제로 실행된 테스트, 실제로 컴파일된 코드)에 판정을 고정해야 한다. 모든 발견에 룰 조항 인용을 강제하는 디테일이 막연한 "별로다"를 재현 가능한 개선으로 바꾼다.

5. Bun 사례로 본 "테스트 100% 통과"의 한계

이 원칙들이 실제로 쓰인 검증된 사례가 Bun의 Zig→Rust 마이그레이션이다(Anthropic·Bun 공식 사례). 정확한 범위는 다음과 같다:

항목검증된 수치
이식 대상1,448개 Zig 파일, 병합된 diff +1,009,272줄
기간11일(5월 3일~14일), 6,778 커밋, 최대 동시 약 64개 Claude, 약 50개 dynamic workflow
비용비캐시 입력 59억 토큰, 출력 6.9억 토큰, 캐시 입력 720억 토큰 — 공개 API 가격 환산 시 약 $165,000 (실제 청구 현금이 아니라 API 가격 환산치)
리뷰 구조구현자 1명 + 적대적 리뷰어 2명 이상, 서로 다른 context에서 diff만 보고 결함 탐색
테스트 결과merge 전 기존 CI 스위트 100% 통과 — 그러나 merge 이후 19건의 회귀가 추가로 발견돼 수정됨

마지막 행이 이 레슨의 핵심 교훈이다: 테스트 100% 통과는 무결함을 보장하지 않는다. 심판은 강력한 도구이지 완전성의 증명이 아니다. 별개로, Anthropic 내부의 Python→TypeScript 이식(165,000줄, 주말, 수백 개 에이전트, 8개 게이트, 3라운드 적대적 리뷰)은 Bun과 완전히 다른 별개 사례다 — 두 사례를 하나로 섞어 인용하면 안 된다.

실무 번역: mystudy 레슨 하나를 배포하기 전에도 같은 원칙이 적용된다. "레슨이 잘 만들어진 것 같다"는 정지 조건이 아니다. HTML이 파싱되는가, SVG가 실제로 들어있는가, 퀴즈가 3개인가, 출처 링크가 죽지 않았는가를 스크립트로 확인할 수 있어야 진짜 심판이다.
