## 1. 공통 핵심 개념 (출처 명시)

### 1-1. "루프는 1노드 그래프다" — 그래프가 루프를 대체하지 않고 감싼다

- **Akshay**: "A single agent loop is just a one-node graph with an edge pointing back to itself. Graphs don't replace loops. They connect and govern them." 그가 제시하는 최소 예시 그래프는 `research → write → review`이고, review에서 실패하면 `write`로 되돌아가는 조건부 엣지 하나가 곧 루프다.
- **Yarchi**: 같은 통찰을 실무 언어로 표현한다 — "Most agents are loops... A graph moves control outside the model." 루프에서는 통제가 모델 내부에 있고(안이 안 보임), 그래프에서는 통제가 모델 밖, 즉 사람이 그린 노드 구조로 옮겨간다.
- **beamnxw**: 3계층 스택으로 정리 — harness(모델을 둘러싼 기계 장치) → loop(반복 작업-피드백 사이클) → graph(작업 흐름의 위상을 명시적으로 만드는 것: 노드, 분기, 합류, 상태 전이, 통제된 순환). "환경 → 피드백 → 흐름"이라는 한 줄 요약을 제공한다.

### 1-2. 노드 / 엣지 / 상태 (Node / Edge / State)

- **Akshay**의 정의가 가장 간결하다: 노드는 작업 단위(에이전트, 순수 모델 호출, 결정론적 함수, 도구, 혹은 사람의 승인 행위 중 무엇이든 될 수 있다), 엣지는 다음에 무엇이 실행될지 결정하는 것(순차/병렬/조건부), 상태는 엣지를 따라 흐르는 공유 객체(모든 노드가 읽고 쓴다).
- **Codez**는 더 엄격한 기준을 준다: "엣지는 데이터가 실제로 이동할 때만 존재한다." "요약해줘, 그리고 날씨 알려줘"는 엣지가 없는 두 개의 독립된 노드다(날씨가 요약을 소비하지 않으므로). 모든 "그리고"에 대해 "다음 단계가 이전 단계의 출력을 실제로 읽는가?"를 물어야 한다는 실천 규칙을 제시한다.
- **beamnxw**는 그래프 설계자가 실제로 결정하는 6가지 항목을 나열한다: 노드 경계(결정론적 함수/LLM 호출/전문 에이전트/사람 검토 중 어디 속하는가), 상태 스키마(각 노드가 무엇을 읽고 쓸 수 있는가, 병렬 갱신을 어떻게 병합하는가), 라우팅 조건, 동시성, 순환과 종료 조건, durability(체크포인트 위치와 재개 방식).

### 1-3. 하네스 vs 루프 vs 그래프의 구분 (beamnxw가 가장 명시적)

- **하네스**: 시스템 프롬프트, 도구 정의, 메모리, 파일시스템, 샌드박스, 모델 라우팅, 핸드오프, 미들웨어 훅, 압축(compaction), 권한, 로깅, 검증 인터페이스 — "모델을 지웠을 때 아키텍처 다이어그램에 남는 모든 것"이 하네스다. LangChain은 "agent = model + harness"로 정의한다고 인용됨.
- **루프**: 트리거, 목표, 상태/메모리, 행동 정책, 근거(evidence), 피드백, 정지 규칙(stopping rule) 7요소로 분해. "확신이 아니라 근거로 루프를 돈다(Loop on evidence, not confidence)"는 문장이 핵심 — "에이전트가 됐다고 말한다"는 정지 조건이 아니고, "테스트가 통과하고, 링크가 살아있고, 스키마가 검증되고, 리뷰어가 승인했다"가 정지 조건이다.
- **그래프**: "무엇을 할지"가 아니라 "다음에 무엇이 실행되도록 허락되는지"를 다루는 계층. beamnxw는 증상→처방 표까지 제공한다: "데이터/도구 접근 불가"→하네스 문제(도구 계약/권한/샌드박스/컨텍스트 주입), "세션 간 진행 상황을 잊음"→하네스 문제(durable state/checkpoint), "첫 시도가 거의 맞지만 신뢰 불가"→루프 문제(외부 채점기/결정론적 테스트/근거 있는 재시도), "여러 전문가가 정해진 순서로 실행돼야 함"→그래프 문제(명시적 노드/엣지/라우팅/합류), "실패 지점을 찾기 어려움"→그래프+하네스 문제(그래프 노드에 정렬된 상태 추적), "워크플로가 너무 자주 바뀜"→오히려 더 단순한 하네스로(통제를 모델에 맡기고 그래프 공식화를 미룸).
- **Akshay**도 5단계 스택을 제시: prompt engineering(보내는 말) → context engineering(모델이 보는 모든 것) → harness engineering(도구 실행/상태 추적/에러 처리 코드) → loop engineering(한 에이전트를 목표로 이끄는 자율 사이클) → graph engineering(여러 루프에 걸친 조정 계층: 무엇이 언제, 어떤 순서로 실행되고 누가 누구를 검사하는가). "각 계층은 이전 계층을 감싼다. 하위 계층을 건너뛰면 그래프는 더 복잡하게 실패할 뿐이다."

### 1-4. 계약(Contract)과 타입 상태 (Typed State)

- **Codez**: 모든 노드는 "계약"을 가져야 한다 — 입력은 명시적으로 전달(공유 창에서 추측하지 않음), 출력은 정의된 형태(가능하면 검증됨)여야 다음 노드가 추측 없이 소비할 수 있다. 실무에서는 JSON 스키마로 강제하고(`agent()` 호출에 스키마를 붙이면 서브에이전트가 검증된 구조화 데이터를 반환하도록 강제된다는 주장, **검증 필요** — 이는 특정 미공개/가상 CLI 기능에 대한 설명임), 스키마 불일치 시 재시도한다고 설명.
- **Akshay**: 상태를 공유 객체로 취급할 때 생기는 문제 — "루프에서는 실패 모드가 컨텍스트 부패(context rot)이고, 그래프에서는 같은 병이 공유 상태로 옮겨간다." 해법은 지루하지만 효과적: 상태에 타입 스키마 부여, 어느 노드가 어느 필드에 쓸 수 있는지 명시적으로 결정, 체크포인트로 재생(replay) 가능하게 만들기. 단, 체크포인트 이후 노드는 재실행되므로 이메일 발송처럼 부작용 있는 노드는 반드시 재실행 안전(idempotent)해야 한다는 주의사항을 명시.

### 1-5. 결정론적 라우팅 (Deterministic Routing)

- **Akshay**: "라우팅을 신뢰할 수 있게 만들기"가 4대 난제 중 하나. 모델이 경로를 결정하면 유연하지만 불안정하다(같은 상태가 실행마다 다른 경로를 탈 수 있어 디버깅이 괴로움). Google의 ADK 2.0 설계 규칙을 가장 깔끔한 입장으로 인용: "예측 가능한 라우팅은 결정론적 코드가 통제하고, 모델은 실제 판단이 필요한 단계만 처리해야 한다." 체크 가능한 조건은 코드로 라우팅하고, 해석이 진짜 필요한 곳에만 모델 호출을 쓰라는 원칙.
- **Codez**: 같은 원칙을 코드 패턴으로: 라우터 노드가 diff 크기를 분류(모델 판단)하되, 분류 결과에 따른 분기 자체는 `if/switch`(코드가 라우팅) — "You get Claude's judgment at the node and the script's reliability at the edge."

### 1-6. 체크포인트 / 내구성 실행 (Durable Execution)

- **Yarchi**: "상태를 컨텍스트 창이 아니라 디스크에 둔다"가 핵심 전환점. 큐를 매번 파일시스템에서 재구축(`queue.sh`가 `source/*.md` 중 `output/`에 없는 것만 나열)하고, 60%에서 죽여도 디스크가 기억하고 있어 60%부터 재개 가능하다고 설명.
- **Akshay**: LangGraph를 "장기 실행되는 상태 기반 에이전트를 위한 저수준 오케스트레이션 인프라, durable execution과 human-in-the-loop 통제에 명시적으로 초점"이라고 인용(원문은 beamnxw 쪽에 더 자세).
- **beamnxw**: durability를 그래프 설계자의 6대 결정 항목 중 하나로 명시 — "체크포인트는 어디서 발생하고, 중단 후 실행은 어떻게 재개되는가."

### 1-7. 팬아웃/팬인, 다이아몬드, 파이프라인 vs 배리어

- **Codez**가 가장 상세하다. 팬아웃(`parallel()`): N개의 독립 노드를 동시에 실행. 팬아웃은 "배리어(barrier)"다 — 모든 스레드가 끝날 때까지 기다린 뒤 다음 단계로 넘어간다. 실패한 스레드는 예외를 던지는 대신 null로 처리되어 `.filter(Boolean)`으로 걸러야 전체 배치가 죽지 않는다(**검증 필요**: 이는 특정 미공개 CLI의 API 설명).
- **다이아몬드(diamond)**: 팬아웃+팬인을 합친 것 — 하나가 쪼개고, 여럿이 병렬로 일하고, 하나가 합친다. "fan out → reduce → synthesize"라는 정형화된 이름. 시장 조사, 의존성 감사, 코드 리뷰, 리서치 리포트가 모두 같은 골격을 재사용한다고 설명.
- **파이프라인 vs 배리어**: `parallel()`은 가장 느린 노드까지 전체가 기다리는 배리어. `pipeline()`은 각 아이템이 모든 단계를 독립적으로 스트리밍(아이템 A가 3단계에 있는 동안 아이템 B는 아직 1단계일 수 있음). "기본값은 pipeline(), 전체 결과가 정말 필요한 단계에서만 배리어를 쓰라"는 원칙 — 토폴로지가 비용·지연의 최대 지렛대라는 주장.
- **Akshay/beamnxw**에는 이 정도 세밀한 API 수준 구분은 없고, "병렬 팬아웃과 조인이 필요하면 그래프를 쓰라"는 상위 원칙만 등장.

### 1-8. 순환과 종료 조건 (Cycles / Exit Conditions)

- **Codez**: "loop-until-dry" 패턴 — 연속 K라운드 동안 새로운 발견이 없을 때까지 계속 스폰. 핵심 함정: "확인된 결과뿐 아니라 지금까지 본 모든 것과 비교해 중복 제거해야 한다." 그렇지 않으면 기각된 발견이 매 라운드 재등장해 루프가 절대 마르지 않는다.
- **Yarchi**: "에이전트는 종료 조건이 없으면 절대 끝나지 않는다. 느낌이 들 때 멈추는데, 그건 조건이 아니라 기분이다." → 저장 검증기(judge)를 코드보다 먼저 만들라는 처방으로 이어짐.
- **beamnxw**: 루프의 "정지 규칙(stopping rule)"을 anatomy의 7요소 중 하나로 명시(성공/예산 한도/타임아웃/복구불가 오류/사람 에스컬레이션).

### 1-9. 리뷰어/검증기 (Reviewer / Verifier) — "자기 숙제를 자기가 채점하지 말라"

- **Akshay**: 루프 엔지니어링의 가장 날카로운 규칙을 인용 — "절대 에이전트가 자기 숙제를 채점하게 하지 말라." 그래프는 이 위험을 키운다: 같은 기반 모델로 만든 20개 에이전트가 같은 결함 있는 컨텍스트를 읽으면 서로 기꺼이 동의해버리고("organized nonsense"), 모델은 측정 가능하게 자기 자신의 출력을 선호한다. 해법: 리뷰어 노드는 다른 모델로, 신선한 컨텍스트로(전체 대화가 아니라), 그래프가 조작할 수 없는 근거(실제로 실행된 테스트, 실제로 컴파일된 코드)에 판정을 고정.
- **Yarchi**: "서로를 볼 수 없는 두 명의 리뷰어" — 워커와 같은 컨텍스트의 리뷰어 하나는 워커의 추론에 이미 물들어 동의하게 된다. 각 리뷰어는 룰북과 산출물만 보고, 워커의 추론이나 채팅 기록은 보지 못하게 한다. "모든 발견에 룰 인용을 강제하는 디테일이 루프를 닫는다" — 막연한 불만을 큐 아이템으로 바꾸는 장치.
- **Codez**: 세 가지 검증 패턴 — 적대적 검증(N명의 독립 회의론자가 각 발견을 반박 시도, 과반수 생존해야 통과), 관점-다양 검증(정확성/보안/재현성처럼 서로 다른 렌즈), 판정단(N개 시도를 다른 각도에서 생성 후 병렬 심사위원이 채점).
- **Akshay**는 Cognition(Devin 개발사)의 1년 운영 결론도 인용: "여러 에이전트가 읽고 의견을 낼 수 있지만, 오직 하나만 변경할 수 있다." 읽기는 병렬이 안전하고(나쁜 의견은 누군가 행동하기 전까진 비용이 없음), 쓰기는 한 곳에서만 일어나야 피해를 볼 수 있다는 논리.

### 1-10. 단일 작성자 / 격리 (One-Writer / Isolation)

- **Codez**: "체인에서는 실패가 연쇄한다 — C가 죽으면 D는 절대 실행 안 되고 전체가 멈춘다. 그래프에서는 실패가 자기 노드에 갇혀야 한다." `parallel()` 안에서 던진 예외는 null로 resolve되어 나머지가 살아남는다는 부분적 격리는 이미 있지만, 더 미묘한 실패는 "에이전트들이 파일을 병렬로 쓸 때 서로 충돌하는 것"이다. 해법은 워크트리 격리(각 에이전트가 자신의 git worktree에서 샌드박스 작업 후 merge) — "실제로 병렬 쓰기가 일어날 때만 쓰는 안전벨트."
- **Yarchi**의 "직렬화된 고비용 연산" 개념도 이와 관련: 한 연산(빌드/재컴파일 등)이 비용/시간을 지배하면, 모든 에이전트가 그것을 직접 트리거하게 두지 말고 요청을 큐에 쓰게 한 뒤 단일 데몬이 배치로 소화한다("Ten agents each triggering a full rebuild means paying ten times for work that batches into one").

## 2. 출처별 고유 프레임워크/사례

### Yarchi — "심판(judge) 먼저, 8단계 폴더 레시피"

이 글은 유일하게 "지금 바로 따라 할 수 있는 셸 스크립트 레시피" 형태다. 실제 폴더 구조(`agent/{source,output,rules,scripts,logs}`)와 8단계를 제시한다:

1. **심판 스크립트 먼저 작성** (`judge.sh`) — 파일 하나를 받아 통과/실패와 이유를 출력. 사람이 읽는 게 아니라 기계가 판정.
2. **심판을 일부러 부순다** — 정상본을 훼손한 사본이 통과하면 심판이 눈먼 것.
3. **룰북 작성, 절대 우회 금지** (`rules/rulebook.md`) — 모호함을 Claude와 대화로 풀며 문장으로 축적. "손으로 산출물을 고치는 순간 진실의 원천이 둘이 되고 하나는 당신 머릿속에만 있다."
4. **3개 항목으로 룰 스트레스 테스트 후 산출물 삭제** — 룰북 있는 버전 vs 없는 버전을 diff해 차이를 룰에 반영, 그리고 산출물은 버림(첫 3개가 다른 관습을 따르는 사고 방지).
5. **상태를 디스크에** — 큐를 매 실행마다 파일시스템에서 재구축.
6. **서로를 못 보는 두 리뷰어**.
7. **결정론적 체크는 비용에 따라 배치** — 빠른 체크는 루프 안에, 느린 체크(컴파일러 등)는 배치로 밖에서 한 번.
8. **비싼 연산 직렬화** — 단일 데몬이 소유.

**핵심 사례 (검증 필요 — 저자 서술, Anthropic 공식 발표 아님)**: "Anthropic 엔지니어들이 지난달 이 방식으로 10개 코드 패키지를 마이그레이션." Jarred Sumner가 Bun을 Zig→Rust로 200만 줄, 2주 내에 이식(전체 기존 테스트 스위트가 머지 전에 CI 통과, 이후 19건의 회귀 모두 수정). Mike Krieger가 Python 코드베이스를 165,000줄 TypeScript로 주말 동안 이식(수백 개 에이전트, 8개 단계 게이트, 3라운드 적대적 리뷰, Python 원본과 모든 명령어 출력을 diff하는 최종 체크). Bun 마이그레이션 비용: 59억 개 비캐시 입력 토큰 + 6.9억 출력 토큰, API 정가 기준 약 $165,000. "$300만 4년 프로젝트를 2주짜리로 만드는 기술"이라는 문구.

### Akshay — "4대 난제(hard parts)" 프레임과 촉발 사건 서사

이 글의 가치는 **역사적 맥락**이다: 2026년 7월 18일 Peter Steinberger(OpenClaw 개발자)가 "우리 아직도 루프 얘기하는 거야, 아니면 이미 그래프로 넘어간 거야?"라는 9단어 트윗을 올렸고, 몇 시간 뒤 Hamel Husain이 "Loop Engineering Is Dead. Enter Graph Engineering."이라는 글을 발행했다는 것 — 이것이 "graph engineering" 밈의 발화점으로 서술된다. Akshay는 이걸 "반은 농담이었지만 뭔가 진짜에 닿았다"고 프레이밍하며, "이건 새 기술이 아니다. LangGraph가 2024년 1월에 이미 이 정확한 모델(공유 상태 위의 노드와 엣지)을 출시했고, Microsoft AutoGen은 GraphFlow가 있고, Google은 ADK 2.0의 전체 워크플로 런타임을 같은 아이디어로 만들었다. 이름은 새롭고 관행은 새롭지 않다"고 명시적으로 인정한다. Hamel 포스트의 상위 댓글 하나가 "welcome back, langchain"이었다는 인용도 이 회의적 태도를 보강.

**4대 난제**:
1. 노드가 존재할 자격이 있는가 (냅킨 테스트: 그래프를 냅킨에 못 그리면 너무 복잡한 것)
2. 공유 상태를 깨끗하게 유지하기 (타입 스키마 + 쓰기 권한 명시 + 체크포인트)
3. 신뢰할 수 있는 라우팅 (결정론적 코드 vs 모델 판단의 역할 분담)
4. 에이전트들이 서로 동의해버리는 문제 (리뷰어 노드 분리)

**비용 주장 (검증 필요)**: "단일 에이전트는 채팅 인터랙션의 약 4배 토큰을 태우고, 멀티에이전트 시스템은 약 15배를 태운다." "Anthropic의 멀티에이전트 리서치 시스템이 내부 리서치 평가에서 단일 Opus 에이전트를 90.2% 능가했다." 두 수치 모두 출처가 명시된 링크(Anthropic 게시물로 추정)를 인용하지만 원문 캡처에는 URL 텍스트가 보이지 않아 1차 확인이 필요하다.

### beamnxw — 가장 체계적인 "3계층 분류 + 증상-처방 표"

이 글은 4건 중 가장 참고문헌이 충실하다(9개 실제 링크: LangChain 하네스 아키텍처 글, OpenAI Agents SDK 문서, LangChain/LangGraph 1.0 발표, AutoGen GraphFlow 문서, LangChain "Art of Loop Engineering", AutoGen Studio 소개, Custom Agent Harness 가이드, "A practical guide to building agents", Anthropic "Building Effective AI Agents"). 다른 3건과 달리 도구 홍보나 서브스택 유도가 없다.

고유 기여는 "**증상 → 시작점 → 처방**" 진단표다:

| 증상 | 시작점 | 처방 |
|---|---|---|
| 에이전트가 올바른 데이터/도구에 안전하게 접근 못함 | 하네스 | 도구 계약, 권한, 샌드박스, 컨텍스트 주입 |
| 세션 간 진행 상황을 잊음 | 하네스 | durable state, 체크포인트, 진행 아티팩트, 압축 |
| 첫 시도가 대체로 근접하지만 신뢰 불가 | 루프 | 외부 채점기, 결정론적 테스트, 근거 기반 재시도 |
| 성공 후에도 계속 일하거나 증명 전에 멈춤 | 루프 | 근거 기반 종료 상태, 예산 인지 정지 규칙 |
| 여러 전문가가 통제된 순서로 실행돼야 함 | 그래프 | 명시적 노드/엣지/라우팅 조건/합류 |
| 다단계 프로세스에서 실패 지점 찾기 어려움 | 그래프+하네스 | 그래프 노드에 정렬된 상태 추적 |
| 워크플로가 너무 자주 바뀜 | (역설적으로) 더 단순한 하네스 | 통제를 모델 주도로 유지, 그래프 공식화를 지연 |

또한 "흔한 값비싼 실수" 5가지를 명시: (1) 일을 이해하기 전에 그래프부터 만드는 것, (2) 같은 모델이 안전장치 없이 쓰고 채점하는 것, (3) "계속 시도해봐"를 루프 명세로 쓰는 것(무한 재시도는 비용 누수), (4) 하네스를 쓰레기통 취급(도구/메모리가 많다고 좋은 게 아님), (5) 오케스트레이션 실패를 모델 탓으로 돌리는 것.

### Codez — "14단계 실전 API 커리큘럼" (가장 코드 밀도 높음, 가장 검증 필요도 높음)

유일하게 특정 CLI 프로덕트("Claude Code dynamic workflows", `agent()`, `parallel()`, `pipeline()`, `/deep-research`, `/workflows`, `ultracode`)를 전제로 구체적 코드를 제시한다. 14단계: (1) 노드=작업, 엣지=흐르는 것 (2) 선형 스크립트는 퇴화한 그래프 (3) 노드에 계약 부여 (4) 엣지를 데이터 계약으로 취급 (5) `parallel()`로 팬아웃 (6) 배리어에서 팬인 (7) 다이아몬드 패턴 (8) 런타임 조건부 라우팅 (9) 엣지에 검증기 배치 (10) 노드 격리(워크트리) (11) 수렴하는 순환 추가 (12) 노드별 모델 티어링 (13) 토폴로지가 곧 비용/지연 (14) Claude가 스스로 그래프를 그리게 하기(self-routing / dynamic workflows).

이 글의 "이번 주에 만들어볼 6가지 그래프" 목록은 학습자에게 실습 아이디어로 유용하다: 라우트 전수 보안 스윕, `/deep-research` 인용 리포트, 파일 단위 모듈 이식, diff 적대적 리뷰, 스케줄 기반 생태계 스캔, 미지 규모 발견(버그 스윕).

## 3. 시각/UI 선호 학습자를 위한 비-코드 비유

학습자는 코드 diff보다 시각·UI 비교를 선호한다는 특성을 고려해, 4개 원문의 개념을 코드 없이 재구성한다.

### 3-1. "지하철 노선도"로서의 그래프
- **역(node)** = 한 가지 일만 하는 작업 단위. 환승역이 여러 노선을 겸하듯, 노드도 "검증기"처럼 겸직할 수 있지만 원문들의 조언은 "한 역, 한 역할"이다.
- **선로(edge)** = 실제로 승객(데이터)이 이동하는 경로만 그린다. 지도에 그려놨지만 아무도 안 타는 선로는 Codez가 말하는 "가짜 엣지"("그리고"로만 연결된, 데이터가 안 흐르는 관계)다.
- **환승 정보판(state)** = 모든 역이 같이 보는 전광판. beamnxw의 "누가 어느 필드에 쓸 수 있는가"는 "이 전광판의 이 줄은 어느 역만 고칠 수 있다"는 규칙과 같다.
- **단선 vs 복선(파이프라인 vs 배리어)**: 단선 구간(배리어)에서는 열차 한 대가 지나갈 때까지 다음 열차가 못 들어온다. 복선(파이프라인)에서는 여러 열차가 동시에 다른 위치를 지난다. Codez의 "기본값은 pipeline"은 "가능하면 복선을 깔라"와 같다.

### 3-2. "레스토랑 주방"으로서의 하네스·루프·그래프 구분 (beamnxw 스택 재구성)
- **하네스** = 주방 설비(가스레인지, 냉장고, 도마, 위생 규정, 재고 시스템). 요리사가 아무리 실력 있어도 설비가 없으면 요리를 못 만든다.
- **루프** = 한 요리사의 반복 작업 사이클: 맛보고 → 간 맞추고 → 다시 맛본다. "맛있는 것 같다"가 아니라 "레시피 기준 염도 측정값이 기준 범위 안"이라는 **근거**로 멈춘다.
- **그래프** = 주방 전체의 동선표: 누가 먼저 손질하고, 누가 그 다음 굽고, 플레이팅 담당은 두 라인이 다 끝나야 시작할 수 있다(팬인=합류 지점). 하나의 화구(비싼 공용 자원)를 여러 요리사가 각자 쓰려 들면 부딪히므로, 화구 담당 한 명(직렬화 데몬)이 순서를 관리한다.

### 3-3. "이중 맹검 심사"로서의 리뷰어 격리
- 학회 논문 심사에 비유하면 가장 직관적이다. 저자(워커)가 자기 논문을 자기가 통과시키면 안 되고(자기 채점 금지), 심사위원 두 명이 서로의 심사평을 보지 못한 채(맹검) 독립적으로 판정하고, 반드시 "몇 조 몇 항 위반"처럼 규정을 인용해 반려해야(막연한 "별로다"가 아니라 룰북 인용) 재현 가능한 개선이 된다.

### 3-4. "건축 도면과 시공"으로서의 durable state / 체크포인트
- 도면(그래프)이 있고, 시공 단계마다 사진을 찍어 기록(체크포인트)해두면, 3층에서 화재가 나도 1~2층 공사 기록은 남아있어 3층부터 재시공하면 된다. 도면이 없는 즉흥 시공(순수 루프)은 무너지면 어디부터 잘못됐는지 알 수 없다.

## 4. 과장/미래지향/기술적으로 의심스러운 주장과 필요한 1차 근거

이 절은 "가르칠 때 사실처럼 제시하면 안 되는 것"을 명시하기 위한 것이다.

## 5. 제안하는 5개 레슨 다이어그램 + 실습

### 다이어그램 1 — "루프는 그래프의 특수 사례" (Akshay 기반)
- 좌측: 한 노드가 자기 자신을 가리키는 화살표 하나(순수 루프).
- 우측: `research → write → review` 3노드, review에서 실패 시 write로 돌아가는 조건부 엣지, 성공 시 종료.
- 캡션: "그래프는 루프를 없애지 않는다. 루프를 이름 붙은 상자 안에 가둘 뿐이다."
- **실습**: 학습자 자신이 지금 쓰는 Aside 서브에이전트 워크플로 하나를 골라, 노드/엣지 다이어그램으로 손으로 그려보기(냅킨 테스트: Akshay가 언급한 "그래프를 냅킨에 못 그리면 너무 복잡한 것").

### 다이어그램 2 — "하네스 · 루프 · 그래프 3층 주방" (beamnxw 기반)
- 3단 다이어그램: 맨 아래 "주방 설비"(하네스: 도구/메모리/샌드박스/권한), 중간 "한 요리사의 맛보기 사이클"(루프: 트리거→행동→근거→피드백→정지), 맨 위 "주방 전체 동선표"(그래프: 노드/엣지/라우팅/합류).
- **실습**: 최근 실패한 자동화 하나를 골라 beamnxw의 진단표를 그대로 적용 — "증상이 무엇이었나 → 하네스/루프/그래프 중 어디서 시작해야 했나 → 실제 처방은 무엇이었나"를 3줄로 적어보기.

### 다이어그램 3 — "다이아몬드: 팬아웃 → 리듀스 → 신테사이즈" (Codez 기반)
- 마름모 모양: 위 꼭짓점(split 노드) → 중간 여러 병렬 노드(work) → 아래 꼭짓점(merge 노드).
- 옆에 "엣지는 공짜, 에이전트는 비싸다" 캡션 — flatten/dedupe 같은 순수 연산은 코드(엣지)로, 판단이 필요한 합성만 에이전트(노드)로.
- **실습**: 여러 소스를 조사해 하나의 리포트로 합치는 자신의 작업(예: 시장 조사, 경쟁사 벤치마킹)을 다이아몬드 패턴으로 재설계 — split 지점과 merge 지점이 정확히 어디인지 표시.

### 다이어그램 4 — "이중 맹검 리뷰어" (Yarchi + Akshay + Codez 종합)
- 워커 노드 → 산출물 → 두 개의 독립 리뷰어 노드(서로를 볼 수 없음, 룰북만 공유) → 판정 합류 지점(불일치 시 룰북 자체를 수정).
- **실습**: 자신이 만드는 산출물(코드 리뷰, 콘텐츠 검수 등) 하나에 대해 "기계로 판정 가능한 심판 규칙 3줄"을 먼저 써보기(Yarchi의 1단계: "무엇이 통과인지 기계가 답할 수 있는가").

### 다이어그램 5 — "체크포인트 철도" (Yarchi durable state + Akshay checkpoint 종합)
- 선로 위에 5개의 역(체크포인트), 3번째 역에서 열차가 탈선(실패)하는 그림, 재시작 열차가 3번째 역부터(0번역이 아니라) 출발하는 화살표.
- 부작용 있는 정거장(이메일 발송 등)에는 "재실행 안전 필요" 경고 아이콘.
- **실습**: 자신이 운영하는 장시간 자동화(cron/heartbeat 루틴 등) 하나를 골라 "지금 중간에 죽으면 어디서부터 다시 시작되는가"를 답해보고, 답이 "처음부터"라면 어느 지점에 체크포인트를 추가할지 표시.
