Lesson 0001 · AI Agents in Depth

에이전트 = LLM + Context + Tools

에이전트를 "똑똑한 챗봇"으로 볼 수 있지만, 책이 제시하는 정답은 세 부품의 분업 공식이다. 모델이 아니라 조합이 에이전트다.

오늘의 한 줄 답: 현대 에이전트는 LLM(추론 엔진) + Context(작업 정보 집합) + Tools(행동 인터페이스)의 조합이고, 이 셋이 ReAct 루프(reason → act → observe) 안에서 결합할 때 비로소 "에이전트"가 된다. 모델을 바꾸지 않고도 Context와 Tools, 즉 Harness를 개선해 성능을 크게 올릴 수 있다.

1. 세 부품의 분업

Bojie Li의 책은 Chapter 1을 이 공식 하나로 연다. 각 부품에는 명확한 역할 이름이 붙어 있다.

LLM = Reasoning Engine
의도 파악, 추론, 계획, 판단을 담당하는 의사결정 코어. 세계 지식은 pre-training이, 의사결정 전략은 post-training(SFT/RL, Ch7)이 만든다.
Context = Working Set
매 의사결정 시점에 에이전트가 사용 가능한 정보 전체: 환경, 사용자 메모리, 도메인 지식, 자기 상태, 태스크 진행 상황.
Tools = Action Interfaces
사전정의 tool call뿐 아니라 on-demand로 로드하는 Skill, 즉석 생성 코드, sub-agent 위임, 사용자 확인 요청까지 포함하는 넓은 개념.

고전 RL에 매핑하면 LLM은 Policy, Context는 Observation Space, Tools는 Action Space다. 그리고 현대 에이전트가 고전 시스템과 다른 세 가지 특징이 있다: open-ended action space(고정 버튼이 아니라 임의의 자연어·코드를 행동으로 생성), internal reasoning(행동 전에 계획), continuous interaction(환경 피드백에 따라 전략을 조정).

2. 도구는 생각보다 넓다: 5가지 분류

"도구 = API 호출"로 좁게 볼 수 있지만 책은 5개 카테고리로 나눈다(Ch4에서 심화). 특히 4번과 5번이 놓치기 쉽다.

  1. Perception Tools — 정보 접근: 검색엔진, 파일시스템, API/DB.
  2. Execution Tools — 외부 시스템에 작용: 코드 실행, 파일 조작, 시스템 명령.
  3. Collaboration Tools — 다른 에이전트·사람과 분업: sub-agent 위임, human confirmation.
  4. Event Trigger Tools — 에이전트가 호출하는 게 아니라 외부 입력이 에이전트를 깨움: 이메일 수신, 스케줄, Webhook.
  5. User Communication Tools — 사용자와의 채널: 문자, 음성 전화, 이메일.

tool calling의 4단계는 이렇다. ① context가 사용 가능한 tool을 모델에 알리고(이름/용도/파라미터) → ② 모델이 스스로 호출 여부·대상·인자를 결정하고 → ③ framework가 실행해 결과를 context에 append하고 → ④ 모델이 결과를 보고 다음 행동을 정한다. 개발자는 tool 정의와 실행만 만들고, 결정은 모델이 한다. 그래서 설계 원칙은 "전용 tool 나열"이 아니라 범용 tool(계산기 대신 Python sandbox, 메모 tool 대신 file read/write)을 주고 LLM에게 조합의 자유를 주는 쪽이다.

실무 번역: Aside를 이 분류로 볼 수 있다. websearch·read_file은 Perception, bash·edit_file은 Execution, subagent·ask_user_question은 Collaboration, routine의 event trigger는 Event Trigger, notification은 User Communication. "스킬(SKILL.md)을 쌓는 행위"는 책의 언어로 externalized learning — 경험을 Harness의 일부로 고정하는 작업이다.

3. Context의 5요소와 절제 실험

API 관점에서 context는 다섯 조각이다. ① System Prompt(에이전트의 job description, 고정) ② Tool Definitions(이름/설명/파라미터 — ①과 함께 static prefix를 이룸) ③ User Messages(사용자 입력 + RAG로 검색된 지식) ④ Assistant Messages(reasoning + content + tool_calls의 최대 3부분) ⑤ Tool Results(framework가 실행한 결과). 즉 Context = static prefix(①②) + dynamic trajectory(③④⑤).

책의 실험 1-1(ablation study)은 요소를 하나씩 제거해 각자의 역할을 증명한다:

  • tool definitions 제거 → tool 호출 자체가 완전 불능
  • tool results 제거 → 같은 tool을 반복 호출하는 무한 루프(blind loop)
  • reasoning 제거 → 연속 결정이 서로 모순
  • history 제거 → 이미 한 단계를 반복

핵심 통찰은 한 문장이다: context가 결정 시점의 정보를 결정하고, 에이전트는 그 정보로만 결정할 수 있다. 에이전트의 이상 행동을 디버깅할 때 "모델 탓" 전에 "그 시점 context에 뭐가 있었나"를 보는 습관이 여기서 나온다.

4. ReAct 루프와 trajectory

ReAct = Reasoning + Acting. 실제로는 3단계의 반복이다: reason → act → observe. 매 LLM 호출은 완전한 trajectory를 입력받고, 응답은 다시 trajectory에 append된다. 책의 예시(다중통화 매출 집계)는 3번의 iteration, 4번의 tool call로 끝난다: 1라운드에 3개 환율 변환을 병렬 호출하고, 2라운드에 code interpreter로 집계하고, 3라운드에 최종 답변을 낸다.

여기서 trajectory는 단순 실행 로그가 아니다. 책은 이를 "능력의 증거 데이터"로 본다: 대규모로 분석하면 행동 패턴과 더 나은 tool 설계가 나오고, 지식베이스로 증류할 수 있고, RL 훈련 데이터가 된다(Ch6, Ch8의 복선).

5. Harness Engineering: 모델 너머의 경쟁력

공식은 확장된다: Agent = LLM + [Context + Tools + Constrain + Verify + Correct] = Model + Harness. 앞의 최소 공식이 데모의 시각이라면, 확장 공식은 프로덕션의 시각이다. 다섯 기능에는 각각 설계 원칙이 붙는다:

Context
충분한 정보 제공.
원칙: Information Sufficiency
Tools
행동 인터페이스.
원칙: Clear Interface
Constrain
행동 경계.
원칙: Fail-Safe Defaults(기본 꺼짐, 명시적 허용)
Verify
결과 정확성 판단.
원칙: Input Isolation(검증은 구조화 데이터만)
Correct
실패 복구.
원칙: 복구 불가 확정 전 중간 상태 비노출(silent retry, circuit breaker)

귀를 기울일 만한 사실: 책에 따륩 Claude Code의 Harness 코드 대부분은 실행 자체가 아니라 Constrain/Verify/Correct — 상태 관리, 다층 압축, 권한 분류, 회로 차단, 오류 복구에 쓰인다. 산업의 초점이 task completion에서 reliable task completion으로 이동했다는 뜻이다.

엔지니어링 패러다임은 중첩 구조로 진화했다: Software Eng ⊃ Prompt Eng ⊃ Context Eng ⊃ Harness Eng ⊃ Loop Engineering. 근거 사례가 강력하다: LangChain은 Terminal Bench 2.0에서 모델 변경 없이 Harness 개선(자기 실행 결과 점검, 반복 루프 감지, 추론 전략 개선)만으로 52.8% → 66.5%, 30위권 밖에서 top 5로 올랐다. Rich Sutton의 "The Bitter Lesson"에 대한 책의 태도도 균형적이다: "방향은 인정, 속도는 실용적으로." 모델이 Harness를 흡수해 가는 건 맞지만 훈련 주기는 월 단위 — 모델의 현재 능력 경계가 바로 Harness가 가치를 만드는 자리다.

6. Workflow vs Autonomous, 그리고 가드레일

오케스트레이션은 두 극단 사이의 스펙트럼이다. Workflow는 사전 정의된 코드 경로(결정론적, 프로세스 통제·보안에 유리), Autonomous Agent는 실행 경로를 런타임에 정한다(= ReAct loop, 유연하지만 비용·오류 누적). 책의 실무 지침은 명확하다: 프롬프트 먼저 → workflow → 마지막에 autonomous. 실제 시스템은 혼합이 일반적이고, autonomous에는 명시적 중단 조건(완료, final answer, tool call 없는 응답, 최대 라운드, 에러 횟수)이 필수다.

가드레일은 3종으로 defense in depth를 이룬다. Input-side(relevance/safety classifier, rule-based — jailbreak와 prompt injection은 구별: 전자는 사용자의 직접 우회, 후자는 외부 데이터 경유 간접 조작), Execution-side(tool risk rating: 가역성/권한/금전 영향으로 low/medium/high, high는 사람 확인), Output-side(PII 필터, 출력 검증). Anthropic의 Constitutional Classifiers(2026)는 자연어 constitution으로 합성 데이터를 만들고, 질문+답변을 함께 보는 joint contextual judgment로 판별하며, 경량 probe가 먼저 스크리닝하는 two-stage로 비용을 줄인다.

실무 번역: ERP 일일 동기화처럼 반사적인 자동화는 workflow(결정론)가 맞고, 탐색성 작업만 autonomous로 두는 것이 책의 순서와 일치한다. 그리고 루틴/크론 설계 시 실행 로직보다 실패 감지·회로 차단·복구 경로(Correct)에 설계 비중을 둬야 한다 — "0행 무음 실패"는 Verify/Correct 부재의 교과서 사례다.
