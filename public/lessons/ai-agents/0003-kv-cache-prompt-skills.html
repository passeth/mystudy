Lesson 0003 · AI Agents in Depth

KV Cache 친화적 설계, 시스템 프롬프트, 그리고 스킬

캐시는 사후 최적화가 아니라 사전 아키텍처 제약이다. 프롬프트 한 줄의 공백이 월 추론비를 두 배로 만들 수 있고, 스킬의 description은 기능 요약이 아니라 라우팅 규칙이다.

오늘의 한 줄 답: 컨텍스트의 앞부분(static prefix)은 절대 건드리지 말고, 동적인 것은 항상 끝에 append하라. 이 한 원칙이 KV cache 경제성, 시스템 프롬프트 설계, 스킬 로딩 방식을 모두 관통한다.

1. 캐시가 왜 "아키텍처"인가

LLM 추론에서 새 토큰을 만들 때마다 이전 모든 토큰의 Key/Value를 다시 계산하면 비용이 폭증한다. 그래서 이전 토큰의 K/V를 재사용하는 것이 KV Cache다. 문제는 prefix의 한 토큰이라도 바뀌면 레이어 전파 때문에 그 지점 이후의 캐시가 전부 무효화된다는 것. 캐시는 끝에서부터가 아니라 변경 지점부터 깨진다.

여기에 API 서비스 계층의 Prompt Cache가 얹힌다. 요청 사이에 동일 prefix를 재사용하는 캐시로, Anthropic·DeepSeek·OpenAI GPT-5 계열 모두 캐시 읽기 가격이 신규 계산의 약 1/10이다. 즉 prefix를 안정적으로 유지하는 것만으로 비용이 10분의 1이 될 수 있다.

실제 사고 사례 (책 §2.3): 어떤 프로덕션 팀이 system prompt에 Current time: {{now}} 한 줄을 추가했다. 매 요청마다 캐시가 무효화되면서 TTFT가 0.5초 → 3-5초, 월 추론비가 약 2배로 뛰었다. 동적 정보는 prefix에 박는 게 아니라 대화 끝에 새 메시지로 append해야 한다.

책이 강조하는 프레임: "Caching as an Architectural Constraint". Claude Code는 캐시 경계 마커로 system prompt를 분할해 경계 앞은 전역 캐시, 뒤는 세션별로 관리하고, 프롬프트 조각을 "cacheable / cache-breaking"으로 타이핑해 후자에 경고를 단다. 캐시 경제성은 나중에 튜닝하는 것이 아니라 설계 단계에서 정해진다.

2. 3대 실천 원칙과 유해 패턴 5종

원칙 1
system prompt와 tool definitions는 확정 후 변경 금지. 공백 하나 추가도 전체 캐시 무효화다.
원칙 2
동적 정보(시각, 사용자 상태)는 항상 끝에 append. 새 메시지로 대화 말단에 붙인다.
원칙 3
표준 API 메시지 형식 사용. "USER: ... ASSISTANT: ..." 수동 문자열 연결은 훈련 포맷 이탈로 다단계 추론이 약해진다.

책의 실험 2-3은 흔하지만 유해한 패턴 5종을 정리한다:

  1. Dynamic System Prompt — 타임스탬프 임베딩. 캐시 전멸. 정답: user 메시지 끝 append 또는 필요시 tool로 획득.
  2. Dynamic User Configuration — 잔여 API 콜·잔액을 매 요청 갱신. 캐시 파괴. 전용 상태 관리로 분리.
  3. Tool 정의 동적 정렬 — 사용 빈도순 재배열. 고정 순서가 선택 정확도에 거의 영향 없이 성능은 크게 낫다.
  4. Sliding Window history — prefix 일관성 파괴 + 핵심 tool 결과 유실. 2라운드에 읽은 파일이 15라운드에 필요한데 윈도우 밖이면 같은 tool을 반복 호출하는 루프에 빠진다.
  5. Text Formatting — role-content를 평문으로 연결. 캐시 문제가 아니라 모델 능력 문제: 반복 작업, tool 결과 무시, 파싱 오류.

참고로 Attention 시각화(실험 2-2)가 보여주는 Position Bias — 처음과 끝의 정보는 잘 찾고 중간은 놓친다(Lost in the Middle, TACL 2024) — 도 배치 원칙과 일치한다. 중요한 것은 처음이나 끝에 둔다.

3. CoT 정책의 업계 반전: "thinking is not waste but state"

DeepSeek R1 시절 업계 표준은 historical reasoning 전량 제거였다(토큰 절약 + 훈련 분포 이탈 우려). 그런데 에이전트 시나리오에서 중간 추론은 "왜 이 tool을 불렀고 어떤 가설을 배제했나"라는 상태다. 제거하면 매 턴 처음부터 재추론하며 같은 실수를 반복한다. DeepSeek V4는 reasoning_content 반환을 의무화했고(미반환 시 API 에러), Kimi K2·GLM-5도 같은 프로토콜을 따른다. Claude는 tool call 루프 안에서 thinking block을 서명 검증과 함께 그대로 돌려받길 요구한다.

4. 시스템 프롬프트: 신입 사원 테스트와 ablation

책이 제시하는 리트머스: "우리 워크플로우를 전혀 모르는 유능한 신입이 이 system prompt만 읽고 뭘 할지 알 수 있는가?"

  • Process-driven > Rule stacking — 흐름도 없는 수백 개 규칙 나열은 사람에게도 모델에게도 혼란. SOP 형태(검증→분류→전처리→실행→검증)로 단계와 예외 분기를 명시한다.
  • 비즈니스 규칙은 실행 가능 수준으로 번역 — "상황에 맞게 과금 유형 선택"은 모호하다. Pine AI 사례처럼 "커미션은 기존 청구액 절감 협상에만, 환불/해지는 NEVER percentage_based → fixed_fee"까지 낮춰야 한다. 모델에게 비즈니스 규칙의 재량권을 주지 말 것.
  • Few-shot — 규칙으로 서술 어려운 것(문체, 포맷)엔 예시 2-3개 > 장문 설명. 단, 예시 세트는 byte-stable하게: 요청마다 "가장 관련된" 예시를 동적 검색하면 캐시가 반복 무효화된다. 경계 케이스를 커버하는 2-3개 > 비슷한 10개.
  • Tool definition — 사용 경계("NEVER invoke grep as Bash command"), 구체 예시, tool 간 관계("Read를 쓴 후에 Edit")까지 적는다.
실험 2-4 (Tau-Bench ablation): ① tone 변경(캐주얼/격식) → 완료율 영향 미미. ② 정보 조직 제거(구조화 → 무구조 규칙 나열) → 성공률 30%p 이상 폭락, "환불 전 본인확인" 같은 핵심 규칙 위반 빈발. ③ tool 설명문 제거 → tool call 오류율 +45%. 교훈: 성능이 나쁠 때 전면 재작성하지 말고 ablation으로 기여도를 측정하라.

5. Prompt Injection과 방어 3종

에이전트는 tool이 있어 챗봇보다 위험하다 — 파일 삭제, 메일 발송 같은 불가역 행동이 가능하고, perception tool 하나하나가 injection 진입점이다(웹페이지 보이지 않는 요소, PDF 메타데이터, 이미지 EXIF). Context 레벨 방어 3종:

Source Tagging
외부 콘텐츠를 <external_content source="webpage">처럼 래핑하고 출처를 주석.
Structured Roles
role 체계로 지시/데이터를 구분. tool 결과를 user 메시지에 섞지 말 것.
Input Sanitization
의심 패턴 필터. 보조 수단일 뿐 주 방어선이 아니다.

새로운 표면: Skill 자체가 고권한 지시로 context에 진입한다. 출처 불명 스킬은 실행 코드처럼 설치 전 리뷰해야 한다. Context 방어는 1차 방어선일 뿐이며 execution 레벨(권한 통제, 샌드박스)과 layered defense가 필요하다(Ch4-5).

6. Agent Skills: Progressive Disclosure와 라우팅 규칙

정적 프롬프트가 팽창하면 두 가지가 망가진다: 토큰 낭비(대부분 현재 태스크와 무관)와 주의 희석(context rot). Skills의 핵심은 3계층 progressive disclosure다:

계층내용시점·비용
L1 metadataSKILL.md frontmatter의 name + description시작 시 주입, 수백 토큰
L2 본문SKILL.md 전체모델이 판단 후 Skill tool로 로드, ~2K 토큰
L3 하위 문서reference.md, scripts/*.py 등선택적 심화 로드

가장 중요한 설계 포인트: description은 기능 요약이 아니라 라우팅 규칙이다. "Use when / Do not use when"과 negative example이 필수. "backend 작업 지원" 같은 광범위 서술은 무관한 태스크에 오발동한다. 라우팅에는 "무엇을 할 수 있나"보다 "언제 나를 쓸 것인가"가 중요하다.

배치 3방법의 트레이드오프: ① system prompt 주입 — instruction-following 최강이지만 로드마다 캐시 무효화. ② 일반 파일 읽기로 중간 배치 — 캐시 무결이나 중간 위치 지시 준수가 모델 의존. ③ metadata는 사전 제공 + 전체는 전용 Skill tool로 on-demand 로드(Claude Code 방식) — 라우팅과 실행 분리, emit-once라 최초 1회 cache creation 비용만 내고 이후 영구 HIT. "KV Cache-friendly"는 비용 제로가 아니라 "write once, benefit repeatedly"다.

실무 번역: Aside 스킬을 만들 때 frontmatter description을 "이 스킬은 ~한다"가 아니라 "Use when ~ / Not for ~" 라우팅 규칙으로 쓰고 있는지 점검하라. 그리고 네가 관리하는 시스템 프롬프트·AGENTS.md·SOUL.md는 static prefix다 — 날짜나 루틴 상태 같은 동적 정보를 거기 박아넣으면 매번 캐시를 깨는 것과 같다. 동적 상태는 MEMORY.md 갱신처럼 별도 채널(끝 append)로 흘려야 한다.

8. 미니 실습 (10분)

네가 직접 만든 Aside 스킬 하나(예: pdp-story, glovv)를 열고 frontmatter description을 라우팅 규칙 관점에서 감사해 보자.

  1. "Use when"이 구체적 트리거(사용자 발화 패턴)까지 적혀 있는가?
  2. "Do not use when" 또는 negative example이 있는가? 없으면 오발동이 나기 쉬운 인접 태스크를 하나 적어 추가해 보자.
  3. 스킬이나 프롬프트 어딘가에 날짜·상태 같은 동적 값이 정적 파일에 박혀 있지 않은가? 있다면 끝 append 채널로 옮기는 설계를 메모하자.
