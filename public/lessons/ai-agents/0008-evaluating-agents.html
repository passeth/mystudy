Lesson 0008 · AI Agents in Depth

에이전트 평가: 벤치마크에서 프로덕션 관측성까지

"측정할 수 없으면 개선할 수 없다"는 상투적이다. 이 챕터의 진짜 주장은 더 날카롭다: 당신이 평가하는 것은 모델이 아니라 모델+하네스 조합이고, 평가 없는 개선은 연금술이며, 오늘 프로덕션이 노출한 실패는 내일의 회귀 테스트다.

오늘의 한 줄 답: 평가 대상은 모델 단독이 아니라 모델 + 하네스 조합이다. model swap 실험으로 병목이 모델인지 하네스인지를 가르고, Pass@k(능력 상한)와 Pass^k(신뢰성)를 구분하고, 관측 데이터를 평가 자산으로 증류하는 폐쇄 루프가 성숙한 에이전트 운영의 조건이다.

1. 평가 대상 = 모델 + 하네스, 그리고 model swap 실험

같은 모델도 하네스에 따라 성적이 크게 달라진다. 그래서 "모델 능력 부족"과 "하네스 설계 결함"을 구분하는 도구가 필요하다 — model swap 실험(하네스 고정, 모델 교체): 강 모델로 바꿔도 점수가 그대로면 병목은 하네스, 모델 강도에 점수가 민감하면 병목은 모델이다. ablation(컴포넌트를 하나씩 제거)과 역할이 다르다: ablation은 "하네스의 무엇이 중요한가", model swap은 "병목이 모델인가 하네스인가"를 답한다.

평가 시스템의 제1 가치는 모델 진화에 빠르고 신뢰성 있게 따라가는 것이다. 신모델이 나올 때 자체 평가셋 풀런으로 업그레이드 결정을 몇 시간 안에 데이터 주도로 내릴 수 있다. 평가 시스템은 3계층으로 나뉜다: ① 환경("어디서 시험") ② 방법("어떻게 채점" — 데이터셋, 메트릭, LLM-as-a-Judge) ③ 결정("시험 후 무엇" — 모델 선택, 아키텍처 최적화, 통계적 유의성).

2. 평가 환경과 데이터셋 설계

평가 환경의 5요소는 Dataset / Environment State(실재성+통제성) / Tools(원자적 연산 제공 — "문제 해결" 같은 고수준 추상 툴은 계획 능력 측정을 불가능하게 한다) / Rubric / Interaction Protocol이다. 두 패러다임:

Tool-calling (Verifiers 프레임워크)
실행 가능 기준으로 검증(테스트 통과, 답 일치). SingleTurnEnv → ToolEnv → StatefulToolEnv → SandboxEnv로 상태성·격리가 올라간다. 인간/모델 판정 불요.
Human-computer interaction (τ-bench)
핵심 설계 원칙은 Progressive Information Disclosure — 실제 사용자는 처음에 요구를 완전히 표현하지 못한다("비행기에 문제가 있어요"). 다른 LLM이 사용자를 시뮬레이션하고, DB 최종 상태 + 대화 내용의 이중 검증, binary reward.
τ²-bench의 개선
Dual-Control(사용자 시뮬레이터도 같은 환경을 조작 — 에이전트는 툴로 그 변화를 관찰해야 함) + Grounding Requirements(응답은 툴 반환의 실제 환경 상태에 근거해야).

데이터셋 5대 도전 — 명확성 vs 개방성(GAIA), 실재성 vs 통제성(SWE-Bench Verified: 2,294개 중 인간 평가를 거쳐 500개, 29%만 통과 — 높은 탈락률이 평가 품질의 필요 투자다), 다양성 vs 체계성(AndroidWorld의 능력 태그), 비용 vs 커버리지, 그리고 데이터 오염 방지(Terminal-Bench는 canary GUID를 내장해 모델이 그 GUID를 출력하면 벤치마크 유출의 증거가 된다).

난이도 계층은 진단 도구다. GAIA에서 인간은 Level 1-3 모두 87-94%인데 GPT-4(도구 장착)는 30.3% / 9.7% / 0%였다. L1 실패는 기본 툴 사용 문제(→ 프롬프트 개선), L2는 계획·정보 통합 문제(→ 계획 메커니즘), L3는 장기 추론 문제(→ 아키텍처/포스트트레이닝) — 같은 "실패"가 층에 따라 완전히 다른 개선 방향을 가리킨다.

3. 메트릭: Pass@k와 Pass^k를 혼동하지 말 것

Pass@k
k회 중 1회 이상 성공 확률. "할 수 있는가?"(능력 상한). 단일 성공률 60% → Pass@5 = 1-0.4⁵ ≈ 99%.
Pass^k
k회 모두 성공 확률. "안정적인가?"(신뢰성). 같은 조건에서 Pass^5 = 0.6⁵ ≈ 7.8%.
사용 기준
회귀 테스트·중요 조작은 Pass^k, 탐색 태스크는 Pass@k/Best@k, 일상은 Pass@1. 혼동하면 에이전트를 오독한다.

그 밖의 메트릭 축: Process(action validity, tool call correctness, path efficiency — 인간 전문가 베이스라인 필요), Outcome(task success rate), 안전/컴플라이언스(zero-tolerance — 단일 심각 위반이 전체 평가를 무효화), Robustness(시드 민감도, 陳腐 메모리 간섭). 그리고 궤적 vs 결과의 이중 커버: 에이전트가 "예약 완료"라고 말한 것(궤적) ≠ DB에 레코드가 있는 것(결과). 궤적만 복면 "말하고 안 함"을 놓치고, 결과만 복면 더 나은 우회로를 벌한다.

4. LLM-as-a-Judge: Rubric이 전부다

오픈엔드 태스크는 표준 답이 없으니 Rubric 기반 LLM 채점으로 간다. Scale AI "Rubrics as Rewards"의 4원칙:

  1. Expert Guidance — 도메인 지식 반영. 전문가 근거 없는 Rubric은 유창성 같은 표면 특징만 포착한다.
  2. Comprehensive Coverage — 정확성/일관성/완전성/안전 + Pitfalls(고위험 흔한 오류) 명시.
  3. Standardized Importance Weighting — Essential/Important/Optional/Pitfall 분급 + Veto 메커니즘(환각 = 다른 차원 만점이어도 무효).
  4. Self-Contained Evaluation — "깊은 이해를 보인다" ❌ → "권위 이론 2개+를 인용하고 결론 지지 방식을 정확히 설명" ⭕.

알려진 함정 세 가지. ① Length bias — 더 긴 답에 고득점. 방어: 장황성 감점 명시, pairwise 비교 시 길이 맞추기, 점수-길이 상관 정기 감사. ② Same-family 문제 — 에이전트와 judge가 같은 모델 패밀리면 에이전트가 judge의 사각을 악용 학습한다. Goodhart's Law: 지표가 최적화 목표가 되는 순간 좋은 지표이기를 멈춘다. 완화는 multi-source heterogeneous judging(다른 패밀리의 독립 심판 — 편향이 직교라 동시 기만이 어렵다). ③ judge 자체의 신뢰성 — 배포 전 인간 주석 gold standard(100-200건)로 Cohen's kappa(우연 일치 할인) > 0.7을 확인하고, Rubric 변경 시 재보정한다.

5. 통계적 유의성과 비용 구조

이항 비율의 표준오차는 SE ≈ √(p(1-p)/n). 100건 평가셋에서 70% vs 73%의 3%p 차이는 표준오차 범위 안에 완전히 들어간다 — 코인 플립과 다를 바 없다. 두 구성을 같은 태스크셋에서 돌리므로 paired 분석(불일치 케이스만 보는 McNemar's test)이 더 민감하고 정확하다. 추가 원칙: 구성당 3-5회 반복해 평균+분산 보고(에이전트는 같은 입력에도 드리프트), 점수 차가 샘플링 노이즈보다 작으면 전환 결정 금지, multiple comparisons 함정 주의(6개 가설을 각 95% 신뢰로 시험하면 최소 1개 위양성 확률 ≈ 26%).

비용은 3계층으로 분해한다: ① 모델 추론 — context accumulation effect(매 턴 전체 이력 재전송)과 thinking token(미표시지만 과금)이 증폭 ② 툴 호출 — 외부 API 과금 + 간과하기 쉬운 툴 출력의 컨텍스트 주입 비용(웹 검색 1회 2,000-5,000 토큰이 이후 매 라운드 입력으로 재과금) ③ 인프라. 책의 3라운드 환불 에이전트 계산에서 캐싱은 입력 비용의 거의 절반을 절감했다(경험 범위 30-60%). 비용 최적화의 핵심은 싼 모델 선택이 아니라 라운드 수와 컨텍스트 증가 제어다.

6. Observability → 평가 자산, 그리고 난부 평가 인프라

분산 시스템의 observability를 차용하되 에이전트는 더 어렵다(같은 입력 다른 출력, 사고 불투명). 데이터 모델은 trace(태스크)와 span(LLM 호출/툴 호출)의 트리이고, 표준은 OpenTelemetry + OpenInference(LLM 특화 시맨틱 컨벤션), 플랫폼은 LangSmith/Langfuse/Arize Phoenix다. 최고 가치 활용은 관측 데이터를 평가 자산으로 증류하는 것: 프로덕션 궤적에서 실패/의심 케이스 추출 → 익명화 → 평가셋의 신규 회귀 테스트. 평가셋은 일회성 정적 문서가 아니라 제품과 함께 진화하는 living asset이다.

프로덕션 에이전트(OpenClaw 사례)의 난부 평가 인프라 4종:

  • Ablation 스위치 — 주요 기능(thinking, 컨텍스트 압축, 자동 메모리)을 마스터 스위치로 끄고 "베어 모델" 베이스라인과 비교. "이 기능이 진짜 UX를 개선하는가, 유용해 보일 뿐인가?" 모델 진화로 불필요해진 기능(feature debt)을 정기 발견한다.
  • 2계층 feature flag — compile-time(코드 물리 제거, 깨끗한 ablation) + runtime(서버 배포 설정, 노출 이벤트는 세션당 최대 1회 로깅해 실험 오염 방지).
  • 프롬프트 회귀 테스트 — 시스템 프롬프트는 에이전트 행동의 코어 "코드"다. 결정론적 렌더링 + 버전 스냅샷 + 모든 프롬프트 변경에 평가셋 회귀 테스트(코드 CI처럼).
  • Mechanism vs target metric 구분 — "plan 파일 길이 단축"은 mechanism, 진짜 target은 "세션 비용 절감". 내가 바꾸는 것이 내가 진짜 care하는 것과 같은가? + guardrail metrics(만족도 하락/에러율 상승 시 실험 중단하는 협상 불가 임계).

방법론 전체는 한 문장으로: Observe → Hypothesize → Experiment → Decide → Iterate. 벤치마크는 일회 시험이 아니라 지속 건강검진이다. 책의 가상 케이스(교육용)에서는 이 루프가 88% → 94%를 만들고, H4(전역 thinking: 성능은 오르지만 전 태스크 비용 3배 → 기각, 대신 조걶 활성화 H7로 진화) 같은 기각의 판단도 데이터로 낸다.

실무 번역: 이 챕터는 당신의 운영에 직접 겨냥한다. 매일 도는 루틴(teach-to-3min-video, erp-sales-hx-daily)은 "가끔 성공"이 아니라 Pass^k로 봐야 하고, erp 싱크의 0행 출력 사건은 "실패 궤적 → 회귀 테스트 증류"(행 수 > 0 assertion) 패턴의 교과서적 적용 대상이다. 그리고 수십 건 규모 자체 평가에서 2-3%p 차이로 모델이나 프롬프트를 바꾸고 있다면, 그것은 코인 플립으로 의사결정하는 것과 같다.

7. 퀴즈 · 회수 연습

Q1. 하네스를 고정하고 더 강한 모델로 교체했는데도 평가 점수가 그대로다. 가장 타당한 해석은?

Q2. 어떤 에이전트의 Pass@5는 99%인데 Pass^5는 7.8%다. 이 에이전트에 대한 올바른 서술은?

Q3. 100건 평가셋에서 신 프롬프트 73%, 구 프롬프트 70%가 나왔다. 올바른 판단은?

8. 미니 실습 (10분)

지금 운영 중인 자동화 하나(루틴, 스킬, 싱크 파이프라인)를 골라 최소 평가를 설계하자.

  1. Verifier 1개 정의: 그 자동화의 "완료"를 기계적으로 판정하는 조건 하나. (예: erp-sales-hx-daily → 당일 삽입 행 수 > 0 AND 최근 sale_date = 어제)
  2. Pass@k vs Pass^k: 그 자동화는 탐색 태스크(한 번이면 충분)인가, 안정성 태스크(매번 성공해야)인가? 후자라면 최근 10회 실행의 Pass^10을 계산해 본다.
  3. 회귀 테스트 증류: 과거 실패 1건(0행 출력, 업로드 실패 등)을 verifier의 assertion으로 옮긴다. "오늘의 실패 = 내일의 회귀 테스트".
