Lesson 0002 · AI Agents in Depth

API 레벨 컨텍스트와 에이전트 코어 루프

에이전트 프레임워크의 본체는 사실 단순하다: message list를 올바르게 유지하는 while 루프 하나. 그 단순함을 아는 것이 모든 고급 기법의 출발점이다.

오늘의 한 줄 답: LLM API는 stateless다 — 매 호출의 message list에 필요한 모든 정보가 들어 있어야 하고, 에이전트 프레임워크의 중심 책임은 바로 그 list를 유지·관리하는 것이다. "에이전트의 코어 루프"는 while 루프 + tool 실행 + append로 직접 쓸 수 있을 만큼 작다.

1. Context는 에이전트 능력의 천장

모델 능력은 범용이다. 그런데 실무 태스크는 local knowledge — 제품 아키텍처, 비즈니스 규칙, 운영 제약, 조직 내의 관례 — 에 의존한다. 이런 지식은 파라미터에 없다. 책의 결론은 직설적이다: 중간 능력 모델 + 잘 정리된 context > 강한 모델 + 부실한 context.

Coding agent 기준 최소 context 3종은 code context(코드베이스 구조/표준), process requirements(브랜치 전략/리뷰/CI-CD), environment configuration(개발 환경/DB/배포/키 관리)다. 그리고 책이 강조하는 전환: context engineering은 기술 문제 이전에 조직 문제다. 지식이 암묵지로 남은 팀은 에이전트도 못 쓴다. "에이전트를 매번 새로 들어온 팀원으로 대하라."

2. 네 가지 message role

API 레벨에서 context는 role이 붙은 메시지의 리스트다.

system
개발자의 지시. 가장 높은 우선순위. 대화 낂내 고정되는 job description.
user
사용자 입력. RAG로 검색된 외부 지식도 여기 실린다.
assistant
이전 모델 출력. reasoning + content + tool_calls의 최대 3부분.
tool
framework가 실행한 결과. tool_call_id로 대응하는 call과 연결된다.

한 가지 오해 교정: tool definitions는 메시지가 아니다. 별도 tools 필드로 전달된다. 그래서 메시지 리스트(trajectory)와 tool 목록은 API 요청 안에서도 다른 자리에 놓인다.

3. Stateless의 의미: 루프가 곧 프레임워크

매 API 호출은 상태를 갖지 않는다. 서버가 "이전 대화"를 기억해 주지 않으므로, 요청의 message list에 필요한 모든 정보가 들어 있어야 한다. 이 사실 하나가 프레임워크의 존재 이유를 정의한다: 에이전트 프레임워크의 중심 책임 = message list의 유지 관리(올바른 시점에 append하고, 관련 history를 전송하는 것). 이 챕터 이후의 모든 기법 — 캐시, 압축, 상태 바 — 은 그 list의 내용과 구조를 개선하는 기법이다.

책임 분할도 다시 확인해 두자: 모델은 어떤 tool을 어떤 인자로 부를지 결정만 하고, 실행은 framework가 한다. 그리고 의존성 없는 call은 모델이 한 번에 여러 개를 반환해 framework가 병렬 실행한다 — 지연 절감의 기본 수법이다.

4. 최소 에이전트 루프, 직접 보기

책이 제시하는 최소 루프는 이 정도다(의사코드):

messages = [system_prompt, user_input]

while True:
    resp = llm.chat(messages, tools=tools)
    messages.append(resp.assistant_message)   # reasoning + content + tool_calls

    if not resp.tool_calls:
        print(resp.content)                    # 최종 답변
        break

    for call in resp.tool_calls:               # 의존 없으면 병렬 실행 가능
        result = execute(call)
        messages.append(tool_message(call.id, result))  # tool_call_id로 연결

프로덕션에서는 여기에 max_iterations 상한이 필수다. Lesson 0001의 실험 1-1에서 봤듯, tool results가 유실되면 모델은 같은 호출을 무한 반복한다. 상한 없는 while 루프는 곧 무한 루프의 온상이다.

실무 번역: "프레임워크가 대단한 일을 한다"는 환상을 벗기는 게 이 레슨의 목적이다. Aside 세션도 결국 이 루프다 — 매 응답 후 assistant 메시지가 append되고, tool 결과가 tool role로 붙고, 다음 호출에 전체가 실린다. 세션이 길어질수록 비용이 늘고 컴팩션이 필요한 이유가 바로 이 "매 호출 전체 재전송" 구조다(Lesson 0004에서 다룬다).

5. 실험 2-1: 0.6B 모델도 tool calling이 된다

책의 실험 2-1은 로컬 소형 모델로 같은 루프를 돌린다: Qwen3-0.6B, Apple M2/16GB, MLX 런타임, 100 tokens/s 이상으로 tool calling 가능. 출력 순서는 <think> 추론 → 사용자 텍스트 → tool call이고, 종료 판단도 모델이 내린다.

시사점은 두 가지다. 첫째, 합리적인 프롬프트와 아키텍처가 갖춰지면 0.6B도 tool call을 할 수 있다 — 온디바이스 에이전트는 생각보다 가깝다. 둘째, 루프는 모델 크기와 무관하게 동일하다 — 프론티어 API든 로컬 MLX든 프레임워크 설계 원칙은 같다.

6. 디버깅 사고법: "그 시점의 list에 뭐가 있었나"

stateless + append-only 구조를 이해하면 디버깅이 단순해진다. 에이전트가 이상 행동을 하면 가능한 원인은 세 갈래뿐이다: ① 필요한 정보가 list에 없었다(context 부족) ② 있었지만 모델이 못 찾았다(밀도/위치 문제 — Lost in the Middle, Lesson 0003) ③ tool 실행 결과가 기대와 달랐다(실행층 문제). "모델이 이상하다"로 뭉뚱그리기 전에, 문제 시점의 message list를 재구성해 보는 습관이 이 코스 전체의 기본 자세다.
