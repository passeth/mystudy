Lesson 0004 · Graph Engineering v2

노드·엣지·상태·계약

실행 그래프는 루프를 대체하지 않는다. 루프는 자기 자신으로 돌아가는 1노드 그래프일 뿐이다. 그래프는 통제를 모델 안에서 밖으로, 사람이 그린 구조로 옮기는 일이다.

오늘의 한 줄 답: 노드는 "한 가지 일"만 하는 작업 단위, 엣지는 "실제로 데이터가 이동하는 관계"만("그리고"는 엣지가 아니다), 상태는 모든 노드가 읽고 쓰는 공유 객체다. 라우팅은 코드가, 판단은 모델이 한다.

1. "루프는 1노드 그래프다" — 그래프가 루프를 감싼다

Akshay Pachaar의 정리가 가장 명료하다: "A single agent loop is just a one-node graph with an edge pointing back to itself. Graphs don't replace loops. They connect and govern them." Yarchi는 같은 통찰을 다르게 표현한다: 루프에서는 통제가 모델 내부에 있어 안이 안 보이고, 그래프에서는 통제가 모델 밖 — 사람이 그린 노드 구조로 옮겨간다.

beamnxw는 5층 스택으로 위치를 짚는다: prompt(보내는 말) → context(모델이 보는 모든 것) → harness(도구 실행·상태 추적·에러 처리 코드) → loop(한 에이전트를 목표로 이끄는 자율 사이클) → graph(여러 루프에 걸친 조정: 무엇이 언제 실행되고 누가 누구를 검사하는가). "각 계층은 이전 계층을 감싼다. 하위 계층을 건너뛰면 그래프는 더 복잡하게 실패할 뿐이다."

2. 노드 자격, 엣지 판별

노드(Node)

작업 단위 하나 — 에이전트 호출, 순수 함수, 도구, 사람의 승인 행위 중 무엇이든 될 수 있다. Akshay의 냅킨 테스트: 그래프를 냅킨에 못 그리면 너무 복잡한 것이다.

엣지(Edge)

Codez의 엄격한 기준: 실제로 데이터가 이동할 때만 존재한다. "요약해줘, 그리고 날씨 알려줘"는 엣지가 없다 — 날씨가 요약을 소비하지 않기 때문이다. 모든 "그리고"에 대해 "다음 단계가 이전 단계의 출력을 실제로 읽는가?"를 물어야 한다.

State(상태)

엣지를 따라 흐르는 공유 객체 — 모든 노드가 읽고 쓴다. 실패 모드는 루프의 context rot가 그래프에서는 공유 상태 오염으로 옮겨간다는 것.

3. 타입 상태와 쓰기 권한

해법은 지루하지만 효과적이다: 상태에 타입 스키마를 부여하고, 어느 노드가 어느 필드에 쓸 수 있는지 명시적으로 결정하고, 여러 노드가 같은 필드를 갱신하면 병합(reducer) 규칙을 둔다. LangGraph 공식 문서의 StateGraph가 이 패턴의 대표 구현이다 — 노드가 shared state를 읽고 쓰며 State → Partial<State>로 동작한다.

4. 라우팅은 코드, 판단은 모델

Google ADK 2.0의 설계 원칙이 가장 깔끔하다: "예측 가능한 라우팅은 결정론적 코드가 통제하고, 모델은 실제 판단이 필요한 단계만 처리해야 한다." 모델이 경로를 직접 결정하면 유연하지만, 같은 상태가 실행마다 다른 경로를 탈 수 있어 디버깅이 괴로워진다. Codez의 코드 패턴도 같은 원칙이다: 라우터 노드가 diff 크기를 분류(모델의 판단)하되, 분류 결과에 따른 분기 자체는 if/switch(코드의 라우팅)로 처리한다.

5. 체크포인트의 정확한 의미

주장정확한 사실
"실패 지점에서 정확히 이어진다"체크포인트는 super-step 경계에 저장된다. 재개 시 영향을 받은 노드는 함수 처음부터 다시 실행된다.
"체크포인트는 아무 부작용 없이 안전하다"interrupt 이전 side effect도 재실행될 수 있으므로, 이메일 발송 같은 노드는 반드시 idempotent해야 한다.
"모든 프레임워크가 같은 durability를 준다"LangGraph checkpointer는 thread의 graph-state snapshot을 저장해 resume/time-travel/HITL/fault-tolerance를 지원하지만, InMemorySaver는 프로세스 재시작을 버티지 못한다.

근거: LangGraph 공식 Graph API, Durable execution, Persistence 문서. "정확히 멈춘 지점에서 이어진다"는 표현은 instruction-level continuation이 아니라 replay/checkpoint semantics로 이해해야 한다.

실무 번역: Aside 서브에이전트 파이프라인을 그릴 때도 같은 원칙이 적용된다. 하나의 산출물(예: HTML 파일)을 정확히 한 서브에이전트만 쓰게 하고, 다른 서브에이전트는 읽기 전용 조사만 하게 하면 상태 오염을 피할 수 있다. 재시도가 필요한 작업(파일 쓰기, git commit)은 반드시 멱등하게 설계할 것 — 같은 호출이 두 번 실행돼도 결과가 같아야 한다.

7. 미니 실습 (5-10분)

자신의 선형 프로세스(예: X 북마크 조사 → 정리 → 발행) 5단계를 종이에 적어보자.

  1. 각 화살표("그리고 나서")마다 "다음 단계가 이전 단계의 출력을 실제로 읽는가?"를 물어본다.
  2. 읽지 않는 화살표는 지운다 — 그것은 가짜 엣지였다.
  3. 남은 진짜 엣지만으로 그래프를 다시 그린다. 몇 개가 사실은 독립적으로 병렬 실행 가능했는지 확인한다.
