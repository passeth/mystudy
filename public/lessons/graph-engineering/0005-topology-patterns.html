Lesson 0005 · Graph Engineering v2

체인에서 다이아몬드까지

노드와 엣지를 알았다고 그래프를 잘 그리는 건 아니다. 같은 부품으로 일곱 가지 다른 모양(토폴로지)을 만들 수 있고, 그 모양이 곧 비용과 지연을 결정한다.

오늘의 한 줄 답: 실행 그래프의 형태는 Chain · Router · Diamond(Map-reduce) · Pipeline · Barrier · Bounded cycle 7가지로 좁혀진다. 팬아웃(fan-out)한 뒤 코드로 합치고(reduce) 판단이 필요한 곳에서만 다시 모델을 부르는(synthesize) 다이아몬드가 가장 많이 재사용되는 모양이고, 배리어(barrier)는 전체 결과가 꼭 필요할 때만 쓰는 값비싼 선택이다.

그림 1. 위: 6가지 토폴로지 미니 카드. 가운데: 다이아몬드(fan-out→reduce→synthesize). 아래: barrier와 pipeline의 시간축 비교.

1. 왜 "다음 단계"마다 배리어를 세우면 느려지는가

Codez(@0xCodez)의 글은 여기서부터 시작한다: parallel()은 배리어다 — 모든 작업이 끝날 때까지 기다린 뒤에야 다음 단계가 시작된다. 반면 pipeline()은 각 아이템이 모든 단계를 독립적으로 통과한다. 아이템 A가 3단계에 있는 동안 아이템 B는 아직 1단계일 수 있다. 빠른 아이템은 느린 아이템 뒤에서 기다리지 않고 먼저 끝난다.

원문의 판단 기준은 단순하다: 기본값은 pipeline()이고, 어떤 단계가 정말로 "전체 결과가 다 모여야만" 의미가 있을 때만 배리어를 쓴다. 예를 들어 전체 소스를 다 모은 뒤 중복을 제거하는 단계는 배리어가 맞다. 그냥 리스트를 펼치는 것뿐이라면 배리어 없이 코드로 처리한다.

Chain

A→B→C. 각 노드가 정확히 하나의 입력을 받아 하나의 출력을 다음에 넘긴다. 가장 단순하지만 하나가 죽으면 전체가 멈춘다.

Router

노드가 상태를 분류하면(모델의 판단), 그 분류 결과에 따른 분기 자체는 코드의 if/switch가 결정한다. "판단은 모델, 라우팅은 코드"가 원칙.

Diamond / Map-reduce

Split → 병렬 워커 → reduce(코드) → synthesize(모델). 시장 조사, 경쟁사 감사, 코드 리뷰가 모두 이 골격을 재사용한다.

Bounded cycle

결과가 새로 나오지 않는 라운드가 K번 연속될 때까지 반복(loop-until-dry). 중복 제거는 반드시 "지금까지 본 모든 것" 기준이어야 한다.

2. 엣지는 공짜, 에이전트는 비싸다

Codez의 실천 규칙: reduce 단계에서 하는 일이 단순히 "펼치고 중복 제거하기(flatten + dedupe)"라면, 그건 에이전트 노드가 아니라 그냥 코드 한 줄이어야 한다. "결과를 합쳐줘"라고 또 다른 에이전트를 부르고 싶은 유혹을 원문은 명시적으로 경계한다 — "모든 엣지가 에이전트인 그래프는 자기 배선에 임대료를 내는 그래프다." 판단이 필요한 합성(synthesize)에만 모델을 쓰고, 기계적인 병합은 코드에 맡긴다.

3. 순환은 반드시 수렴 조건이 있어야 한다

발견의 크기를 미리 모르는 작업(버그 스윕, 미지 범위 리서치)에는 순환(cycle)이 필요하다. Codez가 제시하는 안전한 패턴은 loop-until-dry: 새로운 발견이 없는 라운드가 연속 K번이면 멈춘다. 여기서 거의 모두가 처음에 저지르는 실수는 "확인된 결과"만 기준으로 중복 제거하는 것이다. 그러면 기각됐던 발견이 매 라운드 다시 등장해 루프가 절대 마르지 않는다. 지금까지 "본" 모든 것(확인 여부와 무관하게)과 비교해야 한다.

4. 토폴로지가 곧 비용과 지연이다

같은 작업도 그래프 모양에 따라 완전히 다른 비용 곡선을 그린다. Barrier가 많을수록 가장 느린 노드가 전체 지연을 결정하고, cycle이 수렴하지 않으면 비용이 무한정 누적된다. Codez의 결론은 "형태(topology)가 비용과 지연을 결정하는 가장 큰 지렛대"라는 것 — 알고리즘이나 프롬프트를 고치기 전에 그래프 모양부터 점검하라는 뜻이다.

5. 실제로 무엇을 쓸 수 있는가 — 검증된 범위만

Codez의 글은 특정 CLI 도구(Claude Code)의 agent()/parallel()/pipeline() 같은 이름을 실제 존재하는 공식 기능처럼 구체적인 코드로 제시한다. 검증한 결과는 다음과 같다:

주장검증 결과
Claude Code에 dynamic workflows 기능이 있고 agent()/parallel()/pipeline()을 스크립트에서 쓴다검증됨 공식 문서(code.claude.com/docs/en/workflows)와 Agent SDK reference가 명시. 단, 이는 Claude Code Workflow tool의 스크립트 샌드박스 안에서만 쓰는 전용 primitive이지 범용 JS 전역 API가 아니다.
동시에 수백 개 에이전트를 무제한 병렬로 돌린다오해 소지 공식 런타임 제한은 최대 16개 동시 실행(머신에 따라 더 적을 수 있음), run당 총 1,000개 에이전트까지다. "수백 개"는 총량이지 동시성이 아니다.
중단된 workflow는 어느 세션에서든 이어 실행된다오해 소지 공식 문서는 같은 세션 안에서만 resume 가능하다고 명시한다. 세션이 끝나면 새 세션은 처음부터다. LangGraph의 영속 checkpointer와 같은 durable runtime으로 동일시하면 안 된다.
실무 번역: 이 레슨을 만드는 과정 자체가 다이아몬드였다. 245개 X 북마크 중 관련 원문을 찾는 리서치는 fan-out(병렬 읽기), 4개 종합 노트와 근거 검증표를 만드는 것은 각각 독립된 워커, 그리고 지금 이 레슨을 실제 HTML로 합성하는 단계만 사람(또는 단일 저자 에이전트)이 담당하는 synthesize였다. Aside의 서브에이전트 병렬 호출도 같은 원칙을 따른다 — 읽기는 병렬로 fan-out하고, 최종 산출물 작성은 한 곳에서.
