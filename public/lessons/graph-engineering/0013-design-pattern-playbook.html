Reference 0013 · Graph Engineering v2

그래프 설계 한 장 플레이북

새 자동화를 그래프로 설계하기 전에, 혹은 설계 리뷰 자리에서 바로 인쇄해 체크하는 실전 시트. 12개 예/아니오 체크, 8개 패턴 카드, 실패→처방 표, 인간 게이트 배치 기준, 마지막 워크시트로 구성했다.

1. 설계 전 12개 체크 (예/아니오)

  • 1. 노드가 존재 자격이 있는가
    다른 모델, 다른 툴셋, 다른 역할(예: read-only reviewer)인가. 아니면 기존 노드에 inline해도 되는가.
  • 2. 엣지에 실제 데이터가 흐르는가
    “그리고 나서”가 아니라 이전 노드의 출력이 다음 노드의 입력으로 실제로 쓰이는가.
  • 3. state schema와 writer가 정해졌는가
    어떤 노드가 어떤 필드를 읽고 쓰는지, 병렬 쓰기 충돌을 어떻게 merge하는지.
  • 4. deterministic routing이 가능한가
    체크 가능한 조건은 코드로 라우팅하고, 모델은 진짜 판단이 필요한 곳에만 쓴다.
  • 5. barrier가 정말 필요한가
    전체 집합이 있어야만 하는 단계인가, 아니면 pipeline으로 스트리밍해도 되는가.
  • 6. cycle의 종료 조건이 있는가
    수렴 기준(예: K회 연속 무소득)과 “지금까지 본 전체”against dedupe가 있는가.
  • 7. judge가 산출물보다 먼저 정의됐는가
    “무엇이 통과인가”를 기계가 판정할 수 있는 형태로 먼저 만들었는가.
  • 8. reviewer가 독립 context인가
    작성자의 추론을 보지 않고, 산출물+rulebook만 보는 fresh session인가.
  • 9. side effect가 idempotent한가
    체크포인트 이후 재실행되거나 재시도돼도 같은 결과가 두 번 발생하지 않는가.
  • 10. checkpoint 의미를 정확히 아는가
    “정확히 중단 지점부터”가 아니라 “노드 처음부터 재실행” 또는 “같은 세션 내 resume”임을 구분했는가.
  • 11. 현실 anchor가 있는가
    그래프 내부 지표만 서로 확인하는 원형 확증이 아니라, 실제 행 수·테스트·입금 같은 외부 근거가 연결됐는가.
  • 12. 그래프를 안 쓰는 쪽이 더 단순한가
    한 번뿐인 일, 아직 모르는 경로, 기계 심판 부재, 냅킨에 못 그리는 복잡도라면 loop나 workflow만으로 충분한지 재검토했는가.

2. 패턴 카드 8종

실행

Chain

순차 의존. 가장 단순하지만 한 단계가 막히면 전체가 멈춘다.

실행

Router

코드 조건이 분기를 결정. 모델은 분류만, 라우팅은 결정론적으로.

실행

Diamond (fan-out/fan-in)

split→병렬 작업→merge. 가장 흔한 워크호스 토폴로지.

실행

Pipeline vs Barrier

기본은 pipeline(스트리밍). 전체 집합이 꼭 필요한 단계만 barrier.

실행

Bounded cycle

K회 연속 무소득이면 종료. 전체 이력 대상 dedupe 필수.

개선

Verification loop

작성자와 다른 context의 judge. 자기 숙제 자기 채점 금지.

실행

One-writer

여러 reader는 병렬, 최종 쓰기는 한 노드만. 병합 소유자를 명시.

지식

Temporal graph

사실을 지우지 않고 무효화. 현재/과거 진실을 나란히 질의.

3. 실패 → 처방 표

증상먼저 볼 레이어처방
지표는 좋아지는데 실제 결과는 나빠짐개선 그래프counter-metric 추가, audit loop로 외부 anchor 연결(Goodhart 대응)
루프가 자기 상위 목표를 점검할 수 없음개선 그래프Hierarchy — 느린 루프가 빠른 루프의 reference를 소유
두 자동화가 서로 다른 목표로 충돌개선 그래프Arbitration — 상위 meta-loop가 트레이드오프 결정
같은 실패가 여러 파일에서 반복실행 그래프개별 수정 대신 rulebook에 규칙 한 줄 추가 후 배치 재생성
노드 하나 실패가 전체를 멈춤실행 그래프파티셔닝/격리 — 실패를 해당 노드에 가두고 결과만 null 처리
재시작해도 진행상황이 사라짐실행 그래프state를 디스크에, checkpoint 의미(재실행 vs resume)를 정확히 설계
“완료”라고 했는데 실제로 검증되지 않음실행 그래프judge를 산출물보다 먼저 정의하고 일부러 깨서 검증
“지난달 담당자가 누구였나” 같은 질문에 답 못함지식/시간 그래프valid_from/valid_to를 가진 temporal edge 도입
단 한 번뿐인 작업에 며칠을 설계에 씀없음(그래프 과잉)더 단순한 loop나 수작업으로 되돌리기

4. 인간 게이트 배치 — blast radius 기준

낮음

자동 진행

읽기 전용 조사, 초안 생성, 내부 로그 기록처럼 되돌리기 쉬운 작업.

중간

사후 검토

파일 수정, 내부 상태 변경 — 배치로 모아 사람이 diff를 검토.

높음

사전 승인 필수

발송, 결제, 외부 API 쓰기, 삭제 — 반드시 human gate 뒤에 둔다.
