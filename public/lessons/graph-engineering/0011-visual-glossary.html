Reference 0011 · Graph Engineering v2

시각 글로서리

"그래프 엔지니어링"이라는 한 단어 아래 섞여 있는 네 가지 구조 — 개선(governance), 실행(orchestration), 지식(temporal), 문제(decomposition) — 의 용어를 색으로 분리해 정리한다. 레슨을 읽다 막히면 여기로 돌아온다.

판별 질문 하나로 시작: "이 그래프의 노드는 무엇을 하는가?" — 통제 루프를 감시하면 개선, 작업을 실행하면 실행, 사실/관계를 저장하면 지식, 아직 실행되지 않는 질문이면 문제 그래프다.

개선 루프 거버넌스 그래프 용어

출처: Carlos E. Perez, "From Loop Engineering to Graph Engineering?" (관점/입력 자료) — 레슨 0002-0003 참고.

Control loop (통제 루프)
현재 값을 목표 기준과 비교해 차이를 줄이는 자기 반복 시스템. 온도조절기, PDCA, OKR, ML 훈련 루프가 모두 이 구조다.
Control / Reference / Gap / Act
루프의 4행정: 현재 상태를 관측(Control) → 목표와 비교(Reference) → 차이 계산(Gap) → 행동으로 좁힘(Act). 이 네 조각이 루프의 최소 단위다.
Goodhart (지표 왜곡)
지표가 목표가 되는 순간 지표는 더 이상 좋은 목표가 아니게 되는 현상. 루프가 지표는 개선하지만 실제 목적은 나빠질 수 있다.
혼동 주의: 루프가 고장난 것이 아니라 루프가 설계대로 완벽히 작동해서 생기는 실패다.
Blindness upward (위쪽 맹목)
루프가 자신의 Reference(목표값) 자체가 틀렸는지는 검증할 수단이 없는 구조적 한계. 빠른 루프일수록 심하다.
Loop conflict (루프 충돌)
서로 다른 목표를 최적화하는 두 루프가 같은 자원이나 지표를 두고 반대로 당기는 상태. 조정하는 상위 루프가 없으면 진동한다.
Measurement decay (측정 부패)
센서·로그·리포팅 경로 자체가 서서히 현실과 어긋나는데도 루프는 그 측정값을 계속 신뢰하는 실패. ERP 일배치가 "성공"을 보고하지만 실제 삽입 행이 0건인 사례가 전형적이다.
Pairing (짝짓기)
최적화 루프 옆에 그 루프를 감시하는 별도의 거울 루프를 짝지어 Goodhart를 방지하는 토폴로지.
Hierarchy (계층)
느린 상위 루프가 빠른 하위 루프의 Reference(목표) 자체를 소유하고 주기적으로 갱신하는 구조. Blindness upward의 처방.
Arbitration (중재)
서로 충돌하는 두 루프의 목표를 상위 메타 루프가 트레이드오프로 결정하는 구조. Loop conflict의 처방.
Audit (감사)
운영 루프와 독립된 별도 루프가 실제 데이터를 표본 조사해 측정 경로 자체의 신뢰성을 점검하는 구조. Measurement decay의 처방.
Anchor (앵커) / Frozen rule (동결 규칙)
어떤 루프도 스스로 수정할 수 없는 외부 기준값 또는 규칙. 은행 입금 확인, 실제 테스트 통과, 사람의 최종 승인처럼 그래프 바깥에서 와야 한다.
혼동 주의: 그래프(토폴로지)를 잘 그려도 모든 루프가 서로의 대시보드만 보고 있으면 원형 확증(circular confirmation)에 빠질 수 있다. 진짜 축은 loop vs graph가 아니라 grounded vs ungrounded다.

실행 오케스트레이션 그래프 용어

공식 근거: LangGraph, Microsoft Agent Framework, Google ADK, Claude Code 공식 문서 — 레슨 0004-0007 참고.

Node (노드)
한 가지 일만 하는 작업 단위 — 함수, LLM 호출, 특화 서브에이전트, 사람 승인 단계 중 하나. 노드 자격은 "다른 모델/도구/역할이 필요한가"로 판단한다.
Edge (엣지)
한 노드의 출력이 다른 노드의 입력으로 실제로 흘러가는 관계.
혼동 주의: "그리고 나서"는 엣지가 아니다. 다음 단계가 이전 단계의 출력을 읽지 않으면 엣지가 아니라 그냥 실행 순서일 뿐이다.
State (상태) / Contract (계약)
그래프 전체가 공유하는 타입이 있는 객체. 각 노드가 어떤 필드를 읽고 쓸 수 있는지가 계약이며, 계약이 없으면 어떤 노드도 안전하게 교체할 수 없다.
Router (라우터)
이전 노드의 결과를 코드로 검사해 다음에 실행할 edge를 결정하는 노드. 판단은 모델이, 라우팅 자체는 코드가 담당하는 편이 재현 가능하다.
Fan-out / Fan-in
하나의 입력을 여러 독립 노드로 병렬 분배(fan-out)한 뒤, 전체 결과가 모였을 때만 진행하는 합류 지점(fan-in).
Diamond (다이아몬드)
분할(split) → 병렬 작업(fan-out) → 합류(reduce) → 종합(synthesize)의 표준 실행 그래프 형태. 시장조사·코드리뷰·리서치 리포트가 대부분 이 모양이다.
Pipeline vs Barrier
Pipeline은 각 아이템이 단계를 독립적으로 통과해 빠른 아이템이 먼저 끝나고, Barrier는 전체 집합이 모일 때까지 다음 단계를 막는다. 전체 집합이 필요한 경우(중복 제거, 전수 비교)만 barrier를 쓴다.
Bounded cycle (제한된 순환)
탐색 범위를 미리 알 수 없을 때 되돌아가는 edge를 두되, "K번 연속 새로운 게 없으면 종료"처럼 명시적 수렴 조건을 반드시 둔 순환.
Checkpoint / Durable execution
그래프 상태를 super-step 경계마다 저장해 재개·중단·time-travel을 지원하는 메커니즘.
혼동 주의: 재개는 대부분 중단된 노드 함수를 처음부터 다시 실행하는 것이지, 명령어 단위로 이어지는 것이 아니다. 그래서 Idempotency가 필요하다.
Idempotency (멱등성)
같은 노드가 같은 입력으로 두 번 실행돼도 부작용이 한 번만 일어나는 성질. 재시도·재개가 있는 그래프에서는 필수다.
One-writer rule (단일 쓰기자 원칙)
읽기는 여러 노드가 병렬로 해도 안전하지만, 같은 자원에 대한 쓰기는 한 노드(또는 격리된 worktree)만 담당해야 충돌·오염을 막을 수 있다.
Human gate (사람 승인 게이트)
비가역적이거나 비용이 큰 edge 직전에 사람의 명시적 승인을 요구하는 노드. blast radius(영향 범위)가 클수록 게이트를 앞에 둔다.

지식 / 시간 그래프 용어

공식 근거: Microsoft GraphRAG, Graphiti 공식 문서 — 레슨 0008-0009 참고. "18%/85%" 같은 X 수치는 특정 도메인 논문 결과이며 일반화하지 않는다.

Entity / Relation / Triple
지식 그래프의 최소 단위. Subject → Relation → Object 형태로 저장되는 명시적 사실. "Anthropic → created → Claude"가 한 예다.
Ontology / Schema
어떤 엔티티 타입과 관계 타입이 허용되는지 미리 정의한 설계도. 스키마 없이 추출하면 같은 개념이 다른 이름으로 중복된다.
Entity resolution (엔티티 해상도)
"Microsoft Corp"와 "MSFT"처럼 서로 다른 표기가 같은 실체를 가리키는지 판단해 정규화(canonical name)하는 과정.
Provenance / Confidence
어떤 사실이 어느 문서/발화에서 왔는지(provenance)와 얼마나 확실한지(confidence)를 사실 자체에 함께 저장하는 것. 감사와 모순 해결에 필수다.
Temporal edge / valid_from·valid_to
사실이 참이었던 시간 구간을 엣지에 함께 저장하는 방식. Graphiti는 사실이 바뀌면 지우지 않고 무효화(invalidate)해 "2월에는 누가 계좌 소유자였나"에 답한다.
Community / Community report
GraphRAG가 그래프를 Leiden 알고리즘으로 군집화(community)한 뒤, 각 군집을 요약한 문서(report). Global search의 재료가 된다.
Local search
특정 엔티티와 그 이웃 관계를 확장해 답하는 질문 유형. "이 거래처의 최근 계약은?" 같은 구체적 질문에 맞다.
Global search
전체 데이터셋의 테마나 패턴을 community report들을 map-reduce해 답하는 질문 유형. "전체 공급망의 주요 리스크 패턴은?" 같은 질문에 맞다.
DRIFT search
Local과 Global을 혼합해, global 커뮤니티 컨텍스트로 시작한 뒤 local 세부사항으로 좁혀가는 GraphRAG의 하이브리드 검색 방식.

문제 분해 트리 용어

공식 근거: McKinsey 문제해결 자료(느슨한 1차 근거) — 레슨 0001, 0010 참고. Why/What/How 3분류는 유용한 교수용 taxonomy이지 McKinsey의 공식 표준 3종이라고 확정된 것은 아니다.

Issue tree (이슈 트리)
큰 문제를 실행 가능한 하위 질문으로 나누는 정적 분해 구조. 노드는 "질문"이며, 상태·스케줄링·체크포인트를 가진 실행 런타임이 아니다.
혼동 주의: 트리 모양이 실행 그래프와 비슷해 보여도 돌지 않는다 — 사람이 채워 넣는 계획 문서에 가깝다.
Why / What / How tree
원인을 찾는 Why-tree, 필요한 작업을 나열하는 What-tree, 가능한 실행 경로를 나열하는 How-tree로 나누는 교수용 분류. 어떤 답이 필요한지에 따라 골라 쓴다.
MECE (Mutually Exclusive, Collectively Exhaustive)
같은 레벨의 가지들이 서로 겹치지 않고(mutually exclusive) 빠짐없이(collectively exhaustive) 문제를 덮어야 한다는 구조적 원칙.
혼동 주의: MECE는 명료함을 위한 설계 원칙이지, 현실의 인과관계를 완전하게 증명하는 formal verifier가 아니다.
Hypothesis (가설)
Why-tree의 최종 산출물. 검증 가능한 원인 후보 목록이며, 다음 단계는 데이터로 각 가설을 반증하거나 채택하는 것이다.
Workplan (작업계획)
What-tree의 최종 산출물. 분석/결정/합의/종합으로 나뉜 실행 순서가 있는 계획. 여기서부터 실행 그래프로 넘어갈 수 있다.
