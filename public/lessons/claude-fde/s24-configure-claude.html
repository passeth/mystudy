장면 2 · 메모 한 장의 원리 (약 30초)

장면 3 · 남길 줄, 뺄 줄 (약 40초)

내레이션: 기준은 질문 두 개예요. 코드를 읽으면 찾을 수 있나요? 실제로 찾아볼까요? 둘 다 그렇다면 빼요. 남는 건 확인 명령, 오해하기 쉬운 곳, 저장소에 없는 결정 같은 것이에요.

장면 4 · 두 종류의 지시 (약 35초)

## 핵심 정리

세 장만 기억해요

CLAUDE.md는 새로 온 동료의 책상에 붙여 두는 메모 한 장과 같아요. 한 장일 때는 다 읽지만, 열 장이 되면 중요한 줄이 묻혀요. S21에서 CLAUDE.md가 무엇인지 봤으니, 오늘은 "Claude가 실제로 따르는" 설정으로 다듬어요.

01

줄이는 기준: Claude가 볼 수 없는 것만

CLAUDE.md는 매 세션에 통째로 로드돼요. 그래서 모든 줄이, 관계없는 작업에서도 Claude의 주의를 조금씩 가져가요. 공식 문서가 권하는 시험은 질문 두 개예요. 코드를 읽으면 찾을 수 있나? 실제로 찾아볼까? 둘 다 "예"면 빼요. 남길 것은 이런 줄이에요.

  • 이 저장소에서 작업을 확인하는 명령: 테스트, 타입체크, 린트, 파일 하나만 테스트하는 법
  • 코드가 오해를 부르는 곳: 곳곳에 있지만 새 코드가 따라 하면 안 되는 옛 패턴
  • 저장소에 없는 결정: 배포 방식, 리뷰가 필요한 변경
  • 이미 두 번 고쳐 준 것
# Commands
- Run one test file: pnpm vitest run path/to/file.test.ts
- Typecheck: pnpm tsc --noEmit

# Conventions
- src/legacy/ is still live but don't copy its patterns into new code

# Gotchas
- Integration tests need DATABASE_URL set, see .env.example

(공식 문서의 예를 줄인 거예요.) 길이는 파일당 200줄 미만이 목표예요. /init으로 초안을 만들면 그 뒤의 일은 대부분 줄을 지우는 거예요. /doctor는 코드에서 알 수 있는 내용을 덜어내자고 제안하고, /doctor prompt-audit은 낡았거나 서로 부딪치는 지시를 찾아 줘요. 파일이 실제로 로드됐는지는 /context all로 확인해요. 어떤 줄을 계속 놓친다면 IMPORTANT를 덧붙일 게 아니라 파일을 줄이거나 그 줄의 자리를 옮겨요.

02

지시를 둘 자리 고르기

지시는 두 종류예요. Claude가 읽고 판단하는 지시(비결정적)와 Claude Code가 반드시 실행하는 설정(결정적)이에요.

자리언제 적용되나누가 지키나맞는 내용
CLAUDE.md매 세션 로드Claude가 판단검증 명령, 핵심 관례
.claude/rules/매 세션. paths:를 붙이면 일치하는 파일을 다룰 때만Claude가 판단한 폴더나 언어에만 해당하는 규칙
skill설명만 늘 보이고, 본문은 호출되거나 관련 있을 때 로드Claude가 판단여러 단계 절차, 참고 자료
hook정해진 이벤트마다Claude Code가 강제예외 없는 단계(편집 뒤 포매터)
settings의 권한 규칙도구를 호출할 때마다Claude Code가 강제읽기나 실행 금지(.env 읽기 금지)

고르는 요령은 이래요. "거의 항상"이면 충분한 지침은 위 세 줄에, "한 번도 어기면 안 되는" 규칙은 아래 두 줄에 둬요. 반대도 마찬가지예요. 취향일 뿐인 것을 hook으로 걸어 놨다면 지우고 Claude에게 맡겨요.

파일 위치는 적용 대상도 정해요. ~/.claude/settings.json과 .claude/settings.local.json은 나에게만, 커밋한 .claude/settings.json은 그 저장소에서 일하는 모두에게, managed settings는 조직 전체에 적용돼요. hook과 권한 규칙을 쓰는 법은 S25에서 다뤄요.

03

반복 절차는 skill로, 첫 skill은 검증

같은 절차를 채팅에 세 번째 붙여 넣고 있다면 skill로 옮길 때예요. S22에서 본 대로 skill은 .claude/skills/<이름>/SKILL.md 파일이에요. 설명(description)만 매 세션 컨텍스트에 있고 본문은 쓸 때만 읽히니까, 긴 절차도 다른 작업에 부담을 주지 않아요. 릴리스처럼 부작용이 있는 절차에는 disable-model-invocation: true를 넣어서 사람이 /이름을 쳐야만 실행되게 해요.

왜 검증부터일까요? Claude는 일이 "끝난 것처럼 보일 때" 멈춰요. 통과인지 실패인지 돌려주는 검사가 있으면 Claude가 고치고, 돌리고, 다시 고치는 고리를 스스로 닫아요. Claude Code에는 번들 skill /verify가 있어요. 앱을 빌드하고 실행해서 변경이 실제로 동작하는지 확인하고, 통한 방법을 .claude/skills/verify/SKILL.md에 기록할 수 있어요. 또 세션을 시작할 때 프로젝트나 개인 위치에 verify라는 이름의 skill이 있으면, Claude Code의 커밋 지침이 커밋 직전에 그 skill을 실행하라고 Claude에게 알려 줘요(v2.1.286 이상, 문서나 테스트만 바꾼 경우는 제외).

직접 쓴다면 이런 모양이에요. 형식은 공식 문서를 따랐고 본문은 학습용 예시예요.

---
name: verify
description: 코드 변경을 마친 뒤 이 저장소의 검사를 실행하고 증거를 보고한다. 변경을 끝냈을 때와 커밋하기 전에 사용한다.
---
1. README에 적힌 테스트 명령을 실행한다.
2. 실패하면 출력을 읽고 고친 뒤 다시 실행한다.
3. 실행한 명령과 출력의 끝부분을 그대로 보고한다. "통과했다"는 말만 쓰지 않는다.

skill의 frontmatter와 여러 파일 구성은 S32~S34에서 깊이 다뤄요.

##오늘의 목표

  • CLAUDE.md에 남길 줄과 뺄 줄을 두 가지 질문으로 가를 수 있다.
  • 규칙 하나를 CLAUDE.md, rules, skill, hook, settings 중 맞는 자리에 놓고 이유를 말할 수 있다.
  • 반복하는 절차를 skill로 포장하고, 첫 skill로 검증 skill을 만드는 이유를 설명할 수 있다.

Q4(서술형) src/api/ 아래 파일을 고칠 때만 필요한 규칙이 열두 줄 있어요. 어디에 두고, 왜 그 자리가 CLAUDE.md보다 나은지 써 보세요.

.claude/rules/api.md를 만들고 frontmatter의 paths:에 src/api/** 같은 패턴을 적는다. 일치하는 파일을 다룰 때만 로드되므로, 관계없는 작업에서는 컨텍스트와 주의를 쓰지 않고 CLAUDE.md는 짧게 유지된다.

Q5(상황형) 고객사 리드 개발자가 말해요. "우리 CLAUDE.md가 600줄인데 Claude가 규칙을 자꾸 무시해요. 중요한 건 대문자로 다 강조해 놨는데도요." 무엇이 문제라고 설명하고, 어떤 순서로 고치자고 제안할까요?

예시 답 보기
문제는 강조가 부족해서가 아니라 길이와 자리다. 매 세션 600줄이 로드되면 줄마다 주의가 흩어지고, 대문자 강조는 규칙을 과하게 적용하게 만들 뿐이다. 순서는 (1) /doctor와 두 질문으로 코드에서 알 수 있는 내용을 지워 200줄 아래로 줄이고, (2) 특정 폴더용 규칙은 .claude/rules/에 paths:를 붙여 옮기고, (3) 긴 절차는 skill로 옮기고, (4) 예외가 없어야 하는 규칙은 hook이나 deny 규칙으로 옮긴다. 마지막으로 /doctor prompt-audit으로 서로 부딪치는 지시를 확인한다.
## FDE 관점

고객 저장소에 들어가서 첫 주에 하는 일 중 하나가 설정 정리예요.

고객팀이 이미 만든 CLAUDE.md가 길다면 함께 줄이고, 팀의 "작업을 확인하는 명령"을 찾아 검증 skill로 만들어 두면 이후의 긴 세션이 스스로 검사하며 굴러가요. .claude/settings.json과 .claude/skills/는 커밋하는 순간 그 저장소의 모든 사람에게 적용되니, 남의 저장소에서는 반드시 PR로 올려 고객 엔지니어의 리뷰를 받아요. 검증 skill이 확인하는 기준은 파일럿 계획과도 이어져요. "이 검사를 통과하면 완료"라는 합의가 곧 만들기 전에 정하는 성공 지표의 작은 판이에요. 그리고 어떤 규칙이 "예외 없음"인지 고객에게 물어 두면 S25에서 그 규칙을 hook과 deny 규칙으로 옮길 수 있어요.
