장면 1 · 오늘의 질문 (약 25초)

화면: 클로드 아이콘 앞에 공구 상자가 놓임. 상자 뚜껑에 물음표. 제목 "도구를 쥐여 준다는 건 정확히 무슨 뜻일까?"
내레이션: 클로드에게 도구를 붙인다는 말을 자주 들어요. 그런데 정확히 무엇을 주는 걸까요? 오늘은 도구 사용의 속을 들여다볼게요.

장면 2 · 계약 (약 40초)

화면: 가운데 계약서 한 장. 왼쪽 서명란 "나: 가능한 작업과 입출력의 모양", 오른쪽 서명란 "클로드: 언제, 어떻게 부를지". 계약서 아래에 화살표 세 개: "요청 → 실행 → 결과". "실행" 화살표만 클로드 바깥쪽 영역에 그려짐.
내레이션: 도구 사용은 계약이에요. 나는 어떤 작업이 가능한지 정해요. 클로드는 언제 부를지 정해요. 그리고 클로드는 요청만 해요. 실행은 언제나 모델 바깥에서 일어나요.

장면 3 · 도구 정의 세 요소 (약 40초)

화면: 명함 한 장이 확대됨. 세 줄: "이름: 주문 상태 조회", "설명: 무엇을, 언제", "입력: 주문 번호(글자)". 명함 뒷면에는 "구현 코드"가 있지만 클로드 쪽에서는 앞면만 보임.
내레이션: 도구는 명함 한 장으로 소개해요. 이름, 설명, 그리고 어떤 입력을 받는지예요. 클로드는 이 명함만 봐요. 뒷면에 있는 내 코드는 보지 못해요.

장면 4 · 설명이 가장 중요하다 (약 40초)

화면: 명함 두 장 비교. 왼쪽 "설명: 주문 조회" 아래에 갈팡질팡하는 화살표. 오른쪽 설명 네 줄 "무엇을 한다 / 언제 쓴다 / 입력의 뜻 / 돌려주지 않는 것" 아래에 곧은 화살표.
내레이션: 세 요소 중에 설명이 가장 중요해요. 무엇을 하는지, 언제 쓰고 언제 쓰지 않는지, 무엇은 돌려주지 않는지 적어요. 서너 문장은 써야 해요. 도구 설명도 프롬프트거든요.

장면 5 · 요청과 결과는 짝 (약 40초)

화면: 클로드에게서 쪽지가 나옴: "번호표 7 · 주문 상태 조회 · 주문 번호 에이 천일". 내 코드가 처리한 뒤 답 쪽지를 보냄: "번호표 7 · 배송 중, 내일 도착". 두 쪽지의 번호표가 반짝이며 이어짐.
내레이션: 클로드가 도구를 부르면 쪽지가 와요. 번호표, 도구 이름, 입력이 적혀 있어요. 내 코드는 실행한 뒤 같은 번호표를 붙여 결과를 돌려줘요. 번호표가 맞아야 짝이 이어져요.

장면 6 · 실패도 돌려준다 (약 35초)

화면: 내 코드가 주문 시스템을 두드리지만 "응답 없음". 답 쪽지 두 장 비교: 왼쪽 "실패" 한 단어에 엑스 표시, 오른쪽 "오류 · 주문 시스템 응답 없음 · 30초 뒤 다시 시도"에 체크 표시.
내레이션: 도구가 실패해도 결과는 돌려줘요. 오류라고 표시하고, 무엇이 잘못됐는지와 다음에 해 볼 일을 적어요. 그래야 클로드가 다시 시도할지, 사용자에게 알릴지 정할 수 있어요.

장면 7 · 어디서 실행되나 (약 45초)

화면: 세로 세 칸 표. 첫 칸 "내가 만든 도구 · 내 코드에서 실행", 둘째 칸 "앤트로픽이 모양을 정한 도구 · 내 코드에서 실행", 셋째 칸 "서버 실행 도구 · 앤트로픽 서버에서 실행". 셋째 칸에는 지구본(웹 검색) 아이콘.
내레이션: 도구는 실행되는 곳에 따라 세 종류예요. 내가 만든 도구는 내 코드에서 돌아요. 모양만 앤트로픽이 정해 둔 도구도 내 코드에서 돌아요. 웹 검색 같은 서버 실행 도구는 앤트로픽 쪽에서 돌고, 결과만 받아요.

장면 8 · 쓸 때와 안 쓸 때 (약 40초)

화면: 왼쪽 "도구가 필요": 메일 보내기, 오늘 재고, 정해진 칸의 표, 사내 시스템. 오른쪽 "도구가 필요 없음": 요약, 번역, 일반 지식. 오른쪽 아래에 "왕복이 늘면 느려진다".
내레이션: 도구는 글만으로 안 되는 일에 써요. 무언가를 실제로 바꾸는 행동, 오늘의 데이터, 모양이 정해진 출력이 그래요. 요약이나 번역에는 필요 없어요. 부를 때마다 왕복이 늘어서 느려지거든요.

장면 9 · 고객 앞에서 (약 35초)

화면: 회의실 그림. 고객 말풍선 "데이터베이스 권한을 통째로 주면 되죠?" 에프디이가 카드 두 장을 내밈: "주문 조회 · 읽기 전용", "배송 조회 · 읽기 전용". 뒤쪽에 흐릿한 카드 "기록 수정 · 승인 필요 · 다음 단계".
내레이션: 고객이 권한을 통째로 주자고 하면 이렇게 답하세요. 넓은 권한보다 좁은 도구가 안전하고 정확해요. 읽기 전용 도구 두어 개로 시작해요. 기록을 바꾸는 도구는 승인을 거치게 하고 다음 단계로 미뤄요.

장면 10 · 요약과 예고 (약 25초)

화면: 세 줄 요약이 한 줄씩 나타남: "1. 모델은 요청, 실행은 바깥 2. 설명이 도구의 품질 3. 좁은 도구부터". 아래에 "다음: S13 확장 사고".
내레이션: 정리할게요. 모델은 요청하고 실행은 바깥에서 해요. 도구의 품질은 설명이 정해요. 좁은 도구부터 시작해요. 다음 시간에는 클로드가 답하기 전에 깊이 생각하는 기능, 확장 사고를 볼게요.

도구> 글자 속으로 들어가 볼까요
## 핵심 정리

네 장만 기억해요

01

도구 사용은 계약이다

S11에서 루프가 도는 모양을 봤으니, 오늘은 그 안에서 오가는 도구예요. 도구 사용(tool use, 함수 호출이라고도 해요)은 내가 정의했거나 Anthropic이 제공하는 함수를 Claude가 부르게 하는 기능이에요. 공식 문서는 이걸 애플리케이션과 모델 사이의 계약이라고 설명해요. 나는 가능한 작업과 입출력의 모양을 정하고, Claude는 언제 어떻게 부를지를 정해요. 모델은 스스로 아무것도 실행하지 않아요. 구조화된 요청을 내놓을 뿐이고, 실행은 내 코드나 Anthropic 서버가 해요. S01에서 "도구로 받쳐 준다"고 했던 것의 실체예요.

02

도구 정의: 이름, 설명, 입력 스키마

도구 하나는 세 가지로 정의해요.

const tools: Anthropic.Tool[] = [
  {
    name: "get_order_status",
    description:
      "주문 번호로 현재 배송 상태를 조회한다. 사용자가 특정 주문의 배송이나 도착 여부를 물을 때 쓴다. 환불이나 결제 정보는 돌려주지 않는다.",
    input_schema: {
      type: "object",
      properties: {
        order_id: { type: "string", description: "주문 번호. 예: A-1001" },
      },
      required: ["order_id"],
    },
  },
];

Claude가 받는 건 내 코드가 아니라 이 정의와, 나중에 돌려주는 결과뿐이에요. 그래서 설명이 가장 중요하고, 공식 문서도 도구 성능에 가장 큰 영향을 주는 요소로 꼽아요. 좋은 설명에는 무엇을 하는지, 언제 쓰고 언제 쓰지 않는지, 각 입력의 뜻, 돌려주지 않는 것이 들어가요. 문서의 권장은 도구 하나에 서너 문장 이상이에요. 도구 설명도 프롬프트라서, S05의 설명(Description)이 그대로 적용돼요.

Claude가 도구를 부르면 응답에 id, name, input이 담긴 tool_use 블록이 와요. 내 코드는 실행한 뒤 tool_result 블록에 tool_use_id와 결과를 담아 돌려줘요. 실패했을 때도 돌려줘요. is_error: true를 붙이고, "실패" 한 단어 대신 "주문 시스템 응답 없음. 30초 뒤 다시 시도"처럼 무엇이 잘못됐고 다음에 무엇을 해 볼지 적어요.

03

어디서 실행되나: 세 종류

종류스키마를 정하는 쪽실행하는 쪽예
사용자 정의 도구나내 코드주문 조회, 사내 API 호출
Anthropic 스키마 도구Anthropic내 코드bash, text_editor, memory, computer
서버 실행 도구AnthropicAnthropic 서버web_search, web_fetch, code_execution

앞의 둘은 S11의 루프를 내 코드가 돌려요. 서버 실행 도구는 요청에 켜 두기만 하면 Anthropic 쪽에서 실행하고 결과가 응답에 담겨 와서, 내가 tool_result를 만들 일이 없어요. 웹 검색은 tools: [{ type: "web_search_20260209", name: "web_search" }] 한 줄로 켜요. 내장 도구는 S14에서 자세히 봅니다.

04

쓸 때와 쓰지 않을 때

도구가 맞는 일은 글만으로는 안 되는 일이에요.

  • 메일 보내기, 기록 수정처럼 실제로 무언가를 바꾸는 행동
  • 오늘 가격, 재고, 우리 DB처럼 학습 데이터 밖의 정보
  • 정해진 칸이 있는 JSON처럼 모양이 보장돼야 하는 출력
  • 사내 API, 파일 시스템 같은 기존 시스템 호출

요약, 번역, 일반 지식 질문처럼 모델이 혼자 답할 수 있는 일에는 도구가 필요 없어요. 부를 때마다 왕복이 한 번 늘어서, 가벼운 일에서는 오히려 느려져요.

##오늘의 목표

  • 도구 사용을 "모델은 요청하고, 실행은 바깥에서 한다"는 계약으로 설명할 수 있다.
  • 도구 정의의 세 요소(이름, 설명, 입력 스키마)를 쓰고, 좋은 설명의 조건을 말할 수 있다.
  • 도구를 실행되는 곳에 따라 세 종류로 구분하고, 도구가 필요한 일과 필요 없는 일을 가를 수 있다.

##확인 문제 고르면 바로 채점

Q1도구 사용에서 Claude가 실제로 하는 일은?

모델은 tool_use 블록으로 요청만 해요. 실행은 내 코드나 Anthropic 서버가 해요.

Q2공식 문서가 도구 성능에 가장 큰 영향을 준다고 꼽는 것은?

문서는 상세한 설명을 가장 중요한 요소로 꼽아요. 도구를 많이 붙이는 것(c)은 오히려 고르기 어렵게 만들고 컨텍스트를 차지해요.

Q3web_search 같은 서버 실행 도구의 특징은?

서버 실행 도구는 요청에 켜 두기만 하면 Anthropic 쪽에서 실행돼요. (a)는 사용자 정의 도구와 Anthropic 스키마 도구의 방식이에요.

Q4(서술형) 도구 실행이 실패했을 때 Claude에게 무엇을 어떻게 돌려줘야 하나요? 좋은 예와 나쁜 예를 하나씩 들어 보세요.

예시 답 보기
실패해도 tool_result를 반드시 돌려주고 is_error: true를 붙인다. 내용에는 무엇이 잘못됐는지와 다음에 무엇을 해 볼 수 있는지를 적는다. 좋은 예: "주문 시스템 응답 없음. 30초 뒤 다시 시도하세요." 나쁜 예: "실패". 나쁜 예로는 Claude가 다시 부를지, 다른 방법을 쓸지, 사용자에게 알릴지 판단할 근거가 없다. 그리고 Claude가 다시 시도할 수 있으니 재시도 횟수에 상한을 둔다.

Q5(상황형) 고객사 운영팀장이 말해요. "Claude한테 우리 ERP 데이터베이스 접속 권한을 통째로 주면 알아서 다 하겠죠?" 어떻게 답하고, 무엇을 제안할까요?

예시 답 보기
"Claude는 데이터베이스에 직접 들어가지 않고, 우리가 만들어 준 도구를 불러 달라고 요청만 해요. 그래서 무엇을 할 수 있는지는 우리가 도구로 정해요"라고 설명한다. 통째로 권한을 주는 대신, 업무에 필요한 조회를 좁은 도구 몇 개(예: 주문 조회, 재고 조회)로 만들고 읽기 전용 계정으로 연결하자고 제안한다. 기록을 바꾸는 작업은 사람의 승인을 거치는 도구로 따로 만들어 다음 단계에 넣는다. 도구 설명은 운영팀과 함께 쓰고, 호출 기록을 남겨 검토한다.
## FDE 관점

현장에서 "Claude가 무엇을 할 수 있나요?"라는 질문의 답은 결국 도구 목록이에요.

어떤 도구를, 어떤 권한으로 붙였는지가 파일럿의 실제 범위거든요. 그래서 FDE는 첫 출시 범위를 도구로 적어요. 예를 들어 "주문 조회와 배송 조회, 둘 다 읽기 전용"처럼요. 기록을 바꾸는 도구는 사람의 승인을 거치게 하고 다음 단계로 미뤄요. 도구 설명은 개발자 혼자 쓰지 말고 현장 담당자와 함께 쓰세요. "언제 쓰고 언제 쓰지 않는지"는 그 업무를 하는 사람이 가장 잘 알아요. 성공 지표도 도구에서 나와요. 불러야 할 때 부른 비율, 틀린 입력으로 부른 횟수를 기준선과 함께 재 두면 개선할 곳이 보여요.
