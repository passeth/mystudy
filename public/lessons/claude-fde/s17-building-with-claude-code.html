장면 1 · 오늘의 질문 (약 25초)

화면: 작업대 위에 부품 다섯 개가 흩어져 있음: "루프", "도구", "사고", "스킬", "컨텍스트 관리". 옆에 물음표와 제목 "이 부품을 다 조립하면 무엇이 될까?"
내레이션: 코스 다섯에서 부품을 하나씩 만들었어요. 루프, 도구, 사고, 스킬, 컨텍스트 관리예요. 이걸 다 조립하면 무엇이 될까요? 오늘은 그 답과 코스 전체를 정리해요.

장면 2 · 클로드 코드란 (약 35초)

화면: 흩어진 부품들이 가운데로 모여 하나의 상자로 조립됨. 상자에 "Claude Code" 이름표. 상자에서 네 방향으로 선이 뻗음: 터미널, 편집기, 데스크톱 앱, 브라우저.
내레이션: 답은 클로드 코드예요. 코드를 읽고, 파일을 고치고, 명령을 실행하는 코딩 에이전트예요. 우리가 배운 부품이 이미 조립돼 있어요. 터미널에서도, 편집기에서도 쓸 수 있어요.

장면 3 · 플랫폼 앱을 만드는 도구 (약 40초)

화면: 사람이 말풍선으로 "웹 검색을 추가해 줘"라고 말함. 상자 안에서 "계획", "코드 쓰기", "실행해서 확인" 세 단계가 차례로 켜짐. 폴더 속 파일 두 개에 수정 표시가 붙음.
내레이션: 클로드 코드는 플랫폼 앱을 만드는 도구이기도 해요. 만들고 싶은 걸 말로 설명하면 계획을 세워요. 여러 파일에 코드를 쓰고, 직접 실행해서 확인까지 해요.

장면 4 · 최신 설명서를 읽게 하기 (약 40초)

화면: 달력에 "지식 컷오프" 선. 선 오른쪽에 "새 모델 이름", "새 파라미터" 메모지가 붙어 있음. 상자가 책장에서 "Claude API 참고 자료" 책을 꺼내 펼치자 메모지 내용이 책으로 연결됨.
내레이션: 모델 이름이나 파라미터는 자주 바뀌어요. 그런데 모델의 지식에는 컷오프가 있죠. 그래서 클로드 코드에는 스킬이 하나 들어 있어요. 최신 에이피아이 참고 자료를 불러오는 스킬이에요. 기억이 아니라 설명서를 보고 쓰게 하는 거예요.

장면 5 · 프로그램 안에서 돌리기 (약 40초)

화면: 왼쪽에 대화 창 없는 터미널 한 줄이 실행되고 결과 문서가 나옴, 라벨 "한 번 실행". 오른쪽에 내 프로그램 상자 안에 작은 클로드 코드 상자가 들어감, 라벨 "라이브러리로 쓰기".
내레이션: 대화형으로만 쓰는 건 아니에요. 대화 창 없이 한 번 실행해서 스크립트에 넣을 수 있어요. 에이전트 에스디케이도 있어요. 같은 에이전트를 내 프로그램 안에서 돌려요.

장면 6 · 네 가지 길 (약 40초)

화면: 네 칸짜리 표가 한 줄씩 채워짐: "대화하며 개발: Claude Code", "내 앱에 넣기: Agent SDK", "API 직접 호출: Client SDK", "운영을 맡기기: Managed Agents". 오른쪽 열에 "누가 돌리나" 아이콘(노트북, 내 서버, 구름).
내레이션: 이제 길이 네 가지예요. 대화하며 개발하는 클로드 코드가 있어요. 내 앱에 넣는 에이전트 에스디케이도 있죠. 에이피아이를 직접 부르거나, 매니지드 에이전트에 운영을 맡길 수도 있어요. 누가 돌리느냐가 달라요.

장면 7 · 지도 앞부분 (약 40초)

화면: 가로로 긴 길 위에 표지판 세 개가 차례로 섬: "S10 첫 호출: 요청 하나, 응답 하나", "S11 루프: 도구를 부르는 동안 반복", "S12 도구: 요청은 클로드, 실행은 내 코드".
내레이션: 지도를 그려 볼게요. 처음엔 요청 하나에 응답 하나였어요. 그다음 도구를 부르는 동안 반복하는 루프를 만들었죠. 도구는 클로드가 요청하고 내 코드가 실행했어요.

장면 8 · 지도 뒷부분 (약 45초)

화면: 같은 길이 이어지며 표지판 네 개가 더 섬: "S13 사고: 답하기 전의 연습장", "S14 내장 도구와 스킬: 이미 있는 연장통", "S15 연결과 컨텍스트: 표준 콘센트, 책상 정리", "S16 매니지드 에이전트: 운영을 맡김".
내레이션: 사고는 답하기 전의 연습장이었어요. 내장 도구와 스킬은 이미 있는 연장통이고요. 엠씨피로 연결하고 컨텍스트를 정리했어요. 마지막으로 운영 자체를 맡기는 방법을 봤어요.

장면 9 · 고객 앞에서 (약 40초)

화면: 회의실 그림. 고객 말풍선 "매일 아침 가격 보고서가 필요해요." FDE가 지도 위에서 표지판 몇 개에 동그라미를 침. 아래에 "가장 단순한 단계부터 출시".
내레이션: 고객의 요청을 들으면 이 지도에서 필요한 조각을 골라요. 그리고 가장 단순한 단계로 풀리는 부분부터 출시해요. 설계는 지도로, 구현은 클로드 코드로 빠르게 해요.

내레이션: 정리할게요. 클로드 코드는 같은 부품으로 만든 완성품이에요. 에이전트를 만드는 길은 네 가지고, 가장 단순한 단계부터 시작해요. 다음 시간부터는 새 코스예요. 클로드 코드가 어떻게 일하는지 볼게요. 루프와 컨텍스트, 도구와 권한, 설치까지요.

## 핵심 정리

네 장만 기억해요

01

같은 부품으로 만든 에이전트

코스 5 내내 부품을 하나씩 조립했어요. 루프(S11), 도구(S12), 사고(S13), 내장 도구와 skill(S14), MCP와 컨텍스트 관리(S15)예요. Claude Code는 이 부품들이 이미 조립된 완성품이에요. 공식 문서는 "코드베이스를 읽고, 파일을 고치고, 명령을 실행하고, 개발 도구와 연결되는 에이전트형 코딩 도구"라고 소개해요. 터미널, IDE, 데스크톱 앱, 브라우저에서 써요. 그래서 코스 5의 개념이 그대로 통해요. Claude Code가 파일을 읽는 것은 도구 호출이고, 긴 작업에서 대화를 압축하는 것은 컨텍스트 관리예요.

02

Claude Code로 플랫폼 앱 만들기

Claude Code는 플랫폼 코드를 짜는 사람의 도구이기도 해요. 프로젝트 폴더에서 claude를 실행하고 만들고 싶은 것을 말로 설명하면, 계획을 세우고 여러 파일에 코드를 쓰고 실행해서 확인해요.

여기서 쓸모 있는 것이 기본으로 들어 있는 /claude-api skill이에요. 프로젝트 언어에 맞는 Claude API와 Managed Agents 참고 자료를 불러와요. 코드가 anthropic이나 @anthropic-ai/sdk를 import하면 Claude가 알아서 켜기도 해요. 모델 이름과 파라미터는 자주 바뀌는데 모델의 지식에는 컷오프(S02)가 있어서, 최신 자료를 읽고 쓰게 하는 게 중요해요. /claude-api managed-agents-onboard는 S16의 managed agent 만들기를 단계별로 안내해 줘요.

03

내 프로그램 안에서 Claude Code 돌리기

대화형으로만 쓰는 게 아니에요.

  • claude -p "질문": 대화 창 없이 한 번 실행하고 결과를 출력해요. 스크립트나 CI에 넣을 때 써요. --allowedTools로 허용할 도구를, --output-format json으로 출력 형식을 정해요.
  • Agent SDK: Claude Code를 라이브러리로 쓰는 방법이에요. Claude Code와 같은 도구, 에이전트 루프, 컨텍스트 관리를 Python과 TypeScript 코드에서 불러 써요.

이제 에이전트를 만드는 길이 네 가지가 됐어요.

하고 싶은 일쓰는 것누가 돌리나
터미널에서 대화하며 개발하기Claude Code CLI내 컴퓨터
Claude Code의 에이전트를 내 앱에 넣기Agent SDK내가 운영하는 프로세스
내 코드에서 Claude API를 직접 부르기 (루프는 직접 짜거나 Tool Runner)Client SDK (S10~S15)내 서버
Anthropic이 에이전트를 운영하게 하기Managed Agents (S16)Anthropic
import { query } from "@anthropic-ai/claude-agent-sdk";

// Claude Code의 에이전트 루프를 내 프로그램 안에서 돌려요
for await (const message of query({
  prompt: "이 폴더의 코드가 무슨 일을 하는지 다섯 줄로 요약해 줘.",
  options: { allowedTools: ["Read", "Glob", "Grep"] }, // 읽기 도구만 미리 허용
})) {
  if (message.type === "assistant" && message.message?.content) {
    for (const block of message.message.content) {
      if ("text" in block) console.log(block.text);
      else if ("name" in block) console.log(`[도구: ${block.name}]`);
    }
  } else if (message.type === "result") {
    console.log(`끝: ${message.subtype}`);
  }
}

실행하려면 npm install @anthropic-ai/claude-agent-sdk로 패키지를 먼저 설치해요. S11에서 손으로 짠 루프와 비교해 보세요. 도구 정의도 실행 코드도 없어요. 파일을 읽는 도구가 이미 들어 있기 때문이에요.

##확인 문제 고르면 바로 채점

Q1Messages API로 여러 턴의 대화를 이어 가는 방법은?

Messages API는 상태가 없어서 대화 기록 전체를 매번 보내요. 기록을 서버가 보관하는 건 S16의 세션이에요.

Q2직접 짠 에이전트 루프가 한 바퀴 더 돌아야 하는 신호는?

stop_reason이 tool_use면 Claude가 도구 결과를 기다리는 중이에요. 실행하고 tool_result를 돌려준 뒤 다시 요청해요.

Q3내가 정의한 커스텀 도구를 실제로 실행하는 것은?

커스텀 도구는 클라이언트 도구예요. Claude는 호출을 요청할 뿐이고 실행은 내 애플리케이션이 해요.

Q4사고(thinking)에 대한 설명으로 맞는 것은?

사고 토큰은 출력 토큰으로 청구되고 숨겨도 같아요. 깊이는 output_config.effort로 조절해요.

Q5"한 시간짜리 에이전트 작업이 뒤로 갈수록 앞의 내용을 놓친다"에 가장 직접 맞는 수단은?

압축은 오래된 대화를 요약으로 바꿔 자리를 만들고, 메모리 도구는 꼭 남겨야 할 것을 파일로 보존해요. 캐싱은 값과 속도만 바꾸고, max_tokens는 출력 상한이에요.

Q6"에이전트 루프와 샌드박스를 Anthropic이 운영하고, 세션 기록도 서버에 보관되는" 방식은?

Managed Agents는 하네스와 샌드박스를 Anthropic이 운영하고 세션이 기록을 보관해요. Agent SDK와 직접 짠 루프는 내가 운영해요.

Q7(서술형) S11에서 직접 짠 루프와 S16의 Managed Agents를 비교해, 각각을 고를 이유를 한 가지씩 적어 보세요.

직접 짠 루프는 매 단계를 내 코드가 통제하므로, 승인 절차나 기록 방식 같은 흐름을 원하는 대로 만들어야 할 때 고른다. Managed Agents는 루프와 샌드박스, 기록 보관을 Anthropic이 맡으므로, 오래 걸리는 작업을 인프라 없이 빨리 돌려야 할 때 고른다. (데이터 보관 요건이 엄격하면 직접 짠 루프 쪽이 맞을 수 있다는 점도 좋은 답이에요.)

Q8(서술형) Claude Code로 Claude API 코드를 짤 때 /claude-api skill이 왜 도움이 될까요? S02에서 배운 내용과 연결해 설명해 보세요.

예시 답 보기
모델은 학습 시점 이후의 변화를 모른다(S02의 지식 컷오프). API의 모델 이름, 파라미터, 베타 헤더는 그 뒤에도 바뀐다. /claude-api skill은 현재의 참고 자료를 컨텍스트에 불러와서, Claude Code가 기억이 아니라 자료를 보고 코드를 쓰게 한다.

Q9(상황형) 고객사 팀장이 말해요. "매일 아침 경쟁사 가격을 찾아서 엑셀 보고서로 만들고, 우리 사내 재고 시스템 숫자랑 비교해 주면 좋겠어요." 코스 5에서 배운 것 가운데 무엇을 어떻게 조합할지, 그리고 파일럿에서 먼저 출시할 부분을 제안해 보세요.

예시 답 보기
조합은 (1) 경쟁사 가격은 웹 검색·웹 페치(S14), (2) 엑셀 보고서는 xlsx skill과 코드 실행(S14), (3) 사내 재고 숫자는 커스텀 도구(S12)나 MCP 서버(S15), (4) 매일 아침 실행은 내 서버의 예약 작업에서 루프를 돌리거나 Managed Agents(S16)에 맡긴다. 먼저 출시할 부분은 사내 시스템 연동이 필요 없는 "경쟁사 가격 수집 + 엑셀 보고서"로 하고, 사람이 지금 만드는 보고서의 소요 시간과 오류를 기준선으로 잰다. 재고 비교는 연동 방식과 권한이 정해진 뒤 2단계로 붙인다. 가격처럼 정확해야 하는 값은 출처 도메인을 제한하고 표본을 사람이 확인한다.

Q10(상황형) 고객사 개발자가 말해요. "Claude Code가 써 준 API 코드에서 모델 이름이 틀려서 에러가 났어요. 이거 믿고 써도 되나요?" 어떻게 설명하고, 팀의 작업 방식으로 무엇을 제안할까요?

예시 답 보기
"Claude Code도 모델이라 학습 이후에 바뀐 이름을 틀릴 수 있어요. 그래서 기억 대신 최신 자료를 읽게 하고, 쓴 코드는 실행해서 확인하는 게 기본이에요"라고 설명한다. 제안은 (1) /claude-api skill이 켜진 상태로 작업하고, 모델 이름과 파라미터는 공식 문서에서 확인하게 지시한다. (2) "코드를 쓴 뒤 실제로 실행해 결과를 보여 줘"를 요청에 넣는다. (3) 사람이 변경 내용을 검토하고 테스트를 통과한 것만 반영한다. 믿을지 말지가 아니라 검증 절차를 갖추는 문제라고 정리한다.
## FDE 관점

공식 경로는 다음 코스의 Claude Code를 "고객의 저장소에서 프로토타입을 만드는 도구"라고 소개해요.

FDE의 하루로 보면 이래요. 코스 5의 지식으로 "이 유스케이스는 호출 한 번이면 되는지, 도구와 루프가 필요한지, 누가 운영할지"를 정하고, Claude Code로 고객 저장소에서 그 설계를 빠르게 작동하는 코드로 만들어요. 고객 개발자 앞에서 중요한 건 두 가지예요. Claude Code가 쓴 코드도 사람이 실행해서 확인한다는 것, 그리고 /claude-api skill처럼 최신 참고 자료를 읽게 해서 오래된 기억으로 쓰는 일을 줄인다는 것이에요. 파일럿 계획서의 "먼저 출시할 부분"은 한 장 지도에서 가장 단순한 단계로 풀리는 조각부터 고르면 돼요.
