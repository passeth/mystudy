장면 1 · 오늘의 질문 (약 25초)

화면: 서버 상자에 도구 카드 스무 장이 빽빽하게 꽂혀 있고, 모델 캐릭터가 머리 위에 물음표를 띄운 채 고르지 못함. 제목 "전부 도구로 만들면 될까?"
내레이션: 고객이 원하는 걸 전부 도구로 만들면 어떻게 될까요? 목록이 길어져서 모델이 고르기 어려워져요. 서버가 내줄 수 있는 건 도구만이 아니에요. 오늘은 나머지 둘을 볼게요.

장면 2 · 식당 비유 (약 40초)

화면: 식당 그림 세 칸. 주방에서 주방장이 국자를 집음("도구"), 테이블 위에 메뉴판이 놓임("리소스"), 손님이 손가락으로 세트 메뉴를 가리킴("프롬프트").
내레이션: 식당으로 생각해 볼게요. 도구는 주방장이 필요할 때 스스로 꺼내 쓰는 조리 기구예요. 리소스는 가게가 테이블에 올려 두는 메뉴판이에요. 프롬프트는 손님이 직접 고르는 세트 메뉴예요.

장면 3 · 누가 결정하나 (약 35초)

화면: 세 줄 표가 한 줄씩 나타남: "도구 ← 모델이 결정", "리소스 ← 앱이 결정", "프롬프트 ← 사용자가 결정". 각 줄 왼쪽에 로봇, 창문, 사람 아이콘.
내레이션: 셋을 가르는 기준은 기능이 아니에요. 누가 쓰기로 결정하느냐예요. 도구는 모델이 결정해요. 리소스는 앱이 결정해요. 프롬프트는 사용자가 결정해요.

장면 4 · 리소스는 주소로 찾는다 (약 40초)

화면: 문서함 서랍마다 주소표가 붙음: "docs://documents/report.md", "docs://documents/plan.md". 앱 창에서 주소 하나를 보내자 서랍이 열리고 문서가 앱으로 날아옴.
내레이션: 리소스는 주소가 있는 데이터예요. 이 주소를 유알아이라고 불러요. 앱이 주소를 보내면 서버가 그 내용을 돌려줘요. 도구처럼 일을 시키는 게 아니라, 읽기만 해요.

장면 5 · 빈칸이 있는 주소 (약 35초)

화면: 주소 "docs://documents/{doc_id}"에서 중괄호 부분이 깜빡임. 빈칸에 "plan.md", "report.md"가 번갈아 끼워지고 그때마다 다른 문서가 나옴. 옆에 "함수 하나가 모든 문서를 처리".
내레이션: 문서가 천 개면 주소도 천 개 적어야 할까요? 아니에요. 주소에 빈칸을 두면 돼요. 이걸 리소스 템플릿이라고 해요. 빈칸에 문서 이름을 넣으면 함수 하나가 모든 문서를 처리해요.

장면 6 · 같은 내용, 다른 길 (약 40초)

화면: 위쪽 길: 모델이 "읽어야겠다" 말풍선 → 도구 호출 → 문서. 아래쪽 길: 사용자가 입력창에 골뱅이 기호와 문서 이름을 침 → 앱이 문서를 바로 대화에 첨부. 두 길 끝의 문서는 같음.
내레이션: 문서 읽기는 도구로도 있고 리소스로도 있어요. 왜 둘 다 둘까요? 모델이 판단해서 읽을 때는 도구를 써요. 사용자가 이 문서라고 콕 집을 때는 앱이 리소스로 바로 가져와요. 도구 호출을 기다릴 필요가 없죠.

장면 7 · 프롬프트는 메시지 틀 (약 40초)

화면: 입력창에 슬래시를 치자 메뉴가 펼쳐짐: "문서 요약", "보고서 초안". "문서 요약"을 고르고 문서 이름 칸에 "plan.md"를 채우자, 긴 지시문이 완성되어 대화창에 들어감.
내레이션: 프롬프트는 사용자가 고르는 메시지 틀이에요. 서버를 만든 사람이 잘 쓰는 방법을 미리 적어 둔 거예요. 사용자는 메뉴에서 고르고 빈칸만 채워요. 그러면 완성된 지시문이 대화에 들어가요.

장면 8 · 고르는 질문 (약 35초)

화면: 갈림길 표지판. 맨 위에 질문 "누가 결정해야 하나?" 세 갈래: "모델이 판단 → 도구", "앱이나 사용자가 지목 → 리소스", "사용자가 작업을 시작 → 프롬프트".
내레이션: 무엇으로 만들지 헷갈리면 이 질문 하나만 하세요. 누가 결정해야 하나? 모델이 상황을 보고 판단해야 하면 도구예요. 사용자가 데이터를 지목하면 리소스예요. 사용자가 작업을 직접 시작하면 프롬프트예요.

장면 9 · 고객 앞에서 (약 35초)

화면: 파일럿 첫날 그림. 직원 다섯 명의 화면에 같은 메뉴 "보고서 초안"이 떠 있음. 아래에 "같은 시작 → 비교 가능한 결과".
내레이션: 현장에서 첫 사용자들은 무엇을 물어야 할지 몰라 멈추곤 해요. 서버가 프롬프트를 메뉴로 내주면 첫날부터 같은 방식으로 시작해요. 모두 같은 틀로 시작하면 결과를 비교하기도 쉬워요.

장면 10 · 요약과 예고 (약 25초)

화면: 세 줄 요약: "1. 도구는 모델, 리소스는 앱, 프롬프트는 사용자 2. 리소스는 주소로 읽는 데이터 3. 프롬프트는 고르는 메시지 틀". 아래에 "다음: S31 클라이언트 구현".
내레이션: 정리할게요. 도구는 모델이, 리소스는 앱이, 프롬프트는 사용자가 결정해요. 리소스는 주소로 읽는 데이터예요. 프롬프트는 골라 쓰는 메시지 틀이에요. 다음 시간에는 반대편, 클라이언트를 만들어 볼게요.

## 핵심 정리

네 장만 기억해요

01

서버가 내주는 세 가지, 결정하는 사람이 다르다

식당에 비유하면 이래요. 도구는 주방장이 필요할 때 스스로 꺼내 쓰는 조리 기구, 리소스는 가게가 손님 테이블에 미리 올려 두는 메뉴판, 프롬프트는 손님이 직접 고르는 세트 메뉴예요. 셋을 가르는 기준은 기능이 아니라 누가 쓰기로 결정하느냐예요.

종류결정하는 쪽무엇인가문서 서버의 예
도구(tool)모델모델이 불러서 일을 시키는 함수edit_doc으로 문장 고치기
리소스(resource)애플리케이션앱이 읽어서 모델의 컨텍스트에 넣는 데이터사용자가 문서를 @로 지목하면 내용 첨부
프롬프트(prompt)사용자사용자가 이름으로 고르는 메시지 틀"우리 양식으로 요약" 명령
02

리소스: 주소가 있는 데이터

리소스는 이름이 아니라 URI(주소)로 찾아요. 주소가 고정이면 그냥 리소스, 주소에 {빈칸}이 있으면 리소스 템플릿이에요. S29의 server.py에 이어서 붙여요.

@mcp.resource("docs://documents", mime_type="application/json")
def list_docs() -> list[str]:
    """문서 ID 목록."""
    return list(docs.keys())


@mcp.resource("docs://documents/{doc_id}")
def fetch_doc(doc_id: str) -> str:
    """문서 한 개의 내용."""
    return docs[doc_id]
  • 클라이언트는 resources/list(고정 주소)와 resources/templates/list(템플릿)로 목록을 받고, resources/read로 읽어요.
  • 함수는 목록을 볼 때가 아니라 읽을 때만 실행돼요.
  • {doc_id}와 함수 인자 이름이 다르면 서버가 시작할 때 바로 오류가 나요.

S29의 read_doc 도구와 내용이 겹쳐 보이죠? 결정하는 쪽이 달라요. 도구는 Claude가 "읽어야겠다"고 판단할 때 부르고, 리소스는 사용자가 문서를 지목했을 때 앱이 도구 호출 없이 바로 가져다 넣어요.

03

프롬프트: 사용자가 고르는 메시지 틀

@mcp.prompt(title="문서 요약")
def summarize_doc(doc_id: str) -> str:
    """문서를 우리 팀 양식으로 요약한다."""
    return (
        f"{doc_id} 문서를 read_doc 도구로 읽고 요약해 주세요. "
        "형식: 한 줄 결론, 근거 세 가지, 다음 할 일."
    )

돌려준 문자열은 사용자 메시지 한 개가 돼요. 클라이언트는 prompts/list로 목록을 받고 prompts/get으로 완성된 메시지를 받아요. 프롬프트 인자는 스키마 없이 전부 문자열이에요. 호스트는 보통 이걸 슬래시 명령이나 버튼으로 보여 줘요. S24에서 본 skill이 "Claude Code 안에서 절차를 포장하는 법"이라면, MCP 프롬프트는 "서버 쪽에서 잘 쓰는 법을 같이 내주는 법"이에요.

04

고르는 질문 한 가지

"이걸 쓰기로 누가 결정해야 하나?"

  • Claude가 상황을 보고 판단해야 한다 → 도구
  • 앱 화면에서 사용자가 지목하거나 앱이 자동으로 붙인다 → 리소스
  • 사용자가 "이 작업 시작"이라고 직접 고른다 → 프롬프트

##오늘의 목표

  • 리소스(resource)와 프롬프트(prompt)가 무엇이고 도구와 어떻게 다른지 설명할 수 있다.
  • 고정 URI 리소스와 리소스 템플릿을 구분하고, 문서 서버에 둘 다 추가할 수 있다.
  • "누가 쓰기로 결정하는가"를 기준으로 도구, 리소스, 프롬프트 중 하나를 고를 수 있다.

##직접 해 보기 5분

  • 위 코드를 server.py에 추가하고 uv run mcp dev server.py로 Inspector를 여세요. Resources 탭에서 docs://documents는 리소스 목록에, fetch_doc은 템플릿 쪽에 따로 나오는지 보세요. Prompts 탭에서 summarize_doc에 plan.md를 넣고 어떤 메시지가 만들어지는지 확인하세요.
  • S29에서 Claude Code에 docs 서버를 붙였다면 세션을 새로 열고 해 보세요. 입력창에 @를 쳐서 리소스가 파일과 함께 목록에 뜨는지, /를 쳐서 프롬프트가 명령으로 뜨는지 보세요(/mcp__docs__summarize_doc plan.md처럼 실행해요).

##확인 문제 고르면 바로 채점

Q1세 가지 중 "애플리케이션이 결정해서 쓰는 것"은?

리소스는 앱이 읽어서 컨텍스트에 넣는 데이터예요. 도구는 모델, 프롬프트는 사용자가 결정해요.

Q2docs://documents/{doc_id}처럼 주소에 빈칸이 있는 리소스에 대한 설명으로 맞는 것은?

템플릿은 resources/templates/list에 따로 나와요. 함수는 목록을 볼 때가 아니라 읽을 때만 실행돼요.

Q3MCP 프롬프트의 인자에 대한 설명으로 맞는 것은?

프롬프트 인자는 스키마 없는 문자열 목록이고, 사람이 채우는 양식이에요.

Q4(서술형) 문서 내용을 read_doc 도구로도, docs://documents/{doc_id} 리소스로도 내주는 이유를 "누가 결정하나"를 기준으로 설명해 보세요.

예시 답 보기
read_doc 도구는 Claude가 대화 흐름을 보고 "이 문서를 읽어야겠다"고 스스로 판단할 때 쓴다. 리소스는 사용자가 문서를 지목했을 때 앱이 도구 호출 없이 바로 내용을 가져와 컨텍스트에 넣을 때 쓴다. 내용은 같아도 결정하는 쪽이 달라서 둘 다 둔다.

Q5(상황형) 고객사 팀장이 요청해요. "직원들이 매주 '주간 보고서 초안' 작업을 똑같은 방식으로 시작했으면 좋겠어요. 그리고 Claude가 필요하면 지난주 보고서를 스스로 찾아봤으면 해요." 각각 무엇으로 만들지 제안해 보세요.

예시 답 보기
"같은 방식으로 시작"은 사용자가 고르는 것이므로 weekly_report_draft 같은 프롬프트로 만들어 메뉴에 띄운다. 양식과 순서를 프롬프트 문구에 넣는다. "Claude가 스스로 찾아본다"는 모델이 결정하는 것이므로 지난 보고서를 검색하거나 읽는 도구로 만든다. 사용자가 특정 보고서를 직접 붙이고 싶어 하면 보고서를 리소스로도 내준다. 파일럿에서는 프롬프트 하나와 읽기 도구 하나로 시작하자고 제안한다.
## FDE 관점

고객이 "Claude가 우리 시스템에서 이것도 하게 해 주세요"라고 할 때 전부 도구로 만들면, 도구 목록이 길어지고 Claude가 고르기 어려워져요.

오늘의 질문 하나로 요구 사항을 나눠 보세요. 사용자가 직접 지목하는 데이터는 리소스로, 팀이 반복하는 시작 문구는 프롬프트로 빼면 도구는 "모델이 판단해야 하는 행동"만 남아요. 프롬프트는 변화 관리에도 쓸모가 있어요. 첫 사용자 그룹은 무엇을 물어야 할지 몰라 멈추는 일이 많은데, 서버가 "요약", "보고서 초안" 같은 프롬프트를 메뉴로 내주면 첫날부터 같은 방식으로 시작할 수 있어요. 파일럿 성공 지표를 잴 때도 모두가 같은 프롬프트로 시작했다면 결과를 비교하기 쉬워요.
