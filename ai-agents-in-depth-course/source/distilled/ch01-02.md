# Chapter 1. Getting Started with AI Agents

## 1. 핵심 프레임워크와 정의

### 1.1 핵심 공식: Agent = LLM + Context + Tools
- **LLM = Reasoning Engine (추론 엔진)**: 의도 파악, 추론, 계획, 판단을 담당하는 의사결정 코어. 능력의 근원은 pre-training(세계 지식+언어 능력)과 post-training(의사결정 전략, SFT/RL은 Ch7).
- **Context = Working Set (작업 정보 집합)**: 매 의사결정 시점에 에이전트가 사용 가능한 정보 전체 — 환경, 사용자 메모리, 도메인 지식, 자기 상태, 태스크 진행 상황.
- **Tools = Action Interfaces (행동 인터페이스)**: 넓은 의미. 사전정의 tool call뿐 아니라 on-demand로 로드하는 Skills, 즉석 생성 코드, sub-agent 위임, 사용자에게 확인 요청, 외부 이벤트 응답까지 포함.
- RL 매핑(선택 읽기): LLM=Policy, Context=Observation Space, Tools=Action Space.
- 현대 에이전트의 세 특징: **open-ended action space**(고정 버튼이 아니라 임의 자연어/코드 생성), **internal reasoning**(행동 전 계획), **continuous interaction**(환경 피드백에 따른 전략 조정).
- 제품 사례 5종: Cursor(coding), Deep Research(search), Manus(computer control), Doubao(phone assistant), Pine AI(personal task/요금 협상).

### 1.2 Tools의 5가지 분류 (Ch4에서 심화)
1. **Perception Tools** — 정보 접근: 검색엔진, 파일시스템, API/DB.
2. **Execution Tools** — 외부 시스템에 작용: 코드 실행, 파일 조작, 시스템 명령, 외부 API.
3. **Collaboration Tools** — 다른 에이전트/사람과 분업: sub-agent 위임, human confirmation.
4. **Event Trigger Tools** — 에이전트가 호출하는 게 아니라 외부 입력이 에이전트를 깨움: 이메일 수신, 스케줄, Webhook.
5. **User Communication Tools** — 사용자와의 채널: 문자, 음성 전화, 이메일.

### 1.3 Tool Calling 4단계 (ReAct의 기초)
1. context가 사용 가능한 tool을 모델에 알림 (이름/용도/파라미터) → 2. 모델이 스스로 호출 여부/어떤 tool/인자 결정 → 3. framework가 실행하고 결과를 context에 append → 4. 모델이 결과를 보고 다음 행동 결정. **개발자는 tool 정의+실행만, 결정은 모델이.**
- 설계 원칙: 전용 tool 나열 대신 **범용 tool**(계산기 대신 Python code interpreter+sandbox, 메모 tool 대신 file read/write+virtual FS)을 주고 LLM에게 조합의 자유를.

### 1.4 Model as Agent 패러다임
- post-training(특히 RL)으로 tool calling을 모델 네이티브 능력으로 내재화하는 흐름. 그러나 **모델이 강해질수록 Harness가 더 중요해진다** — 모델의 의사결정 권한이 커질수록 잘못된 결정의 파급이 커져 더 정밀한 constrain/verify/correct이 필요.
- **Harness**: 모델 능력을 신뢰 가능한 태스크 실행으로 바꾸는 엔지니어링 인프라 (context 관리, tool 인터페이스, 안전 제약, 검증/교정).
- Bitter Lesson (Rich Sutton, 2019) 관점: 책의 입장은 "방향은 인정, 속도는 실용적으로(endorse the direction, stay pragmatic about the pace)". 모델이 Harness의 일부를 흡수해가는 건 맞지만 훈련 주기는 월 단위라 느리다. **모델의 현재 능력 경계가 바로 Harness가 가치를 만드는 자리.** Harness engineering은 Bitter Lesson에 대한 저항이 아니라 엔지니어링 시간축에서의 실천.
- RL이 내재화하는 것은 tool 그 자체가 아니라 **tool-calling decision policy(when/how to call)**. tool 실행은 여전히 framework/API 측 (Kimi의 web_search/code_runner는 서버측 Formula 스크립트 엔진).

### 1.5 에이전트 학습의 3가지 시간축 (Figure 1-1)
1. **In-context learning (추론 시)**: attention을 통한 soft update. 일시적·즉시 적응·context window 제약. (예: 예시 3개로 포맷 학습)
2. **Externalized learning (런타임)**: 지식베이스 문서, Prompt/Skill, 프로그램/Harness로의 외부 artifact 갱신. 영속적·갱신 가능·검증 가능. (예: workflow를 tool로 고정)
3. **Post-training (훈련 시)**: 파라미터 갱신. 영구적·범용·고비용·느림.
→ 상호 배타가 아니라 시간축이 다른 협조 메커니즘: context=즉시 적응, 외부 artifact=통제된 축적, 파라미터=명시 불가능한 능력의 내재화.

### 1.6 Context의 5요소 (API 관점)
1. **System Prompt** — 개발자 작성, 대화 낂내 고정. 에이전트의 "job description". 사용자 메모리(Ch3), 동적 환경 상태도 실림.
2. **Tool Definitions** — 이름/설명/파라미터 형식. system prompt와 함께 **static prefix** 구성. (2026년부터는 끝부분 on-demand 스키마 로딩도 가능 — Ch2/4)
3. **User Messages** — 사용자 입력 + RAG로 검색된 외부 지식.
4. **Assistant Messages** — 최대 3부분: reasoning(낶의 사고), content(답변), tool_calls(행동). tool 호출 시 보통 reasoning+tool_calls만, 최종 답변 시 reasoning+content만.
5. **Tool Results** — framework가 실행한 결과. 다음 추론의 직접 근거.
→ **Context = static prefix (1+2) + dynamic trajectory (3+4+5)**.

### 1.7 실험 1-1 (★★): Context 절제 연구 (Ablation Study)
- 방법: 완전 baseline + 구성요소 1개씩 제거한 4개 통제군 (system prompt는 정체성이라 제외).
- 결과: tool definitions 제거 → tool 호출 완전 불능 / tool results 제거 → 같은 tool 반복 호출 **무한루프(blind loop)** / reasoning 제거 → 연속 결정이 모순됨 / history 제거 → 이미 한 단계 반복.
- 핵심 통찰: **context가 결정 시점의 정보를 결정하고, 에이전트는 그 정보로만 결정할 수 있다.**

### 1.8 ReAct Loop
- ReAct = Reasoning + Acting, 실제로는 3단계: reason → act → observe 반복.
- **Agent context = static prefix + trajectory.** 매 LLM 호출은 완전한 trajectory를 받고, 응답이 다시 trajectory에 append (누적성, 구조화로 인한 해석/디버깅 용이).
- 다중통화 매출 집계 예시: 3회 iteration, 4회 tool call로 완료 (1R: 3개 환율 변환 병렬 호출 → 2R: code interpreter 집계 → 3R: 최종 답변).
- trajectory는 실행 기록 이상: **능력의 증거 데이터**. 대규모 분석 → 행동 패턴/더 나은 tool 설계, 지식베이스 증류, RL 훈련 데이터.

### 1.9 실험 1-2 (Kimi K3), 실험 1-3 (GPT-5.6)
- Kimi K3 (Moonshot AI, 2026): ~2.8조 파라미터 MoE, 1M token context, 네이티브 시각, 상시 thinking mode. RL로 tool-calling policy 내재화. **200-300회 연속 tool call을 일관된 추론으로 유지** (대부분 모델은 수십 회에서 성능 저하). K3 Max / K3 Swarm Max 두 변형. 오픈소스.
- GPT-5.6 (Sol/Terra/Luna 3종): **Freeform Tool Calling** — `type: "custom"` tool로 JSON 직렬화 없이 raw text(Python 코드, SQL)를 그대로 전달. API 파라미터 형식의 진화이지 모델 아키텍처 혁신은 아님. Verbosity, Reasoning Effort 파라미터. Responses API의 web search/code interpreter 내장 tool로 Deep Research를 서버측 클로즈드 루프로 실행. **intent clarification**: 실행 전 사용자 의도를 질문으로 먼저 확인 ("어느 데이터 소스? 어느 기술 지표?").

### 1.10 Harness Engineering = Model + Harness
- 확장 공식: **Agent = LLM + [Context + Tools + Constrain + Verify + Correct] = Model + Harness**.
- minimal formula = demo view, expanded formula = production view.
- 5대 기능과 설계 원칙:
  | 기능 | 책임 | 핵심 원칙 | 챕터 |
  |---|---|---|---|
  | Context | 충분한 정보 제공 | Information Sufficiency | Ch2-3 |
  | Tools | 행동 인터페이스 | Clear Interface | Ch4 |
  | Constrain | 행동 경계 | **Fail-Safe Defaults** (기본 꺼짐, 명시적 허용) | Ch4 |
  | Verify | 결과 정확성 판단 | **Input Isolation** (검증은 구조화 데이터만, 모델 자유 텍스트는 불신) | Ch5-6 |
  | Correct | 실패 복구 | 복구 불가 확정 전 중간 상태 비노출 (silent retry, circuit breaker) | Ch2, 5 |
- 경계 예시: 환불 정책을 context에 넣는 것=Context, 환불액이 주문총액 안 넘는지 검사=Constrain, API 호출=Tools, 타임아웃 재시도=Correct.
- **Claude Code의 Harness 코드 대부분은 Constrain/Verify/Correct** — Process State Management, Multi-Layer Context Compression, Permission Classification, Circuit Breaker, Error Recovery. 산업 초점이 task completion → **reliable task completion**으로 이동.

### 1.11 엔지니어링 패러다임 진화 (중첩 구조)
Software Engineering ⊃ Prompt Engineering ⊃ Context Engineering ⊃ Harness Engineering ⊃ **Loop Engineering** (단회 실행을 넘어 지속 자율 운영: 다음 일을 누가 발견하는가, 언제 검증, 언제 완료인가 — Ch10).
- 근거 사례: LangChain의 Terminal Bench 2.0 — 모델 변경 없이 Harness 개선(자기 실행 결과 점검, 반복 루프 감지, 추론 전략 개선)만으로 **52.8% → 66.5%** (30위권 밖 → top 5). OpenAI: 엔지니어 3명이 5개월에 ~100만 라인, ~1500 PR (약 10배 속도) — 동력은 모델이 아니라 Harness.

### 1.12 Anthropic의 효과적 에이전트 구축 3원칙
1. **Keep it simple** — 직접 API 호출 > 복잡한 프레임워크. 추상화 한 층 = 디버깅 사각지대 하나.
2. **Keep it transparent** — 계획/로그/결정 궤적 노출 = 사용자 신뢰의 전제.
3. **ACI (Agent-Computer Interface) 설계** — 프로그래머가 아니라 에이전트 관점에서 인터페이스 설계. **Poka-yoke**(도요타 생산방식의 실수 방지 설계: SIM 카드 모따기, 전자레인지 문 열림 감지): 오용 가능성은 설계 단계에서 원천 차단.

### 1.13 모델 선택 지침
- Big Three: OpenAI(GPT/o, 범용 균형·최대 사용자), Anthropic(Claude, 추론/코딩/tool calling 강점), Google(Gemini, 초장문 context·멀티모달). **리더보드 말고 자기 태스크로 평가(Ch6).**
- 중국 모델: Doubao(저지연), Kimi(에이전트 능력 강함), Qwen/DeepSeek(오픈소스, 비용·커스텀). tool-calling 능력 편차 크니 반드시 실측.
- **대부분의 에이전트는 reasoning 지원 모델 필요** (예외: 단일 단순 스텝, 고정 위치 클릭 GUI 조작).
- 간과하기 쉬운 2축: **output token speed** (라운드당 2초 느리면 20라운드에서 +40초), **multimodal 지원 여부**.

### 1.14 Orchestration: Workflow vs Autonomous
- **Workflow**: 사전 정의된 코드 경로로 LLM+tool 오케스트레이션. 결정론적. 장점: 프로세스 통제(결제 전 예약 불가를 코드로 강제), 보안(공격면이 단일 노드에 한정). 단점: 유연성 부족.
- **Autonomous Agent**: 실행 경로를 런타임에 환경 피드백으로 결정 = ReAct loop. **명시적 중단 조건 필수** (태스크 완료, final answer tool 호출, tool call 없는 응답, 최대 라운드, 에러 횟수 초과). 비용 높고 오류 누적 → 샌드박스 테스트, 가드레일, human-in-the-loop.
- 실무 지침: **프롬프트 먼저 → workflow → 마지막에 autonomous**. 혼합이 일반적 (컴플라이언스 구간은 workflow, 유연 판단 구간은 autonomous). n8n 같은 시각 워크플로우 도구도 두 노드 유형 공존.
- 프레임워크 선택 기준: "정교함"이 아니라 **가장 얇은 추상화로 비즈니스 로직에 집중 가능한가**.

### 1.15 Guardrails 3종 (defense in depth)
- **Input-side**: relevance classifier(주제 이탈), safety classifier(jailbreak/prompt injection — 구별: jailbreak는 사용자가 직접 제한 우회, injection은 외부 데이터 경유 간접 조작), content moderation, rule-based(블랙리스트/길이/regex).
- **Execution-side**: **tool risk rating** (가역성/권한 수준/금전 영향으로 low/medium/high, high는 추가 검토·사람 확인).
- **Output-side**: PII filter, output validation(브랜드 정합성).
- Anthropic **Constitutional Classifiers** (2026, arXiv:2601.04603): ①자연어 "constitution"으로 합성 훈련 데이터 생성 ②질문+답변을 함께 보는 joint contextual judgment ("식품 향료"가 화학약품 은어임은 질문과 대조해야 판별) ③two-stage: 낶부 activation을 읽는 초경량 probe가 먼저 스크리닝, 의심만 상위 classifier로 (거부 대신 에스컬레이션 → 비용 절감).
- **Human-in-the-loop** 트리거 2종: 실패 임계 초과, 고위험 작업(주문 취소, 대액 환불, 결제).

# Chapter 2. Context Engineering

## 1. 핵심 프레임워크와 정의

### 2.1 Context는 에이전트 능력의 천장
- 모델 능력은 범용, 실무 태스크는 local knowledge(제품 아키텍처, 비즈니스 규칙, 운영 제약, 낶부 관례)에 의존 — 이건 파라미터에 없다.
- Coding Agent 최소 context 3종: **code context**(코드베이스 구조/표준), **process requirements**(브랜치 전략/리뷰/CI-CD), **environment configuration**(개발 환경/DB/배포/키 관리).
- **중간 능력 모델 + 잘 정리된 context > 강한 모델 + 부실한 context.**
- Context engineering은 기술 문제 이전에 **조직 문제**: 지식이 암묵지로 남은 팀은 에이전트도 못 쓴다. Linux 커널 같은 문서 중심 공개 문화가 AI-native 환경. "에이전트를 매번 새 팀원으로 대하라."
- OpenAI 연구원 Jiayi Weng: "사람이든 모델이든 가장 중요한 것은 Context", "내 context를 다 가진 사람이라면 내 일을 할 수 있다", 팀워크의 핵심 문제는 context 불일치.

### 2.2 API 레벨 context 구조
- **4가지 message role**: system(개발자 지시, 고우선순위), user, assistant(이전 모델 출력+tool call), tool(실행 결과, **tool_call_id로 대응 call과 연결**). tool definitions는 메시지가 아니라 별도 `tools` 필드.
- **매 호출은 stateless** — 요청의 message list에 필요한 모든 정보가 들어 있어야 함.
- 책임 분할의 핵심: **모델은 어떤 tool을 어떤 인자로 부를지 결정만 하고, 실행은 framework가.**
- 병렬 tool call: 의존성 없는 call은 모델이 한 번에 여러 개 반환 → framework가 병렬 실행해 지연 절감.
- 최소 에이전트 루프(Python): while True → chat.completions.create → assistant message append → tool_calls 없으면 출력 후 break → 있으면 각각 execute 후 tool message append → 반복. **프로덕션에는 max_iterations 상한 필수.**
- **Agent framework의 중심 책임 = message list 유지 관리** (올바른 시점에 append, 관련 history 전송). 이 챕터의 모든 기법은 그 list의 내용과 구조 개선.
- 실험 2-1 (local_llm_serving): Qwen3-0.6B + Apple M2/16GB + MLX, >100 tokens/s로 tool calling 가능. **0.6B도 합리적 프롬프트+아키텍처면 tool call 가능** — 온디바이스 에이전트는 생각보다 가까움. 모델 출력 순서: `<think>` 추론 → 사용자 텍스트 → tool call (스트리밍 구현의 기초). 종료 판단도 모델이.

### 2.3 KV Cache 친화적 설계 — 3대 실천 원칙
1. **system prompt와 tool definitions는 확정 후 변경 금지** — 공백 하나 추가도 전체 캐시 무효화 → 지연·비용 배증.
2. **동적 정보는 항상 끝에 append** — 타임스탬프/사용자 상태는 새 메시지로 대화 끝에.
3. **표준 API 형식 사용, 수동 문자열 연결 금지** ("USER: ... ASSISTANT: ..." 수동 포맷은 훈련 포맷에서 벗어나 다단계 추론 약화; 캐시 자체는 byte-stable하면 맞지만 훈련 분포 이탈이 본질적 해악).
- 프로덕션 사고 사례: system prompt에 `Current time: {{now}}` 한 줄 추가 → 매 요청 캐시 무효 → **TTFT 0.5초 → 3-5초, 월 추론비 약 2배**.
- Attention 메커니즘 (실험 2-2): Query(현재 단어의 검색 요청)/Key(각 단어의 라벨)/Value(매칭 시 추출 내용). dot product → attention weight(softmax 합=100%) → Value 가중합. heatmap 관찰: ①**Attention Sink** — 첫 토큰이 주의의 ~70%까지 흡수 (softmax가 "아무것도 안 보기"를 표현 못 해 잔여 무게의 안정적容器로 첫 위치 사용, 결함 아닌 필연) ②추론 삼각형 패턴(`<think>` 낶 자기주의) ③출력 삼각형 패턴 ④**Position Bias** — 처음/끝 정보 recall 정확, 중간은 누락 (Liu et al., "Lost in the Middle", TACL 2024) → 중요 정보는 처음이나 끝에.
- KV Cache 동작: 새 토큰 생성마다 이전 모든 토큰의 K/V 재계산 대신 캐시 재사용. 캐시 없으면 prefill이 context 길이에 이차 증가, 캐시 있어도 attention 순회는 선형 증가(긴 context 디코딩이 느려지는 이유; KV Cache 메모리/대역폭이 추론 병목). prefix의 한 토큰이라도 바뀌면 레이어 전파로 그 지점 이후 캐시 전부 재계산.
- **Chat Template**: API JSON 메시지 → 모델용 선형 토큰 스트림 변환기 (봉투 형식 비유, `<|im_start|>`/`<|im_end|>` 등 special token). 모델 계엄마다 형식 다름(Qwen/Llama/Gemma), vLLM/Ollama가 자동 처리. 실무 함의 2가지: ①표준 API 형식을 써야 하는 이유 — Qwen3는 마지막 user 메시지 이후의 `<think>` 추론을 다음 턴에 유지(멀티턴 tool call 연속성), tool 결과를 user로 잘못 표기하면 이 리셋이 오작동. ②prefix 민감성의 기술적 근거.
- **역사적 CoT 처리의 업계 반전**: DeepSeek R1 시절 = historical reasoning 전량 제거(훈련 입력에 없던 out-of-distribution + 토큰 절약) → 그러나 Agent 시나리오에서 중간 추론은 "왜 이 tool을 불렀고 어떤 가설을 배제했나"라는 상태라 제거하면 매 턴 처음부터 재추론·실수 반복 → DeepSeek V4는 reasoning_content 반환 **의무화**(미반환 시 API 에러), Kimi K2/GLM-5 동일 프로토콜. Claude는 tool call 루프 안에서 thinking block을 서명 검증과 함께 그대로 반환 요구, 새 user 턴 이후 과거 thinking은 서버가 무시. **"thinking is not waste but state."**
- 실험 2-3 (★★) 흔하지만 유해한 패턴 5종:
  1. **Dynamic System Prompt** (타임스탬프 임베딩) → 캐시 전멸. 정답: user 메시지 끝 append 또는 tool로 필요시 획득.
  2. **Dynamic User Configuration** (잔여 API 콜/잔액 매 요청 갱신) → 캐시 파괴. 전용 상태 관리로.
  3. **Tool 정의 동적 정렬** (사용 빈도 순 재배열) → 고정 순서가 선택 정확도에 거의 영향 없이 성능 크게 개선.
  4. **Sliding Window history** → prefix 일관성 파괴 + 핵심 tool 결과 유실(2라운드에 읽은 파일이 15라운드에 필요한데 윈도우 밖) → 재추론 오류·같은 tool 반복 루프.
  5. **Text Formatting** (role-content를 평문으로) → 훈련 포맷 이탈: 반복 작업, tool 결과 무시, 파싱 오류. 본질은 캐시가 아니라 모델 능력 문제.
- **KV Cache vs Prompt Cache 2계층**: KV Cache = 단일 추론 내 최적화, Prompt Cache = API 서비스 계층의 요청 간 prefix 재사용. 캐시 읽기 가격: Anthropic·DeepSeek·OpenAI GPT-5 계열 모두 **신규 계산의 ~1/10** (GPT-4o는 1/2; GPT-5.6부터 cache write에 1.25배 할증). Anthropic: cache_control 명시, write 할증, 최소 1024 토큰, TTL 기본 ~5분. OpenAI: 자동 prefix caching.
- **Caching as Architectural Constraint (Claude Code 사례)**: ①cache boundary marker로 system prompt 분할 — 경계 앞=전역 캐시, 뒤=사용자/세션별. 경계 앞 런타임 조건 N개(이진) → 2^N cache key (예: OS 2 × 모드 2 × 언어 2 = 8). 프롬프트 조각을 "cacheable/cache-breaking"으로 타이핑하고 후자에 경고 마커. ②**Sub-agent는 parent와 byte-aligned** — sub-agent/side query의 프롬프트·tool·모델 설정·prefix·reasoning 설정이 parent cache key와 바이트 단위 일치해야 Prompt Cache 히트. ③tool 결과 대체 문자열은 최초 발생 시 **동결** — 세션 재시작 후에도 동일 문자열로 복원해 바이트 동일성 유지. **캐시 경제성은 사후 최적화가 아니라 사전 아키텍처 제약.**
- (선택) KV Cache as editable/composable "notes" (저자 자신의 논문, arXiv:2606.17107): prefill 시 모델은 필드 원문이 아니라 **결론을 downstream KV에 "메모"** — 필드 자체 토큰의 KV 기여도 1% 미만. 명시적 CoT가 있으면 필드 변경을 ~1% 연산으로 전파(Editing), RoPE 재배치로 미리 계산된 skill cache를 다른 context에 접합(Composition, O(L²)→O(L)). vLLM 구현: p90 TTFT 수십~수백 배 개선, prefix 히트율 98.5%, logit cosine similarity 0.90-0.999. 아직 연구 단계.

### 2.4 Prompt Engineering (System Prompt 최적화)
- 리트머스: **"우리 워크플로우를 전혀 모르는 유능한 신입이 이 system prompt만 읽고 뭘 할지 알 수 있는가?"**
- Tone/Style: "You MUST answer concisely"류의 행동 프레이밍. 실패 시 "1-2문장", "못 하는 이유 설명 금지". 대문자 NEVER는 salience↑지만 남용 시 희석 — 진짜 중요한 제약에만.
- 구조화: XML 태그는 계층+시맨틱(`<working_directory>` 자체가 의미 전달), Markdown은 경량 계층. XML=기계 파싱 정밀, Markdown=가독성 2층 구조.
- **Process-driven > Rule stacking**: 흐름도 없는 수백 개 규칙 나열은 사람에게도 모델에게도 혼란. SOP 형태(검증→분류→전처리→실행→검증)로 단계·현재 위치·예외 분기를 명시.
- 비즈니스 규칙의 실행 가능 번역 (Pine AI 과금 사례): "상황에 맞게 과금 유형 선택" 같은 모호 규칙 → 행동 불안정. 실행 가능 수준으로: 커미션은 기존 청구액 절감 협상에만, 환불/해지는 NEVER percentage_based → fixed_fee. 성공률 단계별 평가 절차, 과금 단위($0.05/분, 정수 달러 반올림), "savings는 기존 청구서 기준"(미래 인상 회피분 제외)까지. **성숙 팀은 프롬프트를 PM이 설계하고 엔지니어는 정확히 인코딩.** 모델에게 비즈니스 규칙 재량권을 주지 말 것.
- Few-shot: 규칙으로 서술 어려운 것(문체, 리포트 포맷, 어조)엔 예시 2-3개 > 장문 추상 설명. 이미 잘하는 태스크엔 토큰 낭비. 배치: system prompt(정적 prefix) vs 첫 턴 합성 user/assistant 메시지(대화 유형별 상이). **한번 정한 예시 세트는 byte-stable 유지 — 요청마다 "가장 관련된" 예시를 동적 검색하면 캐시 반복 무효화.** 경계 케이스 커버하는 2-3개 > 유사 10개.
- Tool definition 품질 (Claude Code 예): 사용 경계("NEVER invoke grep or rg as Bash command"), 구체 예시, 성능 팁("Batch your tool calls together"), tool 간 관계("Read를 최소 한 번 쓴 후에 Edit").
- **2026년부터 API 네이티브 progressive disclosure**: OpenAI Responses API의 `tool_search` + `defer_loading: true` (tool_search_call → tool_search_output), Anthropic Tool Search(`tool_reference` 블록, Claude Code는 MCP tool 기본 지연 로딩), Codex CLI(BM25 tool_search). 공통 패턴: 정적 prefix엔 이름+간단 설명만, 전체 스키마는 **context 끝에 append** → KV prefix 무결(append-only injection; causal attention이라 기존 토큰 K/V 불변). 스키마는 한 번만 추가되어 원래 위치에 잔존, 매 턴 끝으로 재이동하지 않음. TTL 만료 또는 로드된 tool 세트 변경/제거/재정렬 시에만 그 지점부터 무효화. 제약: "대화 중간에 tool 정의 등장" 패턴으로 훈련된 새 모델(GPT-5.4+, Claude 4.5+)만 지원.
- 실험 2-4 (★★, Tau-Bench ablation): ①tone 변경(Trump식/캐주얼) → 완료율 영향 미미 ②**정보 조직 제거(구조화→무구조 규칙 나열) → 성공률 30%p 이상 폭락**, "환불 전 본인확인" 같은 핵심 규칙 위반 빈발 ③tool 설명문 제거 → tool call 오류율 +45%. **교훈: 성능 저하 시 전면 재작성 대신 ablation으로 기여도 측정.**

### 2.5 Prompt Injection (context 보안의 핵심 위협)
- 정의: 외부 콘텐츠(웹/이메일/문서)에 시스템 지시로 위장한 텍스트를 심어 행동 탈취. Agent는 tool이 있어 챗봇보다 위험 — 파일 삭제, 메일 발송, 데이터 유출 등 **불가역 행동** 가능. perception tool 하나하나가 injection 진입점 (웹페이지 보이지 않는 요소, PDF 메타데이터, 이미지 EXIF).
- Context 레벨 방어 3종: **Source Tagging**(`<external_content source="webpage">` 래핑+출처 주석), **Structured Roles**(Chat Template role 체계로 지시/데이터 구분 — tool 결과를 user 메시지에 섞지 말 것), **Input Sanitization**(의심 패턴 필터 — 보조 수단일 뿐).
- 새로운 injection 표면: **Skill 자체가 고권한 지시로 context 진입** — 출처 불명 Skill은 실행 코드처럼 설치 전 리뷰. Status bar도 모델이 강하게 신뢰하므로 오염 가능 소스 금지.
- context 방어는 1차 방어선일 뿐 완전 보장 불가 → execution 레벨(권한 통제, 샌드박스, 고위험 작업 독립 검토)과 layered defense (Ch4/5).
- 실험 2-5 (★★): 직접 injection / 간접 injection(요약 요청 웹페이지 내 은닉 지시) / **memory injection**(세션에 심은 지시가 이후 세션에서 발동) 3 시나리오 × 방어 조합(없음/프롬프트 경고/XML 출처 태그/복합)으로 성공률 측정.

### 2.6 Dynamic Prompts와 Agent Skills
- 정적 프롬프트 팽창의 2 문제: **토큰 낭비**(대부분 현재 태스크와 무관), **주의 희석**(context rot).
- **Skills = Progressive Disclosure 3계층**: L1 metadata(SKILL.md YAML frontmatter의 name+description, 시작 시 주입, 수백 토큰) → L2 SKILL.md 본문(판단 후 Skill tool로 로드, ~2K 토큰, tool result로 history에) → L3 하위 문서(html2pptx.md, reference.md, scripts/*.py — 선택적 심화).
- **description은 기능 요약이 아니라 라우팅 규칙으로**: "Use when / Do not use when" + **negative example 필수**. "backend 작업 지원" 같은 광범위 서술은 무관 태스크에 오발동. 라우팅엔 "무엇을 할 수 있나"보다 "언제 나를 쓸 것인가".
- Skill은 지식 패키지를 넘어 실행 코드/템플릿 번들 가능 → 운영 능력. pip/npm식 분산 생태계 비유. Anthropic 공식 skills repo(PPTX/PDF/DOCX 등).
- 원칙: **모델/API가 설계해 둔 상호작용 패턴에 맞춰라** (Claude면 Skills와 구조화 system prompt 적극 활용 등).
- Skills 배치 3방법과 트레이드오프:
  1. **System prompt에 주입**: instruction-following 최강, 그러나 Skill 로드마다 prefix 변경 → 캐시 반복 무효화.
  2. **일반 파일 읽기로 중간 배치**: 캐시 무결, 그러나 긴 context 중간의 지시를 따르는 능력이 모델 의존(Claude가 가장 안정적 — 중간 위치 instruction-following 훈련 데이터 多).
  3. **(프로덕션) metadata는 동적 context로 사전 제공 + 전체 내용은 전용 Skill tool로 on-demand 로드** (Claude Code 방식): 라우팅과 실행 분리. metadata 주입 role(user-role 래퍼 vs mid-conversation system block)은 Harness 버전별 구현 디테일일 뿐 메커니즘의 본질 아님.
- KV 관점: skill_listing(~300 tok)과 skill_content(~2K tok) 모두 **emit-once** — 최초 1회 cache_creation 비용만 지불하고 이후 영구 HIT, 메시지 인덱스는 절대 이동 안 하고 새 내용은 끝에만 append. **"KV Cache-friendly" ≠ 비용 제로; "write once, benefit repeatedly".**
- Skills vs Tools: 전용 tool 정의를 전부 prefix에 두면 팽창+변경 시 무효화. Skill+범용 실행기 모델에서는 tool 세트가 작게 유지됨(Ch5: 핵심 tool 7개).

### 2.7 Agent Status Bar
- 정의: framework가 **context 끝에 user-role 메시지로 주입하는 상태 요약**(호출 횟수, 현재 시각, TODO 진행). 폰 상태바 비유. System prompt=고정 매뉴얼, Status bar=실시간 대시보드.
- 이론적 근거: **in-context learning은 추론보다 검색(retrieval)에 가깝다** — attention은 기존 토큰 조회엔 강하지만 단일 forward pass로 집계 상태를 능동 요약하진 못함. "몇 번 전화했나" 같은 결론은 원시 레코드에 흩어져 있어 매번 재계산 → 비효율+오류. **Status bar = 흩어진 암묵 상태를 명시 지식으로 증류 + 끝 배치로 attention steering**(생성 위치에 인접해 최고 주의 가중치).
- 실험 2-7 (주의 시각화): status bar 없으면 주의 분산+모델이 직접 카운팅(소형 모델은 제약 위반 빈발), 있으면 상태바에 주의 집중+제약 준수.
- **Context Distillation 벤치마크** (Li & Shi, 2026; 3종 태스크, 11개 모델, ~24,000회 평가): ①약한 모델은 정확도 +40~54%p 회복 — 로컬 2B가 status bar 없는 프론티어 모델과 대등 ②강한 모델은 추론 토큰 80-90% 이상 절감, 지연/비용 약 1/10 ③status bar 없으면 쿼리당 추론량이 context 길이에 비례 증가, 있으면 **사실상 상수**. **key-value 형식 필수** (산문 형태는 재파싱 비용으로 효과 급감).
- 3대 실천 교훈:
  1. **Status bar는 LLM이 아니라 코드로 유지하라** — 20줄 정규식이 ground truth 수준인데 프론티어 모델 일괄 요약은 오류 多로 baseline 이하. LLM이 꼭 필요하면 항목별 추출 후 코드로 집계.
  2. **원본 삭제 전 status bar가 미래 질문을 커버하는지 확인** — lossy projection. "쌍별 조합"만 저장했는데 "삼중 교집합" 질문 → Claude 정확도 100%→7.6% 붕괴. 불완전한 status bar는 **false authority**. 새 질문 유형 = DB 스키마 변경처럼 취급.
  3. **Status bar 정확도를 1차 프로덕션 지표로 모니터링** — 모델은 status bar를 거의 무조건 신뢰. 오차 <~10%는 이점 유지, 그 이상은 없는 것보다 나쁨. **status bar poisoning** 주의: 신뢰 가능한 실세계 관측에서만 생성.
- (선택) **Interaction Scaling** (저자 논문, arXiv:2607.11598): test-time compute의 제3축. reason longer/sample more는 기존 정보 재배열일 뿐이고, **interaction**(출력→외부 계측→context에 기록)만이 context에 없던 정보를 만든다 (테스트 통과 여부, 렌더링 오버플로 등). Status bar가 그 가장 흔한 적용. 측정 기준 자체가 실관측에 grounding돼야 함.
- 구성 요소 4종: Task Planning(TODO), 이벤트 Side-channel 정보(정밀 시각/위치/경과), 현재 환경 상태(시각/작업 디렉토리/반복 호출 경고), Available Capability List(Skill metadata).
- 위치: **context 맨 끝, API상 user role 메시지로**(`<agent_status>` 태그). system 수정이 아니라 append라 캐시 무결. user role은 프로토콜상 기술적 선택일 뿐 최종 사용자 입력 아님.
- 갱신 2방식: ①**Replace each round** (이전 상태 제거 후 최신 append — 말단부라 무효화 범위는 최근 몇 라운드로 국한) ②**Persistent appending** (Claude Code: 이력 상태 영구 잔존, 매회 신규 append — 완전 캐시 친화, 낡은 상태 누적 비용). Rule of thumb: **갱신 잦고 trajectory 길면 ②, 짧거나 상태 메시지가 크면 ①.**
- 실험 2-8 (★★) 5가지 기법: Timestamp Tracking(메시지 접두, system prompt 아님), Tool Call Counter(전역 카운터, "read_file 3번째 호출" — 실패 후 전략 변경 유도, 암묵적 비용 인식), TODO List(Manus의 "restatement로 주의 조작", rewrite_todo_list/update_todo_status 전용 tool, 외부 메모리로서의 체크리스트; **TODO 있으면 평균 15회 vs 없으면 21회 iteration**), Detailed Error Info(4계층: 유형/파라미터 JSON/스택/수정 제안 — **에러 복구 성공률 60%→95%**), System State Awareness(시각/작업 디렉토리/OS/셸/Python 버전 — cd 후 자동 갱신, apt vs brew 분기). **단독으론 미미, 조합 시 창발 효과.**
- **Time Sense 3축** (저자 논문: Urgency/Persistence/Vigilance): Urgency=예산 축(시간 촉박 시 결단, 여유 시 심화 — 양방향), Persistence=종점 축(410 Gone 재시도 5회는 과잉, 검색 2회만에 포기는 과소), Vigilance=감시 축(500ms 예상 호출이 5초, 1초만에 빈 body 성공 — 둘 다 조사 가치 있는 신호). 벤치마크: raw timestamp만 = 정보 없음과 2-3%p 차이, **timestamp+해석 지침 추가 시 통과율 10%대 → 40-50%(+19~49%p)**. 모델에게 부족한 것은 reading이 아니라 **reading을 행동으로 번역하는 전략**. 4개 벤더 6개 모델 공통 — post-training이 time-sensitive 제어를 못 가르친 것. "status bar + operational guidance" 또는 Ch7의 증류 경로(조밀 token-level 신호는 성공, 희소 outcome 보상은 실패).

### 2.8 Context Compression
- 2대 동기: ①길이/비용 제약 ②**추론 품질 향상 — 요약된 지식이 원시 정볼보다 모델에 유용**(윈도우가 남아도). 10회 검색 원시 결과가 수만 토큰에 흩어짐 vs 1회 LLM 호출로 구조화 요약("A는…, B는…, C는 미확보").
- Status bar는 계산된 결론을 **추가**, compression은 원시 레코드를 결론으로 **대체**. 둘 다 attention에 없는 증류 계층 공급. 차이: status bar는 보통 코드가 결정론적으로 유지, compression은 LLM 호출로 대량 원문 증류.
- **Context Rot ≠ Context Overflow**: overflow는 "못 넣음", rot은 "넣었는데 못 찾음" — 겉으론 정상 작동하며 결정 품질이 조용히 악화. 긴 context에서 주의 가중치 분산, 무관 콘텐츠 지배 시 품질 저하. 흔한 실패 모드는 윈도우 부족이 아니라 **정보 밀도 부족**. Karpathy: 제한된 context가 추상 패턴 학습을 강제한다는 점에서 "나쁜 기억력은 버그가 아니라 feature".
- In-context learning은 진짜 학습이 아니라 **빠른 적응 메커니즘** — 일시적이고 얕음 ("Learning without training", Benoit Dherin et al., 2025: few-shot 예시는 파라미터 변경 없이 소형 전문 훈련과 유사 효과, 세션 간 축적 안 됨).
- **Compression × KV Cache 조화**: 압축은 API 호출 사이에 framework가 message list 전처리. system prompt+tool definitions는 불触碰, 대상은 history의 tool results. 교체 지점 이후 캐시 무효(의식적 트레이드오프) — **매 라운드 압축 말고 임계 근접 시 배치 압축**.
- 실험 2-9 (★★★, OpenAI 공동창업자 재직 추적 태스크, Kimi K3에 128K 윈도우 제한):
  | 전략 | 토큰 | 압축률 | 반복 | 결과 |
  |---|---|---|---|---|
  | No compression | >110K | 100% | 5 | ✗ overflow 실패 |
  | Individual summary | 123,205 | 6.8% | 24 | ✓ |
  | Combined summary | 55,462 | 2.1% | 21 | ✓ |
  | **Context-aware** | 25,198 | 0.9% | 15 | ✓ 최소 반복 |
  | Aware + citation | 45,544 | 1.4% | 17 | ✓ 검증 가능 |
  | Adaptive window | 181,372 | — | 8 | ✓ 최고 충실도 |
  - 개별 요약(결과당 2-3문단, 정보 파편화), 통합 요약(초장문 입력 절단 위험), **context-aware("Given query: {query}" + "Current context: {context}"로 압축 방향 지시 — 147,877자→1,963자(1.3%)에서도 핵심 보존, 토큰 75%+ 절감)**, +citation(URL 출처로 원문 복귀 가능 — 손실 압축+무손실 색인 결합), adaptive window(**80% 임계(128K 중 102,400 토큰) 도달 시 트리거, 미압축 tool 결과 일괄 배치 압축, [COMPRESSED] 마커로 중복 방지**). 단계별 필요 밀도 다름: 초기=광범위 수집, 중기=정밀 검증, 후기=종합.
- **프로덕션 5계층 계층 압축 (Claude Code 참조)**: ①Tool Result Budget Control(대형 출력은 디스크 저장, 모델엔 미리보기만; 대체 결정은 동결) ②Direct Noise Deletion(저가치 콘텐츠는 요약 없이 삭제 — 노이즈 요약은 토큰 낭비) ③API-Level Micro-Compression(서버 context editing으로 특정 tool 결과 제거, 로컬 list 불변 — 제로 구현 비용이나 제거 지점 이후 캐시 재구축 필요, overflow 직전에만) ④Archival Summarization(git log식 라운드별 구조화 요약, squash 아님) ⑤Full Compression(최후 수단, 2단계: session memory 먼저 → 실패 시 전체; 연속 실패 circuit breaker — 프로덕션 데이터상 압축 실패 반복 루프 세션 다수). **앞 3개가 저비용·캐시 영향可控으로 우선.**
- 압축 설계 4원칙: Non-Uniform Information Value(핵심 결정 > 근거 > 노이즈), Semantic Integrity("Sutskever가 2024년 5월 OpenAI 퇴사"에서 시점·회사명은 비타협), Task Relevance(같은 내용도 태스크별로 다른 압축), **Compression is Understanding**(압축 모듈이 본 모델급 언어 이해 필요 → 재귀적 모델 호출 아키텍처).
- 압축이 가장 잃기 쉬운 것: 디테일이 아니라 **초기 아키텍처 결정, 제약의 근거, 실패한 경로**. 보존 우선순위: ①아키텍처 결정·핵심 제약 ②수정 파일 목록·핵심 변경 기록 ③검증 상태(pass/fail) ④미해결 TODO·롤백 노트 ⑤tool 출력(결론만). **UUID/해시/IP/포트/URL/파일명은 한 글자도 바꾸지 말 것** (PR 번호 한 자리 바뀌면 이후 tool call 직접 실패).
- **Sub-Agent Context Isolation (Isolation over Compression)**: 대량 중간 산출물 태스크(다수 파일 읽기, 코드베이스 광범위 검색)를 sub-agent에 위임, 메인 context엔 태스크 기술+수백 토큰 결론만 2개 메시지. 압축=사후 손실 구제+추가 LLM 호출, 격리=사전 차단+메인 KV prefix 무결. 비용: sub-agent는 메인 context를 못 봄 → **태스크 기술이 self-contained해야**. Claude Code의 Task tool, Deep Research의 검색 sub-agent가 구현例.

8. ★★ SKILL.md를 동적 로드한 뒤 후속 작업이 그 지시를 확실히 따르는가? 모델별 지원 차이는?
9. ★★★ tool이 많고 자주 바뀌는 프로덕션에서 캐시 히트율을 최대화하는 context 레이아웃 설계는?

## 4. 실무 함의 (스킬/자동화 빌더 관점, Ch2)
- Aside의 MEMORY.md/USER.md 구조와 system prompt 고정 원칙이 정확히 Ch2의 static prefix 원칙과 일치 — 동적 상태(날짜, 루틴 상태)는 prefix 수정이 아니라 끝 append로 설계돼 있는지 자체 점검 가치.
- "모델은 status bar를 무조건 신뢰" → Aside 루틴이 memory 파일을 상태바처럼 쓰므로, **그 파일의 정확도가 곧 에이전트 결정 품질**. 잘못 적힌 메모리 = false authority. 메모리 갱신 로직을 코드/검증 가능하게.
- Skill description을 "Use when/Do not use when + negative example"로 쓰라는 지침은 Aside 스킬 작성에 직결 — 기존 커스텀 스킬들의 description 점검 항목.
- Sub-agent isolation = Aside의 context_explorer/subagent 위임 패턴과 동일 원리. 탐색·수집 작업은 위임하고 결론만 받는 설계가 메인 세션 context를 지킴.
- 압축 보존 우선순위(아키텍처 결정/변경 파일 목록/검증 상태/미해결 TODO/식별자 원형 보존) → Aside 세션 compaction이나 요약 프롬프트 설계 시 그대로 적용 가능한 체크리스트.
- ERP 일일 동기화 루틴의 "0행 무음 실패" 사례는 Ch1 Constrain/Verify 부재와 Ch2 status bar(실행 결과를 명시 상태로 기록해 다음 실행이 인지) 부재의 교과서적 사례로 볼 수 있음.
