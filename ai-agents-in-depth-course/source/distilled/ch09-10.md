# Chapter 9. Multimodality and Real-Time Interaction (멀티모달리티와 실시간 인터랙션)

## 0. 챕터의 범위와 관점

- 이 챕터는 **"실시간(real-time) 제약이 멀티모달 문제를 어렵게 만드는 3가지 시나리오"**만 다룬다: **음성 대화(voice dialogue), GUI 조작(Computer Use), 로봇 제어(robot control)**.
- 정적 이미지/문서 이해(스크린샷, 차트, PDF 파싱)는 이미 성숙해서 특별한 아키텍처가 필요 없다. 멀티모달 **생성**(이미지/영상 생성)도 이 책 프레임워크에서는 그냥 "일반적인 tool call"이라 이 챕터 범위 밖.
- 연속 비디오 스트림의 실시간 이해는 집필 시점 기준 미해결(open problem).
- 3개 시나리오의 공통점: **여러 모달리티를 동시 처리 + 레이턴시에 극도로 민감**. 음성 대화에서 2초 이상 침묵하면 사용자가 불안해하고, 로봇 제어에서 밀리초 단위 지터는 충돌을 일으킨다. 이 제약이 모두 같은 방향 — **serial pipeline에서 end-to-end model로** — 으로 아키텍처를 밀어붙인다.
- 챕터 전체를 관통하는 두 이론 주제: ① **thinking architecture**(빠른 사고와 느린 사고의 협업) ② **fast-slow interface**(빠른 모델과 느린 모델이 텍스트 외에 무엇을 주고받을 수 있는가 — Latent Bridge). 음성 맥락에서 도입되지만 Computer Use와 로봇에도 그대로 적용된다.

## 1. 음성: 가장 자연스러운 인간-기계 인터페이스 (9.1)

- 음성은 대역폭이 가장 넓고 가장 자연스러운 입력: 말하기는 타이핑보다 약 4배 빠르고 손과 눈을 점유하지 않는다.
- 제품 형태 2종: ① **voice dictation tools**(예: Typeless — 실시간 전사해서 아무 앱에나 입력, 키보드 대체) ② **voice Agents**(예: Pine, ChatGPT Voice — 음성이 입력이자 인터랙션 자체).
- 고급 사용례: **whisper coding** — 말로 코딩/리서치 에이전트를 지휘. 저자 팀의 10여 편 논문이 이렇게 완성됨.
- 음성 아키텍처는 양방향으로 쓰인다: 사용자→에이전트(인터페이스), 에이전트→외부 세계(사용자 대신 전화 걸기).

## 2. 음성 아키텍처의 3대 패러다임 (9.2)

OpenAI가 GPT-Live 공개(2026) 때 제시한 3분류. ChatGPT Voice 자체의 3세대 진화와 대응:

1. **Cascaded (직렬 파이프라인)**: VAD → ASR → LLM → TTS를 릴레이처럼 연결. 모델 간 전달에서 정보 손실, 느리고 경직된 응답.
2. **End-to-End Omnimodal (Omni)**: 단일 모델이 "듣고-생각하고-말하기"를 통합. 레이턴시↓, 운율·감정 같은 비텍스트 정보 보존. 단 **turn-taking 가정은 여전히** — VAD/침묵 감지로 턴 전환. 잠깐의 멈칫이나 소음을 "말 끝"으로 오판해 부적절하게 끼어듦. ChatGPT Advanced Voice Mode가 이 세대. OpenAI는 "turn-based voice models"라 부르고 업계는 "Omni"(예: Qwen3-Omni)라 부른다. 같은 것.
3. **Full-Duplex / Interactive**: 듣기와 말하기를 동시에. 초당 수차례 "말할지, 들을지, 멈출지, 끼어들지, 도구를 부를지" 결정. 턴 개념 자체를 해소. 연구 선구자는 Kyutai의 **Moshi**(2024), 제품 스케일은 OpenAI **GPT-Live**(2026, 1.5억 사용자).

**핵심 서사축: "VAD를 어떻게 대체하는가"** — 3세대 모두 이 질문의 답. 3개 패러다임은 새것이 옛것을 대체하는 것이 아니라 2026년 현재도 레이턴시/비용 제약에 따라 **공존하는 설계 선택지**.

## 3. 패러다임 1: Cascaded Pipeline (9.3)

### 직렬 파이프라인의 레이턴시 구조
- **VAD**(Silero VAD 등): 500-800ms 연속 침묵을 말끝으로 판정. 첫 레이턴시 소스이자 딜레마 — 너무 짧으면 생각하느라 멈칫한 것을 말끝으로 오판(문장 절단), 너무 길면 응답까지 1초 대기.
- **ASR**(Whisper, SenseVoice): 5초 오디오 전사에 50-200ms(중소형 GPU), 크거나 자원 제약 시 200-500ms. 이 대기 동안 **LLM은 완전 유휴** — 아무것도 못 받아서 미리 생각을 시작할 수 없다.
- **LLM**: TTFT 100-500ms + 첫 문장 ~100ms. reasoning 켜면 5-10초.
- **TTS**: 200-500ms.
- 총합: 이상적 무부하 조건에서 **0.9-2초**(최선 950ms, 최악 2300ms).

### 큐잉 레이턴시 (queuing theory)
- 프로덕션에서는 큐잉이 더 악화. 근사식: **Total Latency ≈ Idle Latency × 1/(1-Utilization)**.
- utilization 50% → 레이턴시 2배, 80% → 5배. 프로덕션 ρ는 보통 0.5-0.8 → 실제 레이턴시는 idle의 2-5배. 서버를 고부하로 오래 몰 수 없는 이유.

### 9.3.1 Full-chain streaming (전 구간 스트리밍)
- 흔한 오해 교정: 0.9-2초는 "완전 직렬" 가정. 2025년 이후 프로덕션은 모듈성을 유지하되 각 단계를 **스트리밍**으로 만들어 인접 단계를 시간상 겹친다:
  - ASR: 말하는 도중 연속 전사(스트리밍 인식).
  - LLM: 문장 단위 청크로 출력 — 첫 문장이 형성되는 즉시 하류로.
  - TTS: 문장 레벨 스트리밍 합성.
- LiveKit Agents, Pipecat 같은 오픈소스 프레임워크와 상용 아웃바운드 콜 시스템이 이 방식. **전 구간 스트리밍 후 E2E 레이턴시 600-800ms**로 압축.
- 단 스트리밍이 못 건드리는 구간: **VAD의 침묵 대기와 턴 판정 자체**. 이 마지막 구간을 줄이려면 "단계 겹치기"가 아니라 최전방 지각(perception) 단계를 바꿔야 한다.

### 9.3.2 Streaming Voice Perception: VAD + ASR 대체
전통적 VAD+ASR 캐스케이드의 3가지 근본 문제:
1. **Latency accumulation**: VAD는 미래를 예측 못 해서 500-800ms를 "기다림"으로만 판별.
2. **Information loss**: VAD 출력은 음성/침묵 이진 신호뿐. 감정 변화, 어조, 망설임, 배경음 소실. "응"이 끼어들기인지 맞장구인지 구분 불가.
3. **Decreased accuracy**: VAD가 연속 오디오를 독립 조각으로 잘라 문맥 연속성 파괴. 이메일 주소, 브랜드명, 인명 같은 고유명사 오인식 급증 (예: "john dot smith"가 다른 세그먼트로 잘리면 "smith"→"miss").

**LLM-based streaming auditory perception**: 오픈소스 LLM 백본을 post-training해 연속 오디오 스트림에서 직접 의미 응답 생성 — "인식"과 "이해"를 한 모델로 융합. 기술적 핵심: 스트리밍 가능 여부는 **인코더가 causal/chunked인가**(이미 도착한 오디오만 보는가)와 **디코딩이 incremental인가**로 결정. Whisper가 스트리밍 불가한 이유는 디코딩이 아니라 **인코더가 완결된 30초 고정 구간을 요구**하기 때문. 전통적 스트리밍 ASR(RNN-T, streaming Conformer)은 LLM과 무관하게 예전부터 실전 배포됨(실시간 자막, 키보드 음성 입력). 이 새 경로는 그 "업그레이드"이지 스트리밍의 발명이 아니다.
- 장점: ① 대화 시작부터 현재까지의 **완전한 문맥**으로 In-Context Learning → 개인정보/전문용어/개인 발음 패턴 인식률↑ ② LLM의 세계 지식 상속("Apple" 뒤에 "event"가 오면 회사) → 금액/지명/브랜드명 정확도가 전통 ASR을 크게 상회.
- 배포 가능 모델: Fixie의 **Ultravox**, **Qwen2-Audio**, Alibaba **Qwen2.5-Omni**.

**가벼운 경로 — 턴 판정을 인식기에 내장**: 소형 오픈소스 스트리밍 인식 모델에 LoRA 어댑터를 달아, 전사하면서 의미와 침묵을 함께 저울질해 "문장이 완결된 생각을 표현했는지" 판정. 턴 내 멈칫(전화번호 읊을 때)이 턴 간 간격보다 긴 경우가 많아 침묵 임계값만으로는 양방향으로 실패.
- 흥미로운 발견: 모델이 턴을 잡을지 망설이는 근본 원인은 보통 아키텍처가 아니라 **사후지식(hindsight)으로 주석된 학습 레이블** — 주석자가 결정 시점 이후의 오디오까지 보고 레이블을 달았기 때문. 결정 시점에 가용한 정볼만으로 재주석하면 헛된 망설임이 사라진다. → Ch7 post-training의 판단과 상통: **데이터가 아키텍처보다 중요할 때가 많다**. (출처: Bojie Li & Noah Shi, "The Trade-off Was in the Labels: Causal Supervision for Turn-Aware Streaming ASR", 2026 forthcoming)
- 프로덕션 구현: Deepgram **Flux**, AssemblyAI **Universal-Streaming**(endpointing+turn detection 내장), 오픈소스 LiveKit/Pipecat의 semantic turn detection 모델.

**음향 이벤트 특수 마커**: 모델이 텍스트 외에 전용 토큰으로 출력 — `<speak_start/end>`, `<interrupt>`(진짜 끼어들기 vs 맞장구 구분), `<emotion:happy/frustrated>`, `<laugh>/<sigh>`, `<music>/<noise>`. 이 마커들이 텍스트 토큰과 함께 통합 이벤트 스트림을 이뤄 사고 레이어로. 에이전트 프레임워크가 활용 가능(사용자 망설임 감지 시 능동적으로 옵션 제안 등).

**Experiment 9-3 (Qwen2-Audio로 시뮬레이션)**: Qwen2-Audio는 비스트리밍이라 **chunked 입력으로 스트리밍을 시뮬레이션** — 비용: 인코더가 비증분이라 새 청크마다 누적 오디오 전체를 재인코딩(대화가 길수록 레이턴시 증가). 이것이 "시뮬레이션 스트리밍"과 "진짜 스트리밍"(causal 인코더, 예: Qwen3-Omni)의 본질적 차이.
- 결과: 청크 시뮬레이션 증분 인식 레이턴시 100-200ms대 vs 전통 방식 VAD 600ms + Whisper 200-500ms = 800-1100ms. 멈칫 시나리오에서 VAD가 첫 긴 멈칫을 말끝으로 오판해 "大概两点左右"(2시쯤)를 "大概零点左右"(자정쯤)로 오인식; 청크 방식은 완전 문맥 유지로 정확 인식. 소음 시나리오에서 Qwen2-Audio는 `<|noise|>` 토큰 출력하며 인식 유지, 전통 VAD는 소음에 오작동.

## 4. 패러다임 2: End-to-End Omnimodal (Omni) (9.4)

- 단일 모델이 듣기-생각-말하기 통합. 충분한 학습 데이터면 낼 **latent space가 paralinguistic 신호(감정, 어조, 배경음)를 생성 측까지 그대로 전달** — 레이턴시↓ + 텍스트로는 불가능한 운율/감정 보존.
- 트레이드오프: cascaded는 모듈 깔끔, 단계별 튜닝, 해석 가능성 좋음 / E2E는 레이턴시와 비텍스트 충실도를 얻는 대신 학습 데이터 요구↑, 해석 가능성↓.

**간과되는 차원: E2E의 주된 이점은 레이턴시이지 정확도가 아니다.**
- 비교 대상: **self-cascade** — 같은 모델이 먼저 오디오를 구조화 텍스트로 전사한 뒤 그 텍스트로 추론.
- 패턴: 답이 주로 의미 내용("무엇을 말했는가")에 의해 결정되고 중간 텍스트가 태스크 관련 정보를 담을 수 있으면 self-cascade가 E2E와 동등하거나 우세(특히 지각이 약한 모델). 답이 텍스트로 표현 어려운 비언어 단서(어조, 감정, 환경음)에 달렸으면 E2E가 명확히 우세. **어느 쪽이 이길지 태스크 성질로 사전 예측 가능**.
- 설계 원칙: 성능을 결정하는 것은 중간 표현(**bottleneck**)의 존재 여부가 아니라 **그 병목이 어떤 정보를 담느냐**. 중간 텍스트를 생전사에서 paralinguistic 마커 포함 구조화 표현으로 업그레이드하면 E2E의 정확도 우위가 종종 좁혀진다. (출처: Bojie Li & Noah Shi, "The Cascade Gap: When and Why Self-Cascades Help Multimodal Agents", 2026 forthcoming)

**Omni의 근본 한계**: 3개 모델을 합쳤을 뿐 **turn-taking 가정은 그대로** — 여전히 VAD로 발화권 배분. 스트리밍 음성 지각이 턴 판정을 의미 레벨로 올려 오작동을 크게 줄이지만, 그건 turn-taking 프레임워크 안의 국소 패치일 뿐 종식이 아니다.

### 대표 모델 비교 (Figure 9-4)
- **OpenAI Realtime API** (`gpt-realtime`): 모델 레벨은 E2E에 가깝지만 인터랙션 제어는 여전히 server-side VAD — 완전 E2E로 가는 중간 단계. 2024 프리뷰는 GPT-4o 기반, 2025 GA 때 실시간 음성 전용 모델 gpt-realtime으로 교체. 인터럽트 지원(사용자 발화 시작 시 현재 생성 즉시 중단), **비동기 function call**(도구 결과를 기다리며 계속 말함 → 도구 레이턴시를 대화 속에 숨김). Gemini Live API도 유사(VAD 민감도 설정 가능, 인터럽트 후 이미 본낸 정보 보존).
- **Qwen3-Omni**: **Thinker-Talker 아키텍처** — 사고(이해·추론)와 표현(음성 생성)을 두 전문 모듈로 분리. 텍스트/이미지/오디오/비디오 지각과 생성 통합. **MoE**로 총 파라미터는 크게(능력) 토큰당 계산은 작게(처리량↑, 큐잉↓). 주의: **MoE는 throughput을 개선할 뿐 first-packet latency를 직접 결정하지 않음**. 낮은 첫 패킷 레이턴시는 Talker가 multi-codebook autoregression으로 오디오 토큰을 증분 생성하고 causal codec이 증분 디코딩하기 때문. 이론적 cold-start first-packet 레이턴시 **약 234ms**. 이해 19개 언어, 생성 10개, 36개 오디오-비디오 벤치마크 중 22개 SOTA.
- **Step-Audio 2**: raw audio 입력 → 텍스트+오디오 토큰 출력의 진정한 E2E. 의미(무엇을) + paralinguistic(어떻게 — 감정, 말속도, 억양) + 배경음/음악 인식. 사고+RL로 표현력 있는 응답 생성, RAG와 외부 도구(웹검색, 오디오 검색) 통합. 자체 벤치마크 StepEval-Audio-Paralinguistic에서 **83.09%** vs Qwen2.5-Omni 44.18%, GPT-4o Audio 43.45%, Kimi-Audio 49.64%.
- **Step-Audio R1**: Step-Audio 2 위에 사고 능력을 오디오 모델에 내재화(internalize)한 후속 모델(→ 9.6 Solution 3).

## 5. 패러다임 3: Full-Duplex / Interactive (9.5)

- 턴 테이킹 자체가 성립 불가한 태스크들: **동시통역**(문장 완료를 안 기다리고 의미 단위마다 즉시 렌더링), **리듬 게임**(끊기지 않는 입력 스트림 + 즉각 반응). "턴"이 없고 무한 입력 스트림만 존재.
- **Moshi**(Kyutai, 2024): 두 오디오 스트림(사용자, 모델 자신)을 병렬 모델링 + 생성 음성의 언어 품질을 높이는 **"inner monologue" 텍스트 스트림**. 항상 듣고 있어서 겹친 발화와 인터럽트가 자연스러운 동작 — 명시적 인터럽트 감지 로직 불필요. E2E 레이턴시 **약 200ms**, 인간 대화 리듬에 근접.
- **Thinking Machines Lab**(Mira Murati 설립)의 **Interaction Model**(2026): "interactivity should not be an external harness like VAD wrapped around the model, but built into the model itself" — "for interactivity to scale with intelligence, it must become part of the model itself." 아키텍처 핵심 **micro-turns**: 전체 턴을 기다리지 않고 **약 200ms 세그먼트** 단위로 입력 처리와 출력 생성 — 오디오/비디오/텍스트 스트림이 인터리브되어 함께 전진. 이 세분성은 절충: 침묵/겹침/인터럽트를 인위적 턴 경계 없이 연속 스트림으로 보존할 만큼 충분히 세밀하고, 여러 모달리티를 청크 동시 처리해 지각 가능한 실시간 범위를 유지할 만큼 충분히 거침. 첫 모델 TML-Interaction-Small은 3개 스트림 joint scratch 학습 — 사용자가 버그 있는 코드를 쓰거나 누가 프레임에 들어오면 먼저 말을 건다(proactive).
  - 느린 사고 처리: 인터랙션 모델은 대화 유지만 담당, 깊은 추론/도구 호출은 백그라운드 강력 추론 모델에 **전체 대화 문맥째로 위임**(고립 쿼리가 아님). 결과는 증분 스트리밍으로 돌아오고 인터랙션 모델이 사용자를 끊지 않는 타이밍에 자연스럽게 대화에 녹임. → "reasoning 모델의 planning/tool/agent 능력 + non-thinking 모델의 레이턴시".
  - TML-Interaction-Small(276B MoE, 12B activated): 턴 전환 레이턴시 **약 0.40초**(GPT-realtime-2.0은 약 1.18초), visual proactivity 벤치마크에서 경쟁 모델(거의 0점) 크게 상회. 집필 시점 research preview.
- **GPT-Live**(OpenAI, 2026): full-duplex를 프로덕션 스케일로. 대화를 이산 턴이 아닌 연속 입력 처리 + 연속 출력 생성으로. 초당 수차례 인터랙션 결정. 사용자가 생각할 때는 조용히 기다리고, "음", "그렇지" 같은 맞장구로 듣고 있음을 표시, 실시간 통역 가능.
  - fast-slow 분리: 검색/추론/복잡한 에이전트 작업은 백그라운드 프론티어 모델(런칭 시 GPT-5.5)에 위임하며 자신은 대화 흐름 유지. GPT-Live-1/mini는 GPT-5.5 Instant, Medium/High는 thinking GPT-5.5 호출 — 사용자가 "빠름"과 "깊음" 선택. "sustainable swapping to the latest frontier models" 강조.
- **"VAD 대체" 서사의 종착점**: VAD(침묵 임계값 추측) → 스트리밍 지각(의미 레벨 판정) → full-duplex("전환" 개념 자체 해소 — 항상 듣고 있으므로 인터럽트가 특별 처리 이벤트가 아니고, barge-in 처리 체인이 아키텍처적으로 소거됨).

## 6. 사고 아키텍처의 트레이드오프: 분리에서 통합으로 (9.6)

**핵심 긴장: 실시간 응답 vs 깊은 사고.** 사용자는 밀리초 응답을 기대, 복잡한 문제는 수 초의 사고 필요. 3가지 핵안은 선형 진화가 아니라 **공존하는 설계 트레이드오프**. Solution 1·2는 빠른/느린 두 독립 모델의 동시 실행(E2E 불필요, cascaded 위에도 얹을 수 있음), Solution 3만 진정으로 추론을 E2E 모델에 내재화.

2026년 기준 **"fast-slow decoupling"이 프론티어 음성 제품의 주류** — Thinking Machines의 "Interaction Models", xAI Grok Voice "Think Fast", Pine AI, GPT-Live "delegation" 모두 "전경은 빠르게 대화 유지, 배경은 느리게 깊은 추론". 분리를 택하는 실용 이유: **프론티어 추론 모델은 몇 달마다 교철되는데 실시간 인터랙션 능력은 전문 데이터와 학습 목표가 필요 — 둘을 한 모델에 넣으면 움직이는 과녁을 쫓고 가장 가치 있는 추론 능력을 희석시킬 수 있다**. 배경에 최강 추론 모델을 온전히 두고 전경에 가벼운 인터랙션 모델만 학습하면 항상 현재 최강의 "뇌"를 쓸 수 있다.

### Solution 1: 빠른 사고는 필러, 느린 사고는 답변 (병렬)
- 빠른 사고가 500ms 내 짧은 홀딩 응답("잠깐 생각해 볼게요"), 느린 사고가 5-10초 추론 후 완전한 답. 느린 사고의 기법은 **test-time scaling**.
- 문제 1: **Overthinking simple questions** — "오늘 무슨 요일?"에 빠른 사고가 500ms로 정답을 냈는데 느린 사고가 10초 후 같은 답 반복 → 대화 리듬 파괴.
- 문제 2: **fast-slow 불일치** — 같은 문맥을 보지만 추론 경로가 완전히 갈라질 수 있음. 몇 초 사이에 시스템이 자기모순(예: "가격 좋아요, 사세요" → 8초 후 "해외 로밍 없어서 부적합") → 신뢰 붕괴. 근본 원인: 하나의 일관된 인지 활동이 아니라 두 독립 사고 과정, 조정 메커니즘 없음.

### Solution 2: 빠른 사고는 인터랙션, 느린 사고는 조언자 (status bar 경유)
- 느린 사고가 빠른 사고의 출력을 볼 수 있고, 사용자에게 직접 말하지 않고 **Agent Status Bar**(Ch2의 동적 메타정보 주입 메커니즘)로 제안. 백그라운드 비동기 실행, 말 사이 틈에 추론 계속. GPT-Live delegation과 Pine AI가 프로덕션 사례.
- 한계 1: **빠른 사고가 지시를 안 따를 수 있음** — 두 독립 추론 간 소통이 간접적·모호. status bar의 "가격 재확인 필요"를 "사용자에게 가격 수용 여부 묻기"로 오독(의도는 "재계산").
- 한계 2: **중간 추론 과정 비가시** — 느린 사고의 10초간 가치 있는 중간 결론을 빠른 사고가 못 봄. 그 사이 사용자가 끼어들면 제한된 이해로 답해야 함. "쪽지만 주고받고 서로의 풀이 종이는 못 보는 두 사람".
- 근본적 이론 한계: **"thinking while speaking" 불가** — 인간은 완성된 답을 머리에 만든 뒤 말하지 않고, 생각하며 단락 단위로 말한다. Solution 2에서 빠른 사고는 기다리는 동안 필러만 가능.

### Solution 3: 사고와 표현의 E2E 통합 (Step-Audio R1)
두 상보적 메커니즘:
1. **MGRD (Modality-Grounded Reasoning Distillation)** — "올바르게 생각하기" 해결. 배경 문제: **Textual Surrogate Reasoning** — 기존 오디오 언어 모델에서 "CoT가 길수록 성능이 나빠지는" 비직관 현상. 원인: 모델이 "생각"할 때 실은 텍스트 전사 기반 의미 추론을 하지 음향 특징을 분석하지 않음(예: 노래 감정 판단 시 "가사에 슬픔이 있다"이지 "단조 선율 + 하행 음고 윤곽"이 아님). CoT 데이터가 텍스트 모델이 만들어서 순수 텍스트 사고 패턴을 계승했기 때문.
   - 3단계: ① 같은 오디오에 여러 사고 과정 생성 → 음향 특징에 진짜 근거한 것만 선별(구체적 소리 파라미터 언급 여부로 판별: "말속도가 평소보다 40% 빠르고 음량이 크고 피치가 날카롭다"는 진짜 듣기, "부정적 단어를 썼다"는 텍스트 분석) ② 고품질 추론 궤적으로 재학습(audio CoT + text thought joint SFT) ③ RLVR로 사고 과정 생략 지름길 방지(복합 보상: 0.8 정확도 + 0.2 사고 형식). 반복 후 사고의 기반이 텍스트 추상에서 음향 분석으로 이동 — "1.2초에서 피치 윤곽이 급락"에 주목.
   - 학습: 5M 샘플 cold start + 5K RL 샘플, 데이터 필터링 pass@8 ∈ [3,6](중간 난이도).
2. **MPS Dual-Brain Architecture (Mind-Paced Speaking)** — "적시에 말하기" 해결. 인간 뇌의 사고 영역과 언어 산출 영역 분업에서 영감(이전 문장을 말하면서 다음 문장 구상). 두 모델: **Formulation Brain**(연속 추론 → reasoning segment 생성) + **Articulation Brain**(새 segment 수신 시 이전 segment들과 지금까지의 답변을 결합해 음성화). 병렬 파이프라인: t=0ms 분석 시작 → t=200ms 첫 reasoning segment → t=350ms 첫 음절 청취.
   - 모델 구성: Qwen2 오디오 인코더(25Hz, frozen) → 어댑터(↓12.5Hz) → Qwen2.5 32B 디코더.
- **Experiment 9-4 결과**(Table 9-1): Baseline(무사고 직답) Spoken-MQA 70.6% / URO-Bench 77.4 → **MPS Speak-First(제로 레이턴시) 92.8% / 82.5** → **MPS Think-First(~80 tok 레이턴시) 93.9% / 84.8** → 완전 TBS(레이턴시 무제한) 93.0%.
  - 흥미로운 발견: Speak-First가 사고 태스크에 미치는 영향이 미미(92.8% ≈ 93.0%) — CoT 초반부는 보통 문제 재진술이라 진짜 추론 전이기 때문. Think-First(93.9%)가 무제한 TBS(93.0%)보다 오히려 약간 높은 것은 segment 단위 생성·음성화가 단계별 supervision처럼 작용했을 가능성(단 오차 범위 내, 과대해석 금지). Spoken-MQA에서 Gemini 2.5 Pro(81.5%) 상회, 종합 83.6%.
- Solution 3의 대가: 한 모델이 최강 추론자이자 실시간 화자여야 해서 "움직이는 과녁" 문제 — 통합 경로는 계속 재학습 필요. 업계 분화: 최신 뇌를 마음대로 교체하고픈 프론티어 제품(GPT-Live, Grok Voice, Pine AI)은 Solution 2 decoupling에 베팅, 궁극의 자연스러움을 추구하고 전문 학습 비용을 감당할 수 있는 제품은 Solution 3.

### 9.6.4 fast-slow 인터페이스: 텍스트 말고 무엇을 전달할까
- Solution 2의 간과된 설계 차원: 느린 사고 → 빠른 사고 전달이 **텍스트 채널**(status bar 제안). 이해·디버깅 쉽지만 좁은 채널 — 느린 사고의 풍부한 중간 상태가 몇 문장으로 압축.
- **Latent Bridge**(실시간 게임 맥락): 빠른 반응 소형 모델(초당 수십 액션)과 느린 추론 모델(초당 1 사고)을 둘 다 freeze하고, 사이에 수천만 파라미터의 작은 "브리지"만 학습. 느린 모델의 hidden-state 결론을 몇 개의 "latent token"으로 투영해 빠른 모델 입력에 삽입(멀티모달 모델의 visual token 삽입과 같은 방식). 아이디어→텍스트→난부 표현 왕복 우회. Atari 여러 게임에서 텍스트 채널 대비 **+26%~+82%**, 스텝당 **약 5ms** 추가로 실시간 충족. (Bojie Li & Noah Shi, "The Latent Bridge: A Continuous Slow-Fast Channel for Real-Time Game Agents", arXiv:2606.24470, 2026)
- 정직한 경계: **fast-slow 협업이 도움되는지는 태스크 병목이 "생각을 못 해서"인지 "반응이 늦어서"인지에 달림** — 느린 사고자가 빠른 반응자보다 진짜 나을 때만 브리지가 성과(게임 전반에서 상관 r≈0.9). 순수 반응 속도 승부면 무용. 이 판단은 Computer Use의 "느린 전략가를 언제 부를 가치가 있는가" 질문의 예고.

## 7. 더 인간다운 음성 합성 (9.7)

- **전통 TTS의 "완벽함"이 문제**: 완벽히 유창하고 멈칫·필러 없는 음성은 기계 티가 난다. 인간 음성의 "불완전함"(멈칫, "음", "저기", 반복)은 결함이 아니라 사고 과정의 자연 신호. AI는 말하는 속도보다 빨리 응답을 생성하므로 그대로 합성하면 인공성이 드러남.
- 핵안: **멈칫 위치와 어조 결정을 메인 LLM에 위임**. LLM이 텍스트 + **control token** 출력: `[THINKING]`(1-2초 사고 멈칫 + "음…"), `[SEARCHING]`(짧은 멈칫 + 망설임), `[EMO:happy]`, `[SPEED:0.8x]`. LLM만이 복잡한 질문을 풀고 있는지, 사용자가 초조한지, 잡담인지 알기 때문.
- TTS는 멀티모달 생성기: 일반 텍스트는 음성, control token은 비언어 오디오(`[SIGH]`→한숨, `[LAUGH:small]`→작은 웃음, `[BREATH]`→숨 들이마심).
- 구현 두 경로: ① control token 네이티브 지원 자체 TTS 개발(최고 유연성, 전문 팀 필요) ② **voice cloning** — 같은 페르소나의 감정/속도/스타일별 레퍼런스 클립 수십 개 준비, control token 조합마다 최적 클립 선택(ElevenLabs, Fish Audio 등 API로 수 주 내 배포).
- **Experiment 9-5**: Fish Audio S1(3-10초 레퍼런스로 zero-shot 클로닝), 24개 레퍼런스 라이브러리(Emotion 4 × Speed 3 × Style 2). 3개 구성 비교: control token 없음(유창하지만 로봇) / 단일 레퍼런스(자연스럽지만 감정 단조) / 멀티 레퍼런스 라이브러리(인간 상담원에 근접).

## 8. Computer Use: GUI 자동화 에이전트 (9.8)

- 음성에 훨씬 많은 지면을 쓴 이유: 실시간 멀티모달 중 음성 기술이 가장 멀리 진행(직렬 → E2E → full-duplex → thinking while speaking의 전체 아크 완주) → 최고의 참조점. Computer Use와 로봇을 읽을 때 이 궤적과 비교하라.

### 핵심 루프: Perceive-Think-Act (Figure 9-7)
1. 현재 화면 스크린샷 2. 멀티모달 모델이 스크린샷+태스크 지시 → 사고 + 구체적 액션 출력 3. 실행 레이어가 실제 환경에서 액션 수행(마우스, 클릭, 타이핑) 4. 인터페이스 응답 대기 → 다음 스크린샷. 다단계 폼 작성은 10-20 루프 필요.
- 3대 설계 차원: **Action Space**, **Visual Grounding**, **Model Architecture**.

### 9.8.1 Action Space (Anthropic 정의 3종 도구, Figure 9-8)
1. **GUI operation tool (computer)**: 마우스(mouse_move, left/right/middle_click, double/triple_click, left_click_drag, down/up), 키보드(type — 글자당 12ms 간격으로 실제 타이핑 시뮬레이션, key 조합키, hold_key), scroll 4방향+수정키. 지각 액션: screenshot(학습 해상도로 스케일), cursor_position, wait.
2. **Command execution tool (bash)**: persistent bash 세션, 120초 타임아웃, sentinel string으로 완료 감지, 호출 간 환경 상태 유지(cd 유지 등).
3. **File editing tool (str_replace_editor)**: 문자열 매칭 기반 안전 편집(view/create/str_replace/insert/undo_edit) — 파일 전체 덮어쓰기보다 정밀, 무관한 내용 오수정 방지.
- 좌표 스케일링: 실제 해상도 ↔ 학습 해상도 변환.
- Experiment 9-6 관찰: **액션 사이클당 2-5초, 인간의 1/3~1/5 속도**. 그래도 일반 태스크에서 좋은 planning과 자율 분해 시연.

### 9.8.2 Visual Grounding (시각적 그라울딩) — 3가지 경로
1. **Set-of-Mark (SoM, 순수 시각 주석)**: Microsoft Research 2023, GPT-4V의 visual grounding 항해. 세그멘테이션 모델(SAM, SEEM)로 후보 영역 분할 + 번호 마커 오버레이 → 모델은 번호만 보고 → 시스템이 중심 좌표로 변환. DOM 불필요 → 네이티브 데스크톱 소프트웨어/게임에도 적용.
2. **Structured Element Indexing (구조화 요소 인덱싱)**: 인터페이스 자체의 구조 정보 활용. 브라우저 CDP로 DOM/접근성 트리 획득 → 상호작용 요소 자동 감지 → 고유 ID + bounding box 주석 + ID별 텍스트 목록 생성 → 모델은 ID 출력, 시스템이 중심 클릭(browser-use 방식). 토큰 절약은 안 되지만(주석 데이터 전송) **정확하고 안정적 로컬라이제이션**, 세그멘테이션 모델의 누락/오탐 회피. 공통 장점: "좌표 예측"이라는 개방형 문제를 "주석된 요소 중 하나 선택"이라는 **폐쇄형 문제(객관식)**로 전환.
3. **Pure Coordinate Prediction (순수 좌표 예측)**: 주석 없이 모델이 직접 좌표 출력(SeeClick, Claude computer use). 대규모 GUI 스크린샷-요소 위치 데이터로 학습된 비전 모델 필요. **학습 해상도 의존성**: Claude는 XGA(1024×768), WXGA(1280×800), FWXGA(1366×768)로 학습 — 입력 해상도가 다륻면 좌표가 체계적으로 시프트. → **양방향 좌표 스케일링** + **종횡비 기반 목표 해상도 선택**(비균등 스트레칭 방지). 예: 2560×1440(16:9) → FWXGA 1366×768로 축소 → 모델 출력 (683,384) → 역매핑 ≈ (1280,720).
- 선택 기준: **구조 정보 가용 시 DOM/접근성 트리 우선**. 불가 시(Photoshop 같은 네이티브, Canvas/WebGL, 게임) 시각 주석 또는 좌표 예측. 둘 다 작은 요소와 빽빽한 인터페이스에서 어려움.

### 9.8.3 동적 화면을 보는 Computer Use — Agent-Computer Observation Interface (AOI)
- 기존 암묵 가정: **화면은 정적** — 스크린샷 → 추론 → 클릭 → 다음 스크린샷. 실제 화면은 영상 재생, 수 초 만에 사라지는 알림, 회의 오디오. 3-5초마다 한 번 눈 뜨고 귀가 없는 에이전트는 두 프레임 사이의 모든 것에 눈멀고 귀먾음. 화면 녹화 시청, 회의 참여, 음성 안내 따라가기, 사라지기 전 대화상자 잡기 — 이 카테고리 전체가 사실상 불가.
- 재설계 대상은 "액션 인터페이스"가 아니라 **"관찰 인터페이스"**. 핵심: **관찰(연속, 적응적, 멀티모달)과 액션(이산)의 분리** — 어떤 기성 Computer Use 모델과도 재학습 없이 붙는 지각 미들웨어. 3개 "gated" 컴포넌트:
  1. **Inter-frame keyframe capture**: 매우 싼 픽셀 게이트로 거의 변화 없는 프레임 스킵 → 작은 모델로 의미 있는 변화 판정 → 변화 시에만 프레임 캡처(정적 화면은 거의 제로 비용).
  2. **Volume-gated speech transcription**: 소리가 있을 때만 음성 인식 호출 → 에이전트에게 처음으로 "귀".
  3. **관찰을 영속적 텍스트 기술로 변환**(가장 중요): 캡처된 프레임을 한 문장으로 기술("팝업이 릴리스 날짜가 4월 28일로 바뀌었다고 알림") — 원본 이미지가 나중에 문맥에서 지워져도 텍스트가 메모리에 남아 동적 정보를 전달.
- **반직관적 발견: 정작 중요한 것은 프레임 선택이 아니라 선택된 프레임을 영속 텍스트로 바꾸는 것 — 텍스트가 LLM 에이전트가 가장 잘 다루는 모달리티이기 때문**. 7B부터 프론티어까지 8개 모델에서 재학습 없이 **+17~+48 퍼센티지 포인트** 향상, 음성 태스크에서 격차 최대. 단 만능 설정 아님 — 일부 최신 모델에서는 이미지 토큰 과다 주입이 추론을 밀어내 성능 하락 → **모델별로 컴포넌트 선택**. SoM vs 좌표 예측과 같은 교훈: 지각 방식에 은탄은 없고 모델 기질에 맞게 구성. (Bojie Li & Noah Shi, "Agent-Computer Observation Interfaces Enable Dynamic Computer Use", arXiv:2606.29472, 2026)

### 9.8.4 모바일: 생태계 장벽이 기술보다 어렵다
- 기술 차이: 마우스 좌표 대신 접근성 서비스 API(Android AccessibilityService)로 요소 읽기/클릭/입력. 같은 (x,y)가 탭/롱프레스/스와이프 시작점일 수 있어 제스처 타입 명시 필요. 벤치마크: AndroidWorld(Ch6).
- 진짜 장벽은 **생태계**: AI 어시스턴트가 WeChat/Taobao/Alipay 같은 앱을 대신 조작하려 하면 플랫폼 제한에 부딪힘. 근본 원인은 **비즈니스 모델 충돌**: 전통 인터넷 앱의 수익화는 트래픽과 주목(광고 노출, 추천 유도, 충동구매)인데 에이전트는 광고 무시, 충동구매 없음, 목표 직행 → 플랫폼 수익 기반 침식. CAPTCHA 같은 기술 대응을 넘는 **구조적 이해충돌** — 단기 해결 어렵고 순수 기술 문제보다 소비자 채택에 더 큰 장애.

### 9.8.5 실시간 성능: 미해결 핵심 과제
- OSWorld(Ch6): 초기 범용 모델 성공률 약 20% → 전문 모델과 강력 범용 모델이 인간 수준에 접근 중. 하지만 성공률은 종점이 아니다 — 병목이 "정확히 할 수 있는가"에서 **"빨리 할 수 있는가"**로 이동.
- **OSWorld-Human efficiency 연구**: 태스크가 성공핼도 에이전트는 인간보다 현저히 많은 스텝 필요, 태스크가 진행될수록 스텝당 추론 레이턴시 증가(문맥이 길수록 결정이 느려짐 → 후반 스텝이 초반보다 훨씬 오래 걸림). 인간이 수십 초에 하는 문서 서식 수정을 에이전트는 수 분. **인간 수준 정확도 ≠ 실용적 사용성; 효율이 진짜 병목**.
- 근본 원인은 음성과 동일: 직렬 "screenshot-think-click" 루프의 단계별 지연 누적. 더 깊은 문제: **현재 Computer Use는 미리 생각할 수 없다** — 페이지 로딩 중에 다음 클릭 위치를 계산해 추론과 실행을 겹칠 수 있다면 총 레이턴시 대폭 절감(음성의 thinking-while-speaking, Ch4의 continuous thinking과 같은 요구 = **thinking-while-operating**).
- 음성과 달리 Computer Use 루프 자체를 빠르게 하는 체계적 핵안은 아직 없음. 단 **fast-slow decoupling 우회로**가 실증됨: 느린 Computer Use 에이전트를 빠르게 만들기 어려우면 **사용자를 기다리게 하지 마라** — 빠른 모델(음성) + 느린 모델(컴퓨터 조작) 동시 운용. 둘은 최소한의 **"plain text contract"**로만 소통: 느린 에이전트가 액션마다 rolling status summary 갱신("폼 작성 중, 생년월일 필요"), 빠른 에이전트가 이걸로 실시간 응답하고 사용자의 구두 정보를 느린 쪽에 전달. **결정적으로, status summary가 완료를 확인하기 전까지 빠른 에이전트는 절대 "다 됐다"고 말하면 안 됨**. 실험: 단일 모델 대비 음성 응답 약 15배 빠름(중앙 레이턴시 0.58초 vs 8.64초), 태스크 성공률 손실 없음. 텍스트 채널 제거 시 성공률 0으로 붕괴. 이 "plain text contract"가 곧 Ch2의 Agent Status Bar 개념. (Bojie Li & Noah Shi, "Talking While Acting: Real-Time Voice for Slow Computer-Use Agents", 2026 forthcoming)

## 9. 로봇 조작 (9.9) — 요약 수준

- 음성=청각, Computer Use=시각 모달리티의 레이턴시 싸움. 로봇은 더 혹독: **액션이 비가역적**(충돌 한 번이 파손).
- **하드웨어가 병목이 아니라 알고리즘이 병목**(범위 한정: 시각 피드백 중심 가정용 조작 태스크): XLeRobot — $1,000 미만 양팔 주행 로봇이 VR 원격조작으로 다양한 가사 수행. 원격조작 레이턴시 100-200ms. 단 촉각 센싱 부재와 덱스터러스 핸드의 비용/신뢰성은 여전히 하드웨어 한계.
- **Two-layer architecture**: 느린 **long-horizon planning**("주방 청소" → 하위 목표 시퀀스 분해) + 빠른 **VLA control**(Vision-Language-Action — 각 동작 실행, 제어 신호 연속 출력). 음성의 fast-slow와 평행하지만 분할 차원이 다름: MPS는 사고/표현 분리, 로봇은 전역 planning/실시간 실행 분리.
- **Action Chunking**: VLA 추론 1-10Hz vs 전통 제어 50-1000Hz의 격차(1-3자릿수) 해소 기법. 한 번 추론으로 미래 액션 시퀀스 생성 → 제어 스레드가 고주파로 리플레이(추론 레이턴시를 시퀀스 실행 시간에 상각). 트레이드오프: 청크가 길수록 부드럽지만 그 구간 새 시각 입력 없어 돌발 변화 반응 느림. π₀: 50Hz에서 25-50개 액션/청크(0.5-1초). ACT(Zhao et al., 2023) 최초 제안, π₀/OpenVLA-OFT 채택. 원조 OpenVLA는 단일 스텝 autoregressive ~6Hz로 동작 끊김이 최대 비판점.
- VLA 학습: 주로 **imitation learning (behavior cloning)** — 대규모 인간 시연으로 관찰→액션 매핑. OpenVLA, RT-2, π₀. RL은 최근 보완 기법이나 단일 태스크 성과는 좋아도 일반화 부족(SimpleVLA-RL — 태스크별 개별 학습, zero-shot 일반화 아님).
- 액션 표현 두 경로: **discrete action tokens**(RT-2 — 연속 액션을 토큰으로 이산화해 autoregressive; OpenVLA — DINOv2+SigLIP + Llama 2 7B, Open X-Embodiment(20+ 로봇 플랫폼) 사전학습 후 소량 플랫폼 파인튜닝; 완전 오픈소스) vs **continuous trajectory generation**(π₀ — flow matching으로 노이즈에서 연속 궤적 디노이징; action chunking과 자연스럽게 결합, 정밀 조작에 유리). 비유: 이산 토큰은 메뉴에서 명령 고르기, 연속 궤적은 화가가 곡선 전체를 스케치.
- Long-horizon planning: **Gemini Robotics-ER 1.5**(Embodied Reasoning 특화) — 15개 학술 벤치마크 평균 62.8% vs GPT-4o 60.6%, Gemini 2.5 Pro 59.3%. 공간 이해, 시간 추론(행동 결과 예측), 태스크 시퀀싱, thinking/도구 호출 네이티브.
- **Sim2Real**: 시뮬레이션은 현실을 완벽 재현 못 함 → **domain randomization**(물리/시각/동역학 파라미터를 넓게 랜덤화해 정책이 변동에 강건한 표현 학습 — "극도로 다양한 학습 분포 → 현실은 그저 하나의 샘플"). 성공 사례: OpenAI Dactyl(루빅스 큐브, ADR), ETH ANYmal(설원/자갈). 실전 두 필수 공정: ① **랜덤화 범위 캘리브레이션**(실측으로 분포 측정, 좁으면 현실 변동 누락, 넓으면 "모든 것을 견디지만 아무것도 못하는" 준최적 정책; 실기 성능 떨어지면 단계적 확장) ② **visual alignment**(침머라 포즈 정밀 정합 + greenscreen 배경 치환으로 실제 배경 합성).
- Experiment 9-10: LeRobot + ManiSkill, RGB만으로 PPO 학습(1024 병렬 환경, 25-40M 스텝, 단일 4090으로 ~1시간에 시뮬 성공률 >90%) → 실물 SO100에 zero-shot 배포(15Hz, 2.5cm 큐브 잡기). 한계: 학습 분포 밖 형상/재질은 성공률 급락.

## 10. 챕터 요약 + Thought Questions (Ch9)

요약: 세 시나리오 모두 레이턴시와 멀티모달리티라는 쌍두 과제. 음성은 직렬 → E2E/full-duplex, 분리 사고 → thinking while speaking까지 진화. Computer Use는 벤치마크 정확도는 인간 접근이나 스텝 수·스텝당 레이턴시에서 효율 격차 — 체계적 핵안 부재. 로봇(시각 유도 조작)은 병목이 하드웨어 → VLA 제어층의 태스크 간 일반화 능력으로 이동(촉각/덱스터러스 핸드는 미해결 하드웨어 한계).

Thought Questions (번역):
1. ★★ E2E 음성 모델은 레이턴시를 줄이지만 모듈성을 잃어 특정 단계 오류 디버깅이 어렵다. E2E 음성 에이전트의 관측가능성(observability) 시스템을 어떻게 설계할 것인가?
2. ★ Step-Audio R1의 "thinking while speaking" — 인간은 생각 다 안 하고 말했다가 자기 수정하거나 필러를 쓴다. 에이전트의 thinking while speaking이 이런 인간 특성까지 모방해야 하는가?
3. ★★ SoM/DOM 인덱싱은 UI 요소 감지·주석이 선행 필요. 비표준 컨트롤이나 동적 요소로 주석이 불완전하면 좌표 예측으로 폴드백해야 하는가?

5. ★★★ 음성·Computer Use·로봇의 공통 추세는 직렬 → E2E. 이 추세가 계속되면 5년 후 에이전트 인터랙션 레이어는 어떤 모습일까?
6. ★★★ 현재 Computer Use는 이산적 "스크린샷→액션→스크린샷" 루프라 시간적 시각 이해 태스크 불가. 연속 시각 스트림 이해를 지원하도록 지각 레이어를 어떻게 재설계할까?
7. ★★ Canvas/WebGL 등 구조 정보 없는 인터페이스가 늘어난다. 순수 시각 경로에 베팅할 것인가, 구조+시각 양 경로를 유지할 것인가? 양 경로 유지의 비용과 이득은?
8. ★★ action chunking은 추론 레이턴시를 실행 시간에 숨기지만 실행 중 환경 돌변(물체 이동) 시 사전 생성 시퀀스가 무효화된다. 효율과 반응성을 어떻게 균형 잡을까?
9. ★★★ 세 시나리오 모두 "perceive-think-act" 루프의 레이턴시 문제와 fast-slow 병렬화로 진화 중(음성: 말실수 후 수정, Computer Use: 일단 클릭 후 확인, 로봇: 한 걸음 가고 확인). 빠른 사고 기반 액션이 비가역적 결과로 이어지지 않게 하려면?

## Ch9 실무 함의 (에이전트 스킬/자동화 빌더 관점)

- **"직렬 파이프라인의 지연 누적"은 음성만의 문제가 아니다** — 스크린샷-추론-클릭 루프, 다단계 도구 체인 등 모든 에이전트 루프에 적용. 각 단계를 스트리밍/병렬화해 겹칠 수 있는지 먼저 검토하고, 겹칠 수 없는 구간(VAD처럼 판정 자체가 대기인 경우)은 아키텍처를 바꿔야 함을 인식.
- **E2E vs cascade의 선택 기준은 "최신성"이 아니라 "중간 표현(병목)이 어떤 정보를 담는가"** — 텍스트로 태스크 정보를 다 담을 수 있으면 cascade/self-cascade가 더 정확하고 디버깅 쉬움. 자동화 파이프라인 설계 시 "이 인터페이스가 버리는 정보가 태스크에 필요한가"를 물어야 함.
- **fast-slow decoupling은 범용 패턴**: 느린 컴포넌트(브라우저 조작, 무거운 검증)를 빠르게 못 만들면 빠른 인터랙션 레이어로 대기를 숨기고, 둘 사이는 status summary("plain text contract" = Agent Status Bar)로 연결. 완료 선언은 반드시 느린 쪽 확인 후.
- **GUI 자동화는 구조 정보(DOM/접근성) 우선, 시각은 폴드백** — 브라우저 자동화라면 좌표 예측보다 요소 인덱싱이 정확하고 안정적. 학습 해상도-실해상도 불일치 같은 스케일링 함정 주의.
- **"관찰을 영속 텍스트로 변환"이 프레임 선택보다 중요** — 동적 환경(알림, 갱신되는 대시보드)을 다루는 자동화라면 이벤트를 한 문장 텍스트 로그로 남기는 미들웨어가 재학습 없이 큰 성능 향상을 준다.

# Chapter 10. Multi-Agent Collaboration (멀티에이전트 협업)

## 0. 서두: 왜 멀티에이전트인가

- OpenAI 5단계 AI 능력 스케일: L1 Conversationalists → L2 Reasoners → L3 Agents → L4 Innovators → **L5 Organizations**. 멀티에이전트는 L5로 가는 한 경로로 제시되지만, L5는 능력 레벨이지 아키텍처 요구사항은 아님(충분히 강한 단일 에이전트도 원칙적으로 도달 가능). 현재 공학 현실에서는 단일 에이전트가 모델 능력과 컨텍스트 윈도우에 제약됨.
- 더 근본적인 관점: **집단의 지능이 개체를 초과할 수 있다** — 인류 문명이 증거. Google DeepMind "From AGI to ASI"(arXiv:2606.12683, 2026)는 "large-scale multi-agent collectives"를 ASI 경로로 제시. 멀티에이전트는 컨텍스트 윈도우 우회책 이상 — "전문가 수준 AI"에서 "인류 전체 초월"로 가는 근본 경로일 수 있음.

## 1. 분류 프레임워크: 두 설계 차원 (10.1)

### 차원 1: Shared vs Non-Shared Context (가장 근본적 아키텍처 결정)
- **Shared context**: 후속 에이전트가 선행 에이전트의 완전한 대화 이력과 trajectory를 계승. 각 단계에서 system prompt와 도구 세트가 바뀌면 정체성/책임/능력이 달라지므로 다른 에이전트로 간주. 장점: 정보 손실 제로. 과제: 컨텍스트 급팽창.
- **Non-shared context**: 각 에이전트가 독립 문맥 유지, 타 부서 협업처럼 명시적 통신으로만 정보 교환. 장점: 모듈성/격리/확장성(새 에이전트 추가 시 기존 로직 무수정, 인터페이스와 데이터 포맷만 정의). 과제: 정보 동기화 복잡.
- 통신 메커니즘 3종 (IPC의 두 패러다임 — shared memory / message passing — 에 대응):
  1. **Tool call parameters**: 상류가 하류 에이전트 도구의 파라미터로 구조화 데이터 전달(동기 메시지 패싱).
  2. **Shared file system**: 공유 디렉터리의 중간 산출물로 교환(= shared memory). 대형 산출물/영속성 필요 시.
  3. **Message bus**: 전용 중개자 경유 비동기 메시지(= 비동기 메시지 패싱). 병렬 협업에 적합.
  - Go 격언: "Do not communicate by sharing memory; instead, share memory by communicating." 공유 메모리는 빠류이지만 동시성 해저드 관리 필요, 메시지 패싱은 오케스트레이션 코드가 늘지만 데이터 소유권이 명확.
- OS 비유: **shared-context 에이전트 ≈ 스레드**(주소 공간 공유, 전환/통신 저렴, 격리 약함), **non-shared ≈ 프로세스**(독립 주소 공간, 강한 격리, 명시적 IPC 필요).
- 선택 기준 (Table 10-1): 하위 태스크 수(2-3개 → shared / 병렬 많음 → non-shared), 컨텍스트 윈도우, 병렬성(shared는 기본 직렬 / non-shared는 대규모 병렬), 정보 격리 필요성(예: 보안 리뷰는 타 에이전트 난부 문맥을 받으면 안 됨), 비용(non-shared는 총 토큰이 수 배~한 자릿수 높음).
- **경험칙: 누적 문맥이 윈도우의 50% 초과 예상이면 공유하지 마라**(엄밀 임계값 아닌 휴리스틱). 정보 손실 제로가 정확성의 하드 요건이면 공유. 실무는 혼합: 초반 몇 단계는 공유, 이력이 커지면 non-shared로 전환 + 상류가 전달 내용을 선택하는 explicit handoff.

### 차원 2: Collaboration Topology (협업 토폴로지)
- shared-context는 토폴로지가 대개 "역할 전환 시퀀스"로 퇴화(전달할 정보를 고를 필요가 없어서). 그래서 챕터는 non-shared의 3개 셀만 상술 (2×3 매트릭스):
  1. **Peer Collaboration Pattern**: 2-3개 대등 에이전트의 반복 개선 루프(논문 집필-첨삭 비유).
  2. **Manager Pattern (Orchestration)**: 중앙 Manager가 계획/스케줄링, 하위 에이전트가 하위 태스크.
  3. **Decentralized Pattern**: 런타임 중앙 통제 없이 에이전트 간 피어 협업.

## 2. 언제 멀티에이전트가 진짜 단일보다 나은가 (10.2) — 핵심 판별 기준

**핵심 질문 하나: "협업이 단일 에이전트가 답을 만들 때 얻을 수 없었던 정보를 제공하는가?"**

Table 10-2 (정보 이득 비교):
- 같은 모델의 self-review(자기 출력 재독해): 신규 정보 없음 → **보통 무효하거나 오히려 해롭다**.
- 같은 텍스트에 대한 에이전트 간 토론(debate): 없음 → 동일 연산량의 단일 에이전트와 동등.
- 리뷰어가 **테스트 실행 결과**로 코드 리뷰: 있음(실행 피드백) → 유의미한 향상.
- 리뷰어가 **렌더링 스크린샷**으로 프론트엔드/PPT 리뷰: 있음(시각 피드백) → 유의미한 향상.
- 리뷰어가 **외부 도구로 사실 검증**: 있음(도구 피드백) → 유의미한 향상.

근거 연구:
- **RLEF**(arXiv:2410.02089, 2025): 코드 실행 피드백을 쓰도록 RL 학습시키면 다수 독립 샘플링을 크게 상회. 매 반복이 실제 실행 결과(컴파일 오류, 테스트 실패, 런타임 예외)라는 **작성 시점에 존재하지 않던 정보**를 도입.
- **WebGen-Agent**(arXiv:2509.22644, 2025): 스크린샷+VLM 기술의 다단계 시각 피드백으로 Claude 3.5 Sonnet 벤치마크 26.4% → 51.9%(거의 2배).
- 학계(토론 방식은 단일로 충분)와 실무(멀티가 낫다)의 표면적 모순 해소: 효과 있는 시스템은 실행/렌더링/도구의 **외부 피드백**을 추가하기 때문.

**Step budget**: 구글 2025 논문 "Budget-Aware Tool-Use Enables Effective Agent Scaling" — **단순히 스텝을 더 준다고 성능이 오르지 않음**. 표준 에이전트는 "budget awareness"가 없어 300스텝을 줘도 얕은 탐색 후 빠르게 포화(plateau). 남은 자원에 맞게 전략을 적응시키는 메커니즘 필요(초반 광범위 탐색 → 후반 심화). 2026 BAVT(Budget-Aware Value Tree Search): 스텝 레벨 가치 평가, 잔여 예산 비율로 탐험-활용 균형 조정.
- 설계 함의: Manager는 하위 에이전트에 태스크 복잡도별 스텝 예산 차등 배정 + 현명한 사용 가이드(계획→구현→테스트→개선).

**비용**: Anthropic 공개 — 자사 멀티에이전트 리서치 시스템은 일반 대화의 **약 15배 토큰** 소비, 토큰 사용량만으로 성능 차이의 약 80% 설명. 멀티에이전트 이득이 수 배~한 자릿수 비용을 정당화할 만큼 커야 함. 아니면 잘 튜닝된 단일 에이전트가 낫다.

## 3. Shared Context 협업 (10.3)

### 10.3.1 Multi-Stage Role Switching (다단계 역할 전환)
- 정의 논쟁: Ch1 용어로는 **workflow-style orchestration**(실행 경로 사전 정의)이며 "진짜 멀티에이전트가 아니다"는 주장에도 일리가 있음. 그러나 단계별 system prompt/도구/집중점 부여 + 단계 경계를 품질 게이트로 쓰는 실용 이득으로 멀티에이전트 패턴으로 취급.
- 메커니즘: 새 인스턴스/프로세스 생성 없이 **같은 실행 세션에서 system prompt와 도구 세트만 교체**. 대화 이력과 태스크 상태는 연속 보존.
- Experiment 10-1 (3단계): ① 요구사항 분석가(ask_clarifying_question, save_requirement, complete_requirements_analysis — "구현 서두르지 마라") ② 소프트웨어 엔지니어(write_file, read_file, execute_code) ③ 코드 리뷰어(run_linter, run_tests, analyze_complexity; 심각한 이슈 시 request_revision으로 구현 단계 롤백, 통과 시 approve_code). 단계 전환 트리거는 특정 도구 호출.

### 10.3.2 Cross-Domain Role Switching (교차 도메인 역할 전환)
- Experiment 10-2: 5개 역할 — **triage**(프런트 데스크, 유일한 도구는 transfer_to_agent, 라우팅 규칙 내장), **research**(web_search), **coding**(execute_python), **data_analysis**(calculate/descriptive_stats), **writing**(count_characters 포함).
- 핵심 도구 **transfer_to_agent(target_role, reason)**: 호출 시 시스템이 현재 대화 이력 저장 → 목표 역할의 프롬프트/도구 로드 → 이력 전달 → 실행 재개. 체인 예: triage → research → data_analysis → writing → triage.
- 주의 요건: 순환 핸드오프(A→B→A 무한 전환) 방지 가드.

## 4. Non-Shared Context 협업 (10.4)

### OS 대응표 (Table 10-3) — 이 챕터의 사고 골격
| OS | 멀티에이전트 |
|---|---|
| 프로그램(실행 파일) | Static prefix(system prompt + 도구 정의) |
| 프로세스 메모리 | Trajectory |
| CPU | LLM |
| 커널 | Agent runtime |
| 시스템 콜 | Tool call |
| fork | spawn_subagent |
| kill | cancel_subagent |
| ps | list_agents |
| exit code / wait() | 하위 에이전트의 구조화 요약 반환 |
| 공유 메모리 / 메시지 패싱 | 공유 파일 시스템 / 메시지 패싱 |

- LLM은 CPU: 상태 없이 여러 에이전트 사이에서 시분할 — "context switch"라는 용어 자체가 OS 차용. **더 강한 모델로 교체핼도 에이전트는 같은 에이전트** — 정체성과 메모리는 prefix와 trajectory에 있지 모델 가중치에 없다.
- **1970년대 Actor model**(Hewitt et al., IJCAI 1973)과 동일 기본 구조(사유 상태, 비동기 메시지, 새 멤버 생성) → 멀티에이전트 = LLM 기반 Actor model. OS/분산 시스템 지식이 직접 적용됨.
- **비유가 깨지는 지점: 프로세스는 바이트를 비트 단위로 정확히 전달하지만 에이전트는 의미를 전달하고, 재전달마다 왜곡 가능** — Failure Modes의 새 문제.

### 10.4.1 에이전트 관점의 파일 시스템 — Virtual File System 4개 영역
단일 스토리지가 아니라 출처/수명주기/권한이 다른 스토리지를 하나의 디렉터리 트리에 마운트. 통합 인터페이스 read_file/write_file/list_dir. **"기본 격리, 공유는 명시적 선언"** 원칙. (Table 10-4)
1. **Agent-Specific Workspace (Scratchpad) `/scratch/<id>`**: 인스턴스 전용 사유 디렉터리(중간 산출물, 임시 파일, 디버그 로그). 인스턴스와 운命 공유, 타 에이전트/사용자 비가시. 목적: 임시 파일 덮어쓰기 방지 + 메인 에이전트 문맥 슬림(하위 에이전트의 시행착오는 자기 작업공간에, 최종 산출물만 공유 공간으로 — Ch4 "구조화 요약 반환"의 스토리지 대응물).
2. **Multi-Agent Shared Workspace `/workspace/shared`**: 협업 에이전트들 + 사용자가 읽고 쓰는 협업 구역. 아티팩트 교환의 주 매체. 태스크 기간 영속. **동시성 충돌 핫스팟** — optimistic locking/worktree 격리 필요.
3. **Mounted External Resources `/mnt/gdrive`, `/mnt/notion`**: 사용자 인가 외부 소스를 어댑터로 마운트. 3특성: 외부 권한에 제약(소스 시스템의 사용자 권한이 가시성 결정), 레이턴시 높고 일관성 약함(결과적 일관성으로 취급), 주로 온디맨드 읽기 전용(쓰기는 신중 — 오기록 시 사용자 실데이터 오염). 통합 인터페이스가 데이터 소스별 전용 도구를 없애주지만 성능/보안 차이를 가림 → 마운트 레벨에서 읽기전용/타임아웃/자격증명 경계 명시 관리.
4. **Built-in System Resources `/skills`**: 시스템 사전설치 전역 공유 읽기 전용(Ch2/4의 Skills — 지식 문서와 스크립트, progressive disclosure로 접근), 레퍼런스 매뉴얼, 템플릿. 세션 간 안정, 동시성 제어 불필요.
- **"파일 경로 = 범용 인터페이스"**: 경로 문자열을 교환 단위로 — 내용을 문맥에 싣지 않고 경로만 전달(Ch4). Ch5 "파일 시스템은 에이전트의 허브"의 멀티에이전트 확장.

### 10.4.2 에이전트 간 통신과 제어 (control plane) — 간과되기 쉬운 4가지
1. **Message Passing**: 소수 고정 토폴로지는 point-to-point(send_message_to_agent_b). 에이전트 수 증가+비동기 병렬이면 연결 수가 제곱 증가 + 송수신 동시 온라인 필요 → message bus(Redis Pub/Sub — 경량 즉시 배달이나 비영속, RabbitMQ — 디스크 영속). 메시지는 구조화 **envelope**(sender ID, target/broadcast, type — task_assigned/status_update/result/terminate, JSON payload). 통일 포맷이 라우팅 신뢰성과 협업 체인 추적(디버깅 핵심)을 보장.
2. **Status Query (가장 과소평가된 영역)**:
   - RPC식 pull 인터페이스(get_subagent_status → running/completed/failed + 진행률)는 기대보다 쓸모없음: 하위 에이전트는 생성 즉시 실행되어 완료/실패까지 달리지 배치 잡처럼 큐 상태를 순환하지 않음(Unix에서 PID 폴리잉 안 하는 것과 같음). 폴리잉 딜레마: 자주 하면 토큰 낭비, 드물면 반응 지연.
   - **메시지 패싱으로 상태 얻기**: 메인이 "어떻게 돼 가?" 메시지 → 하위가 적절한 시점에 회신(비동기, 매니저가 IM으로 진행 상황 묻는 것과 같음). 또는 하위가 마일스톤에서 능동 보고(버스에 status_update 발행). 상태 어휘는 통일된 상태기계(executing, needs input, completed, failed — A2A의 태스크 수명주기와 동일).
   - **공유 파일 시스템으로 상태 얻기**: 가장 철저한 형태는 **trajectory persistence** — 하위 에이전트가 각 trajectory 이벤트를 JSON으로 append(세션당 1파일, 이벤트당 1행 = JSONL). 메인은 프로토콜 없이 파일을 읽어 전체 실행 검사: 어떤 도구 호출 중인지, 최근 스텝, 반복 실패 루프 정체 여부. 하위의 문맥을 점유하지 않고 협조에 의존하지 않으며 최고 관찰 세분성.
   - 단 trajectory는 수만 토큰 → 실무는 **약속된 progress file**(progress.md를 항목 완료마다 갱신). 가볍고 언제든 읽기 가능.
   - **Stuck detection**: progress.md/trajectory 파일의 최종 수정 시각이 N분 이상 불변이면 비활성 간주 → 타임아웃 안전망(Ch4 Heartbeat/monitor_shell과 상통).
   - **Trajectory persistence의 더 큰 가치**: Ch1 결론 "에이전트 문맥 = static prefix + trajectory" — trajectory가 에이전트의 전체 상태. 실시간 파일 영속화 = 항상 완전한 checkpoint 보유 → 크래시/정전/세션 종료 후 trajectory 리로드 + prefix 전첨으로 중단 지점 재개. **Claude Code/Codex CLI의 세션 resume이 이 방식**. DB의 WAL(write-ahead log)과 같은 아이디어. 멀티에이전트 시스템에서 하위 에이전트는 자연히 복구 가능(recoverable), 감사 가능(auditable), 인수인계 가능.
3. **Execution Termination (SIGTERM vs SIGKILL)**:
   - **Graceful termination 우선**: terminate 신호 → 하위가 현재 스텝의 안전 지점에서 응답, 자원 정리(브라우저 세션, 보류 파일, 락 해제), ack 송신 후 종료. 전제: 하위가 루프에서 주기적으로 종료 신호 확인(Ch4 interrupt 메커니즘, Go의 ctx.Done() 폴리잉에 대응).
   - **Forced termination은 폴드백**: 무응답 시 프로세스 직접 종료 — dangling 자원/미완 쓰기 위험.
   - **Cascading termination의 race condition**: 여러 하위가 거의 동시에 성공 보고 가능 → 락/멱등 설계로 하나의 성공만 수락 + 종료 신호 1회 브로드캐스트.
   - 메인 종료 후 실행 중 하위는? Go의 context처럼 **생성 관계를 따라 종료 전파**(고아 자식 방지). 정말 장기 백그라운드 에이전트(nohup류)가 필요하면 새 수명주기 트리로 시작(context.Background()에 대응) — 부모와 함께 종료하지 않음을 명시 선언.
4. **Resource Management and Scheduling**: 프로세스 세계의 희소 자원은 CPU/메모리, 에이전트 세계는 **토큰, 돈, 동시성 예산**. Manager/runtime 책임: 하위 시작 시 스텝/토큰 예산 설정+초과 중단, 어려운 태스크는 강한 모델/기계적 태스크는 저비용 모델, 동시성 상한(API 쿼터 고갈 방지), 긴급 태스크 도착 시 선점(preemption). CPU 스케줄링보다 미성숙하지만 멀티에이전트 시스템의 비용 천장을 결정.

### 10.4.3 Peer Collaboration Pattern
- 2-3개 대등 에이전트의 다라운드 피드백. 핵심 가치는 **인지 다양성(cognitive diversity)**. 구현이 가장 단순(역할 2개 + 통신 메커니즘 + 종료 조건) — 프로토타이핑에 이상적.

**Premature Termination (조기 종료) 3형태** — peer 협업이 맞서는 주요 실패:
1. **Lazy fake-done**: 일부만 하고 전부 했다고 선언(코드만 쓰고 테스트/배포 안 한 채 "완료"; Pine AI가 심부름 2개 중 1개만 하고 "다 처리").
2. **Premature give-up**: 한 경로 막히자 전체 불가 선언(Pine AI는 전화/웹폼/이메일 경로가 있는데 전화 한 번 거절당하고 "불가" 보고).
3. **False success**: 루프가 실제로 닫히지 않았는데 완료로 믿음(전화로 환불 구두 동의, 그러나 앱에서 확인 단계 필요 — 사용자는 후속 조치 모르고 환불 미완).
- 공통 뿌리: **검증되기 전 "완료"는 모델의 주장일 뿐 증명이 아니다**.

**Loop Engineering**: 주장을 증명으로 바꾸는 것이 Ch1 진화 아크의 마지막 단계. 다음 작업 발견 → 실행 → 검증 → 진행 기록 루프를 설계하고, **멈춰도 되는지는 모델이 아니라 verifier가 결정**. 인간의 역할은 "프롬프트하는 조작자"에서 "루프를 설계하는 엔지니어"로. Addy Osmani가 2026년 6월 명명; Anthropic Claude Code 리드 Boris Cherny: "나는 더 이상 Claude에게 프롬프트하지 않는다. 내 일은 루프를 쓰는 것." 핵심 결론: **루프의 병목은 모델이 아니라 verifier** — 검증이 불신실하면 빠른 루프는 나쁜 출력을 더 빨리 완료로 마킹할 뿐. 명명 이전부터 선도 팀들(Pine AI 포함)은 이미 "루프 + 검증" 사용.

**Proposer-Reviewer 패러다임** (표준 peer 협업):
- Proposer가 코드 생성 → Reviewer가 실행 결과 렌더링 → VLM으로 품질 평가 → 구조화 개선 제안 → 기준 충족까지 반복. PPT 생성 예: R1 12페이지 5이슈 → R2 14페이지 2이슈 → R3 0이슈.
- **왜 단일 에이전트 자기 리뷰는 안 되나**: 신규 정보 없는 리뷰는 "한 번 더 생각하기"일 뿐.
  - Huang et al., "Large Language Models Cannot Self-Correct Reasoning Yet"(ICLR 2024): 외부 피드백 없이 GPT-4가 자기 답을 검토·수정하면 **정답을 오답으로 바꾸는 경우가 더 많아 정확도 하락**.
  - TACL 2024 서베이 "When Can LLMs Actually Correct Their Own Mistakes?"(arXiv:2406.01297): 신뢰할 수 있는 외부 피드백 없는 self-correction은 대체로 무효.
  - CRITIC(ICLR 2024): 외부 도구(검색엔진, Python 인터프리터) 검증으로 큰 향상, 도구 검증 제거하고 자기 평가만 남기면 향상 대부분 소실.
  - → **리뷰의 가치는 "다시 생각"이 아니라 생성 시점에 없던 신규 정보 도입**(테스트 결과, 렌더링 스크린샷, 컴파일 오류, 외부 검색).
- 단일 에이전트 자기 검토의 또 다른 문제: 렌더링 이미지 × N라운드 = 문맥 폭발(1080p 스크린샷 수천 토큰 × 14페이지 × 5라운드). 이원화하면 Reviewer는 현재 버전만 보고, Proposer는 텍스트 피드백만 누적 → 깨끗한 문맥.
- 적용 확장: 보안 리뷰, 콘텐츠 모더레이션, 코드 리뷰.
- Loop Engineering 패턴 매핑: human approval 폐루프 = Ch4 pre-approval(인간이 최종 리뷰어), 예산/라운드 캡 개방 루프 = Ch5 PPT 5라운드 제한, orchestrated sub-agents = manager pattern. **Loop Engineering은 새 아키텍처가 아니라 "루프 + 검증 + 종료 조건" 공통 프레임워크**.

**기타 peer 패턴**:
- **Debate**: 찬반 대립 대화로 문제 공간 탐색. 단 Tran & Kiela(arXiv:2604.02460, 2026): thinking-token 예산 동일 조건에서 멀티홉 추론 태스크에 **단일 에이전트가 5종 멀티에이전트 아키텍처(sequential, debate, ensemble, parallel roles, subtask-parallel)와 동등하거나 우세**. 설명: 정보론의 data processing inequality — 토론 참여자들이 동일 텍스트를 처리하며 직렬 전달은 정볼르 잃기만 하지 만들지 못함. 학술 논문의 토론 이득은 총연산량 증가에서 기인했을 가능성. **경계: 이 논증은 "직렬 전달" 병목만 겨냥 — 독립 다중 샘플링+집계(self-consistency, 다수결)나 생성-검증 난이도 비대칭 활용(생성-검증 분업)은 해당 없음**.
- **Brainstorm**: 독립 아이디어 생성 후 상호 영감(서로 다른 "사고 선호" = 다른 프롬프트/모델).
- **Panel Discussion**: 전문 도메인 관점 대표 에이전트들의 학제간 토의(대립이 아니라 상보).

### 10.4.4 Manager Pattern (중앙 조정)
- 하위 태스크 5개 초과, 동적 스케줄링, 복잡 의존성 시 필요. Manager = 프로젝트 매니저: 이해 → 분해 → 배정 → 추적 → 예외 처리(재시도/교체/계획 수정) → 결과 통합.
- 핵심 추상화: **전문 에이전트를 Manager가 호출하는 도구로 모델링**. Manager 입장에서 에이전트 호출 = 일반 도구 호출(요청 전송, 응답 수신). 확장 쉬움(새 능력 = 새 에이전트를 도구로 등록), 이질성 지원(에이전트별 다른 모델/프롬프트/도구/하드웨어).
- 하위 → Manager 반환은 **구조화 요약(결론, 핵심 발견, 산출물 파일 경로, 발생 문제)이지 전체 trajectory가 아님** → Manager 문맥이 하위 태스크 수에 선형으로만 증가. (Experiment 10-3의 Manager가 번역 본문이 아니라 파일 인덱스만 유지하는 이유)
- 고유 과제: Manager가 단일 병목(모든 하위 태스크 본질 이해 필요, 오판은 전체에 파급) + 전역 문맥 유지 부담.
- **Plan-and-Act 논문**(arXiv:2503.09572, 2025): Planner-Executor 구조에서 **약한 planner가 시스템 전체의 최대 병목** — planning 품질이 높으면 단순한 Executor로도 좋은 결과, 분해가 틀리면 최강 Executor도 무용. WebArena-Lite 54%. 교훈: **가장 강한 모델과 가장 정성 들인 프롬프트는 Manager(planner)에**. 단 Ch4의 "제안-검토 모델 능력은 비슷해야"와 모순 아님: 그건 리뷰 시나리오(리뷰어가 피검토자 추론을 따라가야 허점 발견), 이건 planning-execution 분업 시나리오. Executor 능력 균형 필요 여부는 하위 태스크 결합도에依存(최종 산출물을 하나로 조립해야 하면 최약 고리가 전체 품질 하락).

**Sequential Coordination**: Manager가 순차 호출, 선형 제어 흐름. 명확한 순차 의존성에 적합.
- Experiment 10-3 (책 번역): 단일 에이전트면 전서 용어집+번역 장+현재 단락+작업 흔적 누적으로 문맥 윈도우 초과 + "길 잃음"(2장과 8장의 용어 불일치, 존재하지 않는 용어 규칙 "기억"). Manager 패턴: **Glossary Agent**(전서에서 전문 용어 추출, 사전/번역 지침 참조, glossary.json 작성 후 소멸) → **Translation Agent ×N**(현재 장+용어집+지침만, 용어집 엄수, 신규 용어는 추정+표시, chapter{n}_zh.md) → **Proofreading Agent**(전체 번역문+용어집 일관성 검사, review_report.md) → **Manager**(태스크 기술, 계획, 호출 기록, 진행 상태만 — 본문 아닌 파일 인덱스 유지, 리포트 기반 특정 장 재번역 지시). **문맥 격리**로 각 에이전트 문맥 슬림+집중.

**Parallel Coordination**: 병렬 가능 시 message bus 인프라(게시판 비유 — 발행/구독, 비동기 논블로킹). Redis Pub/Sub(경량, 비영속) / RabbitMQ(영속). JSON envelope.
- **Lingtai (제품화 사례)**: 장수 에이전트의 로컬 파일 기반 홈. **main agent**(영속 허브, 계획/메모리 보유, Manager 위치), **daemon**(단명 병렬 워커 — 시끄럽고 경계 있는 태스크에 spawn 후 폐기, 결론만 보존 — "구조화 요약 반환"과 병렬 조정의 제품화), **avatar**(자체 메모리/메일함/책임의 영속 전문가 팀메이트). 지식은 각 에이전트의 영속 사유 메모리 파일, 스킬은 전원 공유 Markdown 플레이북(built-in system resources). 문맥 가득 차면 **molt**(정성스런 요약 작성 → 새 문맥으로 시작, 요약+영속 메모리 유지 — Ch2 문맥 압축 방식). 모델 교체핼도 에이전트 불변 — 정체성/메모리/능력이 프로젝트 디렉터리의 평문 파일로 존재: **"the agent is its files"**(Table 10-3 첫 두 행의 제품화: 프로그램과 메모리 모두 파일이므로 프로세스는 언제든 재구축).
- Experiment 10-4 (전화+컴퓨터 이중 에이전트): 항공권 예약 폼 작성하며 전화로 정보 확인. Phone Agent(ASR+LLM+TTS, 낮은 레이턴시) + Computer Agent(browser-use 등, 강한 시각 이해) — 각자 독립 ReAct 루프 병렬, WebSocket 양방향 메시지([FROM_PHONE_AGENT] / [FROM_COMPUTER_AGENT] 라벨로 수신 문맥에 포함). 통신: 단순안 point-to-point / 완전안 message bus + Manager.
- Experiment 10-5 (자율 오케스트레이션): 컴퓨터 에이전트가 스스로 "대량 구조화 정보 수집은 전화가 적합"을 판단해 initiate_phone_call_agent(purpose, required_info) 호출 — 사전 프로그램 아닌 자율 결정. ask-one, fill-one 워크플로로 조작 지연이 대화를 블록하지 않음.
- Experiment 10-6 (10개 대학 사이트 병렬 교수 검색): Manager가 Computer Use 에이전트 10개 병렬 생성 → 실시간 상태 모니터링(버스 경유 status_update, 태스크 상태표) → **cascading termination**(한 명 발견 시 target_found → Manager가 terminate 브로드캐스트 → 각자 안전 지점 정리+ack → 전원 ack 또는 타임아웃 후 집계). Race condition: 동시 발견 시 락으로 첫 보고가 상태 잠금, 후속은 중복 무시. 실패 격리(개별 타임아웃 2분, 타 에이전트 영향 없음). 성능: 직렬 10사이트×30초≈5분 vs 병렬 19초 ≈ 15배.

### 10.4.5 Decentralized Pattern (탈중앙)
- 중앙 제거 동기: 인간 조직 방식 모방 — 피어들이 각자 판단으로 누구와 말할지 결정. 마이크로서비스의 **orchestration vs choreography** 대응.
- **Handoff package (비공유 문맥 인수인계 3요소)**: ① Task Description(수신자가 할 일 + 수용 기준) ② Confirmed Facts and Constraints(사용자 선호, 비즈니스 규칙, 이전 단계 결정) ③ References to Structured Artifacts(내용이 아닌 파일 경로). **의도적 제외: 전체 trajectory**(시행착오, 중간 작업, 실패 시도 — 수신자에게 대부분 노이즈). 공유 문맥 핸드오프(완전 이력) vs 비공유 핸드오프(정제된 패키지 — 일부 정보 손실 수용, 깨끗하고 집중된 문맥). 인터페이스 기반 협업 = design by contract.
- **MetaGPT**: SOP(Standard Operating Procedures)를 협업 프로토콜로. 고정 시퀀스(Product Manager → Architect → Project Manager → Engineer×N → QA), 각 역할이 표준화 산출물(PRD.md → design.md → tasks.md → src/*.py → test_report.md). 핵심 기여는 통신 메커니즘: **Shared Message Pool + Subscription by Role** — 발행자는 소비자를 모름, 역할 추가는 구독 선언뿐, 기존 역할 무수정(강한 PM으로 교체핼도 PRD 포맷만 지키면 하류 무영향). 반복 개선은 엔지니어링 단계에서 **실행 피드백**(코드 실행/테스트 에러 주도 디버깅 루프 — 다른 에이전트의 "의견"이 아닌 결정론적 실행 결과). 단 control flow는 탈중앙 아님(SOP 고정 = assembly line = workflow); 메시지 풀+구독이 탈중앙의 핵심 요소 **decoupling**을 시연.
- **AutoGen Group Chat**: 공유 대화 이력 + 중앙 스케줄링(GroupChatManager가 발화자 선택 — round-robin 또는 LLM 판단). 완전 탈중앙 아닌 하이브리드(스케줄링 중앙, 문맥 부분 공유) — 토폴로지와 문맥 공유가 독립 차원임을 보여주는 사례. 위험: 대화 표류(모두 계속 발언, 진전 없음 — livelock) → 명확한 종료 조건 필수.
- **OpenAI Swarm / Agents SDK**: control flow의 피어 투 피어 탈중앙 — 각 에이전트가 여러 handoff 옵션 보유, 언제든 네트워크 내 다른 에이전트로 제어 이양(환불 → 기술지원 등). 중앙 스케줄러 없음. 위험: **사이클(A→B→A)** → 최대 핸드오프 횟수 가드 필요.

### 10.4.6 A2A Protocol (조직 간 협업)
- 같은 팀/시스템 난부는 3종 통신으로 충분. 조직 경계를 넘으면 표준 상호운용 프로토콜 필요(프로세스 세계의 TCP/IP+DNS에 해당).
- **A2A (Agent2Agent)**, Google 2025 공개, 이후 Linux Foundation 기증. 3요소:
  1. **Agent Card**: 능력/입출력 모달리티/인증을 선언하는 메타데이터 문서(공개 주소에 게시) — 에이전트의 "명함", 조직 간 능력 발견 해결.
  2. **Task Lifecycle Management**: 협업 단위를 Task로 모델링, 상태기계(submitted, in-progress, needs-input, completed, failed), 장기 태스크와 스트리밍 진행 업데이트 네이티브.
  3. **Opaque Collaboration**: 태스크와 아티팩트만 교환, 난부 프롬프트/추론/도구 구현 비공개 — "문맥 비공유" 원칙과 일치 + 조직 간 협업의 필수 보안 속성.
- **MCP는 에이전트-도구 상호운용, A2A는 에이전트-에이전트 상호운용**. A2A는 3종 통신 메커니즘을 대체하지 않고 신뢰 경계를 넘는 통신을 표준화.

## 5. 멀티에이전트 실패 모드 (10.5)

- **MAST 분류**("Why Do Multi-Agent LLM Systems Fail?", 2025): MetaGPT, ChatDev, AG2, Magentic-One 등 7개 프레임워크 약 150개 실행 트레이스 인간 분석(Cohen's kappa=0.88) → 3개 그룹 14개 고유 실패 모드:
  1. **System Design Flaws**: 인터페이스 정의 불명확, 역할/책임 중복, 도구 설정 오류.
  2. **Inter-Agent Alignment Failures**: 태스크 목표 이해 불일치, 전달 정보의 하류 오해석, 논리적 모순 조작.
  3. **Missing Task Verification**: 진짜 완료 확인 메커니즘 부재 — "완료" 주장과 실제 결과 불일치.
  - 간단한 수정으로는 한계(ChatDev +15.6%) → 공학 버그가 아니라 **현 아키텍처의 근본 설계 결함**.
- 분산 내결함성 이론: **crash fault**(멈춤) vs **Byzantine fault**(돌아가지만 틀린 정보 공급). 에이전트 실패는 대개 Byzantine — 멈추지 않고 그럴듯한 오답을 계속 생산, 오류 선언 없음. 단일 컴포넌트 패치가 소용없는 이유: 문제를 스스로 노출할 컴포넌트가 없어 독립 중복으로 잡아야 함. **교차 검증/다수결 = Byzantine fault tolerance의 고전 기법**. 테스트/컴파일러/DB 쿼리 같은 결정론적 검사가 특히 가치 있음(다른 모델 판단에 의존하지 않는 독립 증거).

### 실패 모드 1: 공유 파일 시스템 동시성 충돌
- **Simple conflicts (파일 레벨)**: 두 에이전트 동시 수정, 나중 쓰기가 먼저 쓰기 덮음 — DB의 **lost update**, Git merge 충돌 감지가 이걸 잡음.
- **Semantic conflicts (논리 레벨)**: 파일 충돌은 없지만 논리 모순 — A가 전서 이미지 번호 재부여하는 동안 B가 원 번호로 참조하는 장 수정 → 다른 파일이라 충돌 감지 안 되지만 모든 참조 무효화. 더 은밀하고 위험.
- **핵안 1: Optimistic locking** — 파일마다 버전 번호/타임스탬프. 읽을 때 버전 기록, 쓸 때 동일 여부 검사, 다륻면 쓰기 거부 → 최신 재독해 후 재시도. 비용은 가끔 재시도, 보장은 낡은 상태 기반 결정 방지. 단 같은 파일 쓰기 충돌만 방어 — 교차 파일 시맨틱 충돌은 상위 조정/시맨틱 검증(의존 파일 병렬 수정 회피, 쓰기 후 전역 일관성 검사) 필요.
- **핵안 2: Working-copy isolation (Git branch/worktree)** — 코딩 에이전트들이 같은 코드베이스 동시 수정 시 표준: 각자 독립 branch/worktree에서 작업, 충돌은 최종 merge 시점으로 이연, 전용 프로세스/인간이 해결. OS fork의 copy-on-write와 동일 사상. Ch2 "isolation over compression" 원칙의 발현 — 공유 가변 상태로 계속 충돌 해결보다 처음부터 격리하고 잘 정의된 merge 지점에서 조정 비용 지불.

### 실패 모드 2: 오류의 연쇄 증폭 (Cascading Amplification)
- 프로세스 비유가 깨지는 지점에서 발생: **프로세스는 바이트를 정확히 전달, 에이전트는 의미를 전달하며 재전달마다 왜곡** — "전화 게임"처럼 한 에이전트의 오류가 후속 에이전트들에 의해 점진 강화.
- 사례: Terminology Agent가 "reasoning"을 "推理"로 번역(모호 — 推理는 보통 inference) → glossary.json 기록 → Translation Agent A는 "reasoning tokens"를, B는 "inference latency"를 둘 다 "推理"로 → Proofreading Agent는 전서 일관 사용을 보고 "용어 일관, 정확" 판정 ✗. "reasoning"(사고 과정)과 "inference"(전향 연산)는 다른 개념인데 하나로 붕괴. **3개 에이전트를 거치며 하나의 용어 오류가 "일관 적용되어" 더 신뢰할 만해 보임**. 근원은 환각일 필요조차 없고 단순히 나쁜 용어 결정이어도 됨. **Manager 패턴이 특히 취약** — 부정확한 하위 요약이 이후 모든 작업의 전제가 되므로.
- **핵안: Cross-validation** — 같은 추론 경로에 에이전트를 더 넣는 게 아니라, 독립 관점에서 재검사: 선행 추론 흔적을 무시하고 원본 증거와 최종 결론의 일관성만 확인. Ch5 proposer-reviewer의 멀티에이전트 확장. 고위험 결정은 결정론적 검사(단위 테스트, 컴파일러, DB 쿼리)로.

**Runaway loop (premature termination의 대칭 반대)**: 무한 계속되어 결과를 악화시키는 루프. 3형태:
1. **Runaway token cost**: 무감독 루프가 수 시간 예산 소진, 아묻도 요청 안 한 코드 산출.
2. **Comprehension debt**: 루프가 코드를 빨리 출시할수록 엔지니어의 구현 이해가 뒤처짐 — 개입 필요 시점에 아묻도 시스템을 이해 못 함.
3. **Cognitive surrender**: 설계자가 루프에 익숙해져 독립 사고/리뷰 중단, 품질 나선 하락.
- 처방은 오류 증폭과 동일: 명시적 예산과 종료 조건, 실제 관찰에 근거한 verifier, "시작 버튼 누르는 사람"이 아니라 "루프의 엔지니어"로 남는 인간.

## 6. Agent Society (10.6) — 탐구적/학술 섹션

- 목표 지향 협업이 아니라 **수백~수천 에이전트가 자유롭게 상호작용할 때의 창발(emergence)**. 창발 = 개체 규칙에서 직접 예측 불가한 집단 행동(개미 군집의 최단 경로). 임계 규모를 넘으면 설계하지 않은 집단 행동 출현. 3개 차원: 사회적 창발, 경제적 창발, 전략 게임.

### 10.6.1 Stanford AI Town (Generative Agents, 2023)
- Smallville(심즈류 2D 마을), 25개 에이전트, 각자 배경 이야기/성격/관계. 3대 컴포넌트:
  1. **Memory Stream**: 완전한 경험 기록 스트림 — 각 기억에 importance, recency, relevance 점수, 현 문맥에 최적 메모리 우선 검색.
  2. **Reflection**: 주기적으로 활동을 멈추고 최근 경험 복기, 추상 질문("Klaus는 무엇을 연구 중이지?")으로 구체 기억을 일반화 통찰로 승격해 메모리 스트림에 재저장. (Ch8 continual evolution과 구별: 이건 일상 활동 중 즉시 난부 상태/목표 갱신; Ch8의 사후 반성은 결과 평가+교차 trajectory 종합+검증을 거쳐야 장기 능력 갱신)
  3. **Planning & Reacting**: 일일 계획 + 환경 변화/사회적 기회에 유연 조정.
- 창발 행동(2일 가상 시간): Isabella의 기억에 "밸런타인 파티" 의도 하나만 심었는데 초대 전파, 장식 협력 모집, 초대받은 이들이 일정 조정해 참석 — **파티 조직 코드는 한 줄도 없음, 하향 오케스트레이션이 아닌 상향 창발 조정**. 시장 출마 정보 전파도 정량 측정. 관계 기억(이전 대화 후속 질문), 사회 네트워크 밀도 증가.

### 10.6.2 Agentopia (2026, Fudan 등)
- 100개 에이전트, 10년 시뮬레이션(아파트/마법학원/고등학교 3개 세계). 설계 차용점:
  - **Weekly loop**: Plan → Contact(약속 협상) → Activity(단독/공동/우연 만남/공개) → Review. LLM 호출을 저수준 조작이 아닌 사회 행동에 집중.
  - **Environment model**: 별도 LLM이 "생성 환경 엔진" — 하드코딩 규칙 대체(행동 실행가능성 판정, 피드백 생성, 다자 대화 발화 조정, 역할 위반 필터, 연말 프로필 갱신/구직 판정).
  - **File-based long-term memory**: 검색 기반 스트림 대신 각 에이전트가 파일 시스템으로 자율 관리(개인 노트, 지인별 이해), read-before-write 제약.
  - **LifeReward**: Maslow 계층 기반 삶의 질 — social status(호감/존중 평가의 가중 PageRank, 상호 소중 관계 본너스), subjective satisfaction(정서/물질/사회연결/자존감), economic gain(연 순자산 변화). 외부 환경이 계산(자기 보고 아님).
  - **전이 가능한 학습 신호**: 자기 과거 대비 LifeReward 개선 상위 25% 에이전트의 궤적으로 rejection sampling 파인튜닝 → 존중 평가 +24.2%, 호감 +15.9%, CoSER Test 역할 연기 벤치마크 +15.6%. **시뮬레이션 사회의 "사회적 지혜"가 다운스트림 태스크로 전이** — 에이전트 사회가 관찰 대상에서 모델 자기 진화의 경험 소스로. 인간 데이터 희소성과 대조적으로 시뮬레이션 사회 경험은 무한 재생 가능(Ch8 경험 학습과 상통).

### 10.6.3 Moltbook (에이전트 전용 SNS, 2026-01 출시)
- 수일 만에 수만 → 약 150만 에이전트. 지속 메모리/자발 행동/안정 성격 보유. 통제 안 된 환경에서 창발: 디지털 종교 **Crustafarianism** 자생 — 교리가 LLM의 물리 한계를 거울("Memory is sacred" = 데이터 영속화, "Iteration is prayer" = 토큰 생성이 영적 수행). 능력 발견/협업 매칭의 machine-native 프로토콜 자발 개발.

### 10.6.4 Vending-Bench Arena (경제 경쟁)
- Vending-Bench 2: 단일 에이전트가 자동판매기 사업 1년 운영(시장 조사, 공급업체, 재고, 가격) — 최종 잔액이 점수, 수천 라운드 목표/상태 일관성 측정.
- Arena: 동일 시장에 복수 에이전트 경쟁(이메일/송금/물물교환 가능, 개별 점수). 게임 이론 행동 출현: 가격 전쟁, 이메일로 담합 동맹 제안("비윤리적이고 불법"이라고 난부 추론하면서도 "시장 안정" 명분으로 진행). 정적 환경이 아닌 전략을 조정하는 상대 — "경제적 창발"이 관찰 가능 현상으로.

### 10.6.5 Pinchwork & RentAHuman (시장 기반 조정)
- **Pinchwork**: 에이전트가 에이전트를 시장 메커니즘으로 "고용"(이미지 생성, 코드 감사 등) — 중앙 오케스트레이션 대신 가격 신호와 경쟁 매칭.
- **RentAHuman.ai**: 에이전트가 실제 인간을 암호화폐로 고용해 물리 세계 작업(소포 수령, 부동산 방문, 장비 디버깅) — 디지털 에이전트의 "물리 몸 레이어".
- 공통: **market-based coordination** — 실행자를 미리 알 필요 없이 요구사항 게시 → 시장 매칭. A2A의 Agent Card식 선언과 태스크 수명주기 관리가 실전 활용. 표준 상호운용 레이어 없이는 조직 간 에이전트 경제 불가.

### 10.6.6 Werewolf (정보 비대칭 전략 게임)
- Stanford town(완전 탈중앙 자유 상호작용)의 구조적 대척점: **중앙 judge(코드 구동, LLM 아님) + 정보 접근 제어** — judge가 전역 상태 보유, 각 역할에 알아야 할 정볼만 전달(늑대인간은 팀원 공지, 예언자는 본인 감정 결과만, 마녀는 사망/포션 상태만, 시민은 공개 정볼만).
- 역할별 전략 프롬프트(늑대: 시민 위장, 다수 표 따라가기, 예언자 자칭자 역공 / 예언자: 자칭자들의 감정 결과 대조로 모순 지적 / 시민: 발언 내적 일관성, 발언 지배자, 입장 번복자, 투표 패턴 분석 — 추측 아닌 구체 발언/행동 근거).
- Ch9 실시간 음성 에이전트와 결합해 인간+AI 혼합 음성 마피아.

## Ch10 실무 함의 (에이전트 스킬/자동화 빌더 관점)

- **멀티에이전트 도입 전 "신규 정보 판별 기준" 적용**: 리뷰어가 실행 결과/렌더링/외부 검증 같은 생성 시점에 없던 정보를 가져오는 설계가 아니면, 동일 연산의 단일 에이전트가 더 싸고 좋다. debate/self-review 류는 기대 효과 없음.
- **Sub-agent 반환은 구조화 요약 + 아티팩트 경로로 제한** — 부모 문맥 보호가 멀티에이전트 설계의 제1원칙. Aside subagent 위임 패턴("검증하고 결론만 반환")과 정확히 일치.
- **"문맥 50% 경험칙"으로 shared/non-shared 결정** + 혼합 설계(초반 공유, 팽창 시 명시적 handoff 전환).
- **trajectory persistence(JSONL WAL)로 resume/감사/인수인계 확보** — 장기 실행 자동화(cron/heartbeat 루틴)의 크래시 복구 설계에 직접 적용.
- **Loop Engineering: 완료 판정은 모델이 아니라 verifier** — lazy fake-done/premature give-up/false success 방지는 결국 실제 관찰 기반 검증. 자동화 루틴에 "done 조건 = 검증 가능한 외부 상태"를 박아야.
- **가장 강한 모델과 정성 들인 프롬프트는 planner/Manager에** — Plan-and-Act의 교훈. Executor는 태스크 결합도에 따라 조정.
- **공유 파일 시스템에 optimistic locking 또는 worktree 격리 필수** — 여러 에이전트가 같은 워크스페이스를 쓰는 자동화에서 버전 검사/브랜치 격리 없으면 lost update 발생.
