Lesson 0004 · AI Agents in Depth

상태 바, 컨텍스트 압축, 서브에이전트 격리

Attention은 조회에는 강하지만 집계에는 약하다. 흩어진 상태를 명시 지식으로 증류해 끝에 놓는 세 가지 기법 — status bar, compression, isolation — 이 장수 에이전트의 성패를 가른다.

오늘의 한 줄 답: 모델이 "몇 번 시도했나, 지금 몇 시인가, 뭘 아직 못 했나"를 원시 로그에서 매번 재계산하게 하지 말고, 코드가 유지하는 상태 요약을 컨텍스트 끝에 놓아라. 압축은 사후 구제, 격리는 사전 차단이다.

1. Status Bar: 흩어진 상태를 끝에 증류한다

Agent Status Bar는 framework가 컨텍스트 끝에 user-role 메시지로 주입하는 상태 요약(호출 횟수, 현재 시각, TODO 진행)이다. 폰 상태바를 떠올리면 된다. system prompt가 고정 매뉴얼이라면 status bar는 실시간 대시보드다.

이론적 근거가 중요하다: in-context learning은 추론(reasoning)이 아니라 검색(retrieval)에 가깝다. Attention은 기존 토큰 조회에는 강하지만, 단일 forward pass로 "지금까지 몇 번 전화했나" 같은 집계 상태를 능동 요약하지는 못한다. 그 결론은 원시 레코드에 흩어져 있고, 모델이 매번 재계산하면 비효율에 오류가 낀다. Status bar는 이 암묵 상태를 명시 지식으로 증류하고, 생성 위치에 인접한 맨 끝에 두어 attention을 조종(steering)한다.

Context Distillation 벤치마크 (Li & Shi, 2026; 3종 태스크, 11개 모델, ~24,000회 평가):
① 약한 모델은 정확도 +40~54%p 회복 — 로컬 2B가 status bar 없는 프론티어 모델과 대등해짐
② 강한 모델은 추론 토큰 80-90% 이상 절감, 지연·비용 약 1/10
③ status bar 없으면 쿼리당 추론량이 context 길이에 비례해 증가, 있으면 사실상 상수
④ 형식은 key-value 필수 — 산문 형태는 재파싱 비용 때문에 효과 급감

2. Status Bar의 3대 실천 교훈

  1. LLM이 아니라 코드로 유지하라 — 20줄의 정규식이 ground truth 수준인데, 프론티어 모델의 일괄 요약은 오류가 많아 baseline 이하로 떨어졌다. LLM이 꼭 필요하면 항목별 추출 후 코드로 집계.
  2. 원본 삭제 전, 미래 질문을 커버하는지 확인하라 — status bar는 lossy projection이다. "쌍별 조합"만 저장했는데 "삼중 교집합"을 묻자 Claude의 정확도가 100% → 7.6%로 붕괴했다. 불완전한 status bar는 false authority: 모델이 틀린 상태를 확신하게 만든다. 새 질문 유형은 DB 스키마 변경처럼 취급하라.
  3. 정확도를 1차 프로덕션 지표로 모니터링하라 — 모델은 status bar를 거의 무조건 신뢰한다. 오차 ~10% 미만이면 이점이 유지되지만 그 이상이면 없는 것보다 나쁘다. 신뢰 가능한 실세계 관측에서만 생성할 것(status bar poisoning 주의).

Time Sense 3축(저자 논문)도 같은 원리다: Urgency(예산 축 — 시간 촉박 시 결단), Persistence(종점 축 — 410 Gone에 5회 재시도는 과잉, 검색 2회 포기는 과소), Vigilance(감시 축 — 500ms 예상 호출이 5초 걸리면 조사). 벤치마크에서 raw timestamp만 주면 정보 없음과 2-3%p 차이였지만, timestamp + 해석 지침을 함께 주자 통과율이 10%대 → 40-50%(+19~49%p)로 뛰었다. 모델에게 부족한 것은 읽기(reading)가 아니라 읽은 값을 행동으로 번역하는 전략이다.

3. Context Compression: overflow가 아니라 rot이 문제다

압축의 동기는 두 가지다: ① 길이/비용 제약, ② 추론 품질 향상 — 윈도우가 남아 있어도 요약된 지식이 원시 정볼보다 모델에 유용한 경우가 많다. 10회 검색 결과 수만 토큰에 흩어진 것보다 1회 LLM 호출로 만든 구조화 요약("A는…, B는…, C는 미확보")이 낫다.

핵심 구별: Context Overflow ≠ Context Rot. overflow는 "못 넣음", rot은 "넣었는데 못 찾음" — 겉으로는 정상 작동하면서 결정 품질이 조용히 악화된다. 흔한 실패 모드는 윈도우 부족이 아니라 정보 밀도 부족이다.

실험 2-9(★★★, Kimi K3에 128K 윈도우 제한을 두고 장문 조사 태스크 수행)의 6전략 비교:

전략토큰결과해석
No compression>110K✗ overflow압축 없이는 실패
Individual summary123K✓ 24회 반복결과당 2-3문단, 정보 파편화
Combined summary55K✓ 21회초장문 입력 절단 위험
Context-aware25K✓ 15회, 최소"Given query / Current context"로 압축 방향 지시, 147,877자→1,963자(1.3%)에도 핵심 보존
Aware + citation46K✓ 검증 가능손실 압축 + 무손실 색인(URL) 결합
Adaptive window181K✓ 최고 충실도80% 임계 도달 시 미압축분 일괄 배치 압축

압축과 KV cache의 공존 포인트: 압축으로 교체한 지점 이후 캐시는 무효가 되므로, 매 라운드 압축하지 말고 임계(예: 윈도우의 80%) 근접 시 배치 압축한다. system prompt와 tool definitions는 절대 건드리지 않고 대상은 history의 tool results다.

4. 프로덕션 5계층과 보존 우선순위

프로덕션(Claude Code 참조)의 계층적 압축 메커니즘 — 앞 3개가 저비용·캐시 영향可控으로 우선이다:

  1. Tool Result Budget Control — 대형 출력은 디스크에 저장하고 모델엔 미리보기만. 대체 문자열은 최초 발생 시 동결.
  2. Direct Noise Deletion — 저가치 콘텐츠는 요약 없이 삭제. 노이즈 요약은 토큰 낭비다.
  3. API-Level Micro-Compression — 서버측 context editing으로 특정 tool 결과 제거. overflow 직전에만.
  4. Archival Summarization — git log처럼 라운드별 구조화 요약(squash 아님).
  5. Full Compression — 최후 수단. 연속 실패 시 circuit breaker(프로덕션에 압축 실패 반복 루프 세션이 실제 존재).

압축이 가장 잃기 쉬운 것은 디테일이 아니라 초기 아키텍처 결정, 제약의 근거, 실패한 경로다. 보존 우선순위: ① 아키텍처 결정·핵심 제약 ② 수정 파일 목록·핵심 변경 기록 ③ 검증 상태(pass/fail) ④ 미해결 TODO·롤백 노트 ⑤ tool 출력은 결론만. 그리고 UUID·해시·IP·포트·URL·파일명은 한 글자도 바꾸지 말 것 — PR 번호 한 자리가 바뀌면 이후 tool call이 직접 실패한다.

5. Isolation over Compression: 서브에이전트 격리

압축보다 먼저 고려할 것이 Sub-Agent Context Isolation이다. 다수 파일 읽기, 코드베이스 광범위 검색처럼 대량 중간 산출물이 나오는 태스크를 sub-agent에 위임하고, 메인 context에는 태스크 기술 + 수백 토큰의 결론 2개 메시지만 남긴다.

압축 (Compression)
사후 손실 구제. 추가 LLM 호출 비용. 메인 context 안에서 원문을 결론으로 대체.
격리 (Isolation)
사전 차단. 메인 KV prefix 무결 유지. 오염 원인이 처음부터 메인 context에 들어오지 않음.
격리의 비용
sub-agent는 메인 context를 못 본다 → 태스크 기술(task brief)이 self-contained해야 한다.

Claude Code의 Task tool, Deep Research의 검색 sub-agent가 구현 예다. 격리할 것인가 압축할 것인가의 기준은 단순하다: 중간 산출물이 메인 라인의 결정에 필요 없다면 격리, 필요하다면 방향 지시(context-aware) 압축.

실무 번역: Aside의 MEMORY.md·루틴 메모리 파일은 사실상 status bar다 — 모델이 무조건 신뢰하는 위치에 놓인다. 즉 그 파일의 정확도가 곧 에이전트의 결정 품질이고, 잘못 적힌 메모리는 false authority다. 네 ERP 동기화 루틴의 "0행 무음 실패"는 status bar(실행 결과의 명시 상태 기록)가 없었던 교과서적 사례다. 그리고 context_explorer·subagent 위임 패턴은 이미 isolation over compression의 실천이다 — 탐색은 위임하고 결론만 받아 메인 세션을 지키는 구조.

7. 미니 실습 (10분)

네가 운영 중인 Aside 루틴 하나(예: erp-sales-hx-daily 또는 pathy-daily-content)에 status bar를 설계해 보자. 종이나 메모에 아래를 적는다.

  1. 다음 실행이 알아야 할 상태 5개를 key-value로 (예: last_run_date, rows_synced, consecutive_failures)
  2. 각 항목을 갱신하는 주체가 코드인지 LLM인지 표시 — LLM 표시가 있으면 코드로 바꿀 수 없는지 검토
  3. 이 status bar가 답하지 못하는 "미래 질문" 하나를 적고, false authority 위험이 없는지 점검
  4. 갱신 방식 선택: 매 실행 replace vs 누적 append — 갱신 빈도와 history 길이로 판단
